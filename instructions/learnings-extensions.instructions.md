# Learnings — Editor Extensions

> **See also:** The extensions communicate with the language server — see [learnings-lsp.instructions.md](learnings-lsp.instructions.md) for protocol details and LSP features. Syntax highlighting queries must match the Tree-sitter grammar in `extensions/zed/grammars/`.

## Editor Extensions

- **VS Code** (`extensions/vscode/`): TypeScript/JavaScript extension bundling LSP + DAP. TextMate grammar for syntax highlighting.
- **Zed** (`extensions/zed/`): Rust extension with Tree-sitter grammar and LSP integration.
- **Modifying `grammar.js` requires regenerating and committing the parser artifacts.** The CI `Tree-sitter Grammar Tests` job (`ci-zed.yml`) diffs `src/parser.c` against a fresh `tree-sitter generate` output and fails if they diverge. After editing `extensions/zed/grammars/tree-sitter-luma/grammar.js`, run `cd extensions/zed/grammars/tree-sitter-luma && npm ci && ./node_modules/.bin/tree-sitter generate` and commit the resulting changes under `src/` (at minimum `parser.c`, `grammar.json`, `node-types.json`).
- **`build_workspace_config` (`extensions/zed/src/lib.rs`) deliberately omits `codeLens` from the `luma` settings payload sent to the language server**: per `extensions/FEATURE_PARITY.md`, code lens is VS Code-only, so Zed must never advertise `codeLens.enabled` (even `false`) to avoid implying the feature applies there. Extracting the payload-building logic into its own testable function (previously inlined in the `workspace_configuration` trait method) made this omission assertable by a unit test instead of only visible by reading the merge call site.
- **Tree-sitter highlight queries exist as canonical and editor copies, and the editor copy intentionally diverges from canonical.** `extensions/shared/queries/highlights.scm` is the canonical reference but is **not consumed at runtime**: Zed ships `extensions/zed/languages/luma/highlights.scm`, which renames capture *groups* to its editor's highlight conventions (e.g. for `interpolation` the canonical `@punctuation.special` becomes `@string.special`; Zed also reorders literals and uses `@constant.builtin`) while matching the **same grammar nodes**. So a change to query *structure* — e.g. reordering a node's children — must be hand-applied to both files; editing only the shared copy changes nothing a user sees. `extensions/shared/sync-queries.py` (`--check`/`--force`) is meant to propagate the canonical copy, but its structural compare only strips comment/blank lines — it does **not** ignore group-name renames despite its docstring — so `--check` flags the *intentional* group-name divergence and exits 1, and `--force` does a literal `shutil.copy2` that would clobber the editor-specific names. It is **not** wired into CI; treat it as a coarse diff aid, not a clean gate.
- **A query pattern's child order must match the grammar's `seq(...)` order, or it silently never matches** — and stricter Tree-sitter runtimes reject the *entire* highlights query, killing all highlighting. The grammar is `generic_params: seq("<", commaSep1($.type_identifier), ">")`, so the capture must sit *between* the brackets — `("<" (type_identifier) @type.parameter ">")`, **not** `("<" ">" (type_identifier))`, which can never fire. **Validate impossible patterns with `tree-sitter query`, never `tree-sitter highlight`**: the latter ran in degraded mode here and "passed" by a coincidental match against the temp filename, hiding the dead pattern. `extensions/tests/validate_queries.js` (run manually from the repo root after generating the parser in `extensions/zed/grammars/tree-sitter-luma` via `npx tree-sitter generate`; among the Tree-sitter checks only `parse_fixtures.js` is wired into CI, so this guard is effectively local-only) compiles the editor copy against the grammar via `tree-sitter query` and asserts expected captures on known snippets; it SKIPs cleanly when the CLI/parser is unavailable. When you add or reorder a highlight capture, add a `tree-sitter query` regression snippet that asserts the new capture appears.
- **Zed inline "Run" buttons need BOTH a `runnables.scm` tag AND a matching task template in `languages/<lang>/tasks.json` — task templates in `config.toml` (`[[tasks]]`) are silently ignored.** Zed's language `config.toml` schema (`LanguageConfig`) has no `tasks` key; the extension host loads task templates only from `TaskTemplates::FILE_NAME` (`"tasks.json"`) in the language directory (`crates/extension_host/src/extension_host.rs` → `ContextProviderWithTasks::new`). A `runnables.scm` `(#set! tag main)` produces a `RunnableTag("main")` (only the `tag` property key is read by `runnable_tags_from_pattern`; `tag.args` and other keys are harmless no-ops), and Zed shows a run button *only* when a `tasks.json` template's `tags` array contains that same string. So the two files must stay in sync: `runnables.scm` tags ⇄ `tasks.json` `tags`. The grammar-binding tests in `grammars/tree-sitter-luma/bindings/rust/lib.rs` only prove the query *captures* `@run` — they cannot catch a missing/mismatched `tasks.json`, so verify runnables end-to-end in Zed (or by asserting the tag sets match).
- **A Zed debug adapter needs `extension.toml` to declare `[lib] kind = "Rust"`, or it never appears in the `debug: start` picker.** Debug adapters (and language servers, and context servers) are WASM-only features: the extension host registers them by iterating `wasm_extensions` — extensions whose compiled `extension.wasm` component is loaded (`crates/extension_host/src/extension_host.rs`, the `for (manifest, wasm_extension) in &wasm_extensions` loop). Zed only *builds* that component when `manifest.lib.kind == Some(Rust)` (`crates/extension/src/extension_builder.rs`, the `rust_compilation_task` guard). `populate_defaults` auto-sets `lib.kind` from a present `Cargo.toml`, but only at compile/package time — the *packaged/published* manifest must carry the section explicitly, so declare `[lib] kind = "Rust"` (with `version` matching the `zed_extension_api` Cargo dep; it is refreshed from the WASM at build time) rather than relying on auto-detection. This bug hides because Luma's LSP is resolved via a manifest `[language_servers.*.binary] path` and keeps working without the WASM, so only the DAP silently breaks. Pinned by `manifest_declares_rust_library` in `extensions/zed/src/tests.rs`.
- **A saved scenario in `.zed/debug.json` is silently dropped from the `debugger: start` picker unless its `adapter` string case-sensitively equals a registered adapter name.** Zed's New Process modal filters saved scenarios with `valid_adapters.contains(&scenario.adapter)` where `valid_adapters` is the `HashSet` of registered `DebugAdapterName`s (`crates/debugger_ui/src/new_process_modal.rs`). The Luma extension registers its adapter as **`Luma`** (`[debug_adapters.Luma]`), so a scenario written as `"adapter": "luma"` matches nothing and vanishes — while sibling scenarios for an installed adapter (e.g. `"CodeLLDB"`) still show, making it look like "only C++ entries exist". The locator is a *separate* namespace registered lowercase (`[debug_locators.luma]`); do not confuse it with the adapter name. Keep every `.zed/debug.json` `adapter` (and any `debug.json` in docs) exactly `"Luma"`. Pinned by `workspace_debug_json_uses_registered_adapter_name` in `extensions/zed/src/tests.rs`.
