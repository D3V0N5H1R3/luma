# Learnings — Editor Extensions

> **See also:** The extensions communicate with the language server — see [learnings-lsp.instructions.md](learnings-lsp.instructions.md) for protocol details and LSP features. Syntax highlighting queries must match the Tree-sitter grammar in `extensions/zed/grammars/`.

## Editor Extensions

- **VS Code** (`extensions/vscode/`): TypeScript/JavaScript extension bundling LSP + DAP. TextMate grammar for syntax highlighting.
- **Zed** (`extensions/zed/`): Rust extension with Tree-sitter grammar and LSP integration.
- **Modifying `grammar.js` requires regenerating and committing the parser artifacts.** The CI `Tree-sitter Grammar Tests` job (`ci-zed.yml`) diffs `src/parser.c` against a fresh `tree-sitter generate` output and fails if they diverge. After editing `extensions/zed/grammars/tree-sitter-luma/grammar.js`, run `cd extensions/zed/grammars/tree-sitter-luma && npm ci && ./node_modules/.bin/tree-sitter generate` and commit the resulting changes under `src/` (at minimum `parser.c`, `grammar.json`, `node-types.json`).
- **Config/keybinding/platform/type constants are code-generated for *both* extensions from shared sources — never hand-edit a `src/generated/` file.** `extensions/shared/generate-all.py` runs seven generators (config, editor-native config, download constants, platform maps, keybindings, test-discovery, builtin-types) whose inputs of record are `extensions/shared/defaults.json`, `keybindings.json`, the download/platform maps, and the interpreter's built-in list; outputs are `extensions/vscode/src/generated/*.ts` + `extensions/zed/src/generated/*.rs`, and *spliced regions* of `extensions/vscode/package.json` (contributes/config/keybindings) and `extensions/zed/KEYBINDINGS.md`. After changing any input (e.g. removing a setting when a feature is dropped) run `python extensions/shared/generate-all.py` and commit every regenerated file. **`extensions/shared/ci-check-generated.py` regenerates then `git diff`s against `HEAD`**, so with **uncommitted** work it reports every session-edited generated file as "stale" — a false positive, not real drift. To actually test freshness of an uncommitted change, run `generate-all.py` and check whether it produces *further* working-tree changes (a byte-identical diff means the generated files already match their sources).
- **Tree-sitter highlight queries exist as canonical and editor copies, and the editor copy intentionally diverges from canonical.** `extensions/shared/queries/highlights.scm` is the canonical reference but is **not consumed at runtime**: Zed ships `extensions/zed/languages/luma/highlights.scm`, which renames capture *groups* to its editor's highlight conventions (e.g. for `interpolation` the canonical `@punctuation.special` becomes `@string.special`; Zed also reorders literals and uses `@constant.builtin`) while matching the **same grammar nodes**. So a change to query *structure* — e.g. reordering a node's children — must be hand-applied to both files; editing only the shared copy changes nothing a user sees. `extensions/shared/sync-queries.py` (`--check`/`--force`) is meant to propagate the canonical copy, but its structural compare only strips comment/blank lines — it does **not** ignore group-name renames despite its docstring — so `--check` flags the *intentional* group-name divergence and exits 1, and `--force` does a literal `shutil.copy2` that would clobber the editor-specific names. It is **not** wired into CI; treat it as a coarse diff aid, not a clean gate.
- **A query pattern's child order must match the grammar's `seq(...)` order, or it silently never matches** — and stricter Tree-sitter runtimes reject the *entire* highlights query, killing all highlighting. The grammar is `generic_params: seq("<", commaSep1($.type_identifier), ">")`, so the capture must sit *between* the brackets — `("<" (type_identifier) @type.parameter ">")`, **not** `("<" ">" (type_identifier))`, which can never fire. **Validate impossible patterns with `tree-sitter query`, never `tree-sitter highlight`**: the latter ran in degraded mode here and "passed" by a coincidental match against the temp filename, hiding the dead pattern. `extensions/tests/validate-queries.js` (run manually from the repo root after generating the parser in `extensions/zed/grammars/tree-sitter-luma` via `npx tree-sitter generate`; among the Tree-sitter checks only `parse-fixtures.js` is wired into CI, so this guard is effectively local-only) compiles the editor copy against the grammar via `tree-sitter query` and asserts expected captures on known snippets; it SKIPs cleanly when the CLI/parser is unavailable. When you add or reorder a highlight capture, add a `tree-sitter query` regression snippet that asserts the new capture appears.
- **Zed inline "Run" buttons need BOTH a `runnables.scm` tag AND a matching task template in `languages/<lang>/tasks.json` — task templates in `config.toml` (`[[tasks]]`) are silently ignored.** Zed's language `config.toml` schema (`LanguageConfig`) has no `tasks` key; the extension host loads task templates only from `TaskTemplates::FILE_NAME` (`"tasks.json"`) in the language directory (`crates/extension_host/src/extension_host.rs` → `ContextProviderWithTasks::new`). A `runnables.scm` `(#set! tag main)` produces a `RunnableTag("main")` (only the `tag` property key is read by `runnable_tags_from_pattern`; `tag.args` and other keys are harmless no-ops), and Zed shows a run button *only* when a `tasks.json` template's `tags` array contains that same string. So the two files must stay in sync: `runnables.scm` tags ⇄ `tasks.json` `tags`. The grammar-binding tests in `grammars/tree-sitter-luma/bindings/rust/lib.rs` only prove the query *captures* `@run` — they cannot catch a missing/mismatched `tasks.json`, so verify runnables end-to-end in Zed (or by asserting the tag sets match).
- **A Zed debug adapter needs `extension.toml` to declare `[lib] kind = "Rust"`, or it never appears in the `debug: start` picker.** Debug adapters (and language servers, and context servers) are WASM-only features: the extension host registers them by iterating `wasm_extensions` — extensions whose compiled `extension.wasm` component is loaded (`crates/extension_host/src/extension_host.rs`, the `for (manifest, wasm_extension) in &wasm_extensions` loop). Zed only *builds* that component when `manifest.lib.kind == Some(Rust)` (`crates/extension/src/extension_builder.rs`, the `rust_compilation_task` guard). `populate_defaults` auto-sets `lib.kind` from a present `Cargo.toml`, but only at compile/package time — the *packaged/published* manifest must carry the section explicitly, so declare `[lib] kind = "Rust"` (with `version` matching the `zed_extension_api` Cargo dep; it is refreshed from the WASM at build time) rather than relying on auto-detection. This bug hides because Luma's LSP is resolved via a manifest `[language_servers.*.binary] path` and keeps working without the WASM, so only the DAP silently breaks. Pinned by `manifest_declares_rust_library` in `extensions/zed/src/tests.rs`.
- **A saved scenario in `.zed/debug.json` is silently dropped from the `debugger: start` picker unless its `adapter` string case-sensitively equals a registered adapter name.** Zed's New Process modal filters saved scenarios with `valid_adapters.contains(&scenario.adapter)` where `valid_adapters` is the `HashSet` of registered `DebugAdapterName`s (`crates/debugger_ui/src/new_process_modal.rs`). The Luma extension registers its adapter as `Luma` (`[debug_adapters.Luma]`), so a scenario written as `"adapter": "luma"` matches nothing and vanishes — while sibling scenarios for an installed adapter (e.g. `"CodeLLDB"`) still show, making it look like "only C++ entries exist". The locator is a *separate* namespace registered lowercase (`[debug_locators.luma]`); do not confuse it with the adapter name. Keep every `.zed/debug.json` `adapter` (and any `debug.json` in docs) exactly `"Luma"`. Pinned by `workspace_debug_json_uses_registered_adapter_name` in `extensions/zed/src/tests.rs`.
- **Zed applies the LAST highlight pattern that captures a node** (as Neovim does; the `tree-sitter highlight` CLI and Helix use first-match). So the general fallbacks `(identifier) @variable` / `(type_identifier) @type` must be the *first* patterns in `languages/luma/highlights.scm` — at the end of the file they overrode every specific capture (calls, parameters, properties, variants, generic params). A wrapper node with the same range as its child (`function_name` → `identifier`) needs the capture on the inner node too, or the fallback still wins. `validate-queries.js` checks the winning capture per token (`PRECEDENCE_TESTS`); `tests.rs` pins the fallback order in CI. Zed's built-in grammars (`crates/grammars/src/<lang>/`) are the reference for every query convention: `(_ "{" "}" @end) @indent` (an `@indent` on the `{` token alone never indents the body), outline patterns need `@item` (decorators use a standalone `@annotation`), auto-closing comes from `brackets` in `config.toml` with `not_in` scopes named by `overrides.scm`.
- **Only nine built-in type names are reserved words; `void` (in no keyword table) and the container/handle names (`set`, `task`, `queue`, `channel`, … — `k_builtin_type_identifiers` in `token_type.hpp`) lex as identifiers and are valid variable names.** A grammar must therefore scope them as types only in type position, or `print(task)` and `match channel {` render as types. The TextMate `#type` rule splits the reserved keywords (always types) from the contextual names (types only before `<` or a name, or after `<` or `->`), mirroring the language server's semantic-token rule; spans that can hold only types — generic arguments, tuple types, function-type parameter lists — go through `#type_arguments`/`#builtin_type_name`, which match unconditionally so `result<(set, set)>` stays coloured. `builtin-types.test.ts` checks both `type` sub-patterns and `builtin_type_name` against `extensions/shared/builtin-types.json`. Generic-argument spans must not treat the `>` of `->` as a closing bracket.
- **A top-level TOML key written after a `[table]` header belongs to that table.** `snippets = [...]` placed below `[lib]` in `extension.toml` became `lib.snippets`, so Zed loaded none of the snippets. Pinned by `manifest_snippets_key_is_top_level` in `tests.rs`.
- **Tree-sitter dedupes identical anonymous `repeat` helpers across rules, which can hide a declared GLR conflict.** A conflict listed for `[$.tuple_destructure, $.lambda_parameter]` never forked because the comma-list repeat had been merged with another rule's helper (`choice_variant_repeat1`), so the parser silently picked the lambda. Give the repeated element its own (hidden) rule (`_tuple_binding`) and list *that* in `conflicts`; confirm with `tree-sitter parse --debug=normal` that the parser actually splits.
- **The grammar cannot see Luma's newline rule** (a `(` that begins a line starts a new statement) without an external scanner. Postfix calls whose callee could end the previous line (`obj.field(...)`, `f(1)(2)`) therefore carry no static precedence plus a `prec.dynamic` preference and a declared `[$._expression, $.call_expression]` conflict, so GLR drops the call reading when the next line is, say, a tuple destructuring. Giving them `prec(15)` made `pair.0` + newline + `(integer a, integer b) = pair` parse as a call. Check grammar changes against every `.luma` file in `examples/`, `tests/features/`, and `benchmarks/` (`tree-sitter parse --quiet`), not just the fixtures — the fixtures once passed while 86 of 209 repo files had `ERROR` nodes.
- **Every expanded snippet must parse.** Placeholder defaults are inserted verbatim, so a keyword default (`${1:type}`, `${2:result}`, `${3:dictionary}`) or an untyped lambda is a `SyntaxError` the moment the user accepts it. `validate-snippets.test.mjs` runs `luma --check` on every expansion when a built interpreter is available (exit 3 = syntax error; type errors from placeholder names are expected).
- **`vscode-languageclient` registers server-advertised commands globally**, so with one client per workspace folder the second client's `ExecuteCommandFeature` throws "command already exists" and that client never starts. `LumaLanguageClient` skips that feature; the extension registers `luma.showReferences` once (`lsp/commands.ts`) and routes it to the owning client (`ClientManager.executeServerCommand`).
