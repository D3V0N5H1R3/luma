# Learnings — Build

> **See also:** C++ portability issues often surface during CI — see the core [learnings.instructions.md](learnings.instructions.md) § Architecture & Pipeline for the phase where a build failure roots. Compiler-specific codegen traps (clang-cl funclet, ASan) are documented here because they manifest as build/CI failures, but may root-cause to code in `core/runtime/`.

## Build System

*Canonical guides: [build.instructions.md](build.instructions.md) and [cmake.instructions.md](cmake.instructions.md). The notes below are a quick-reference summary.*

- CMake 3.21+ with C++20 required, no extensions. The top-level `VERSION` file is the single source of truth for the project version (read by `CMakeLists.txt` into `project()`, `common/version.hpp`, and CPack); never hardcode the version number elsewhere.
- Key build options: `LUMA_BUILD_TESTS` (ON), `LUMA_BUILD_FUZZ` (OFF), `LUMA_FEATURE_SANITIZERS` (OFF), `LUMA_FEATURE_COVERAGE` (OFF), `LUMA_FEATURE_TLS` (ON), `LUMA_FEATURE_WEBVIEW` (ON), `LUMA_FEATURE_LTO` (OFF).
- The two `LUMA_HAS_*` macro-scopes are gated by `LUMA_FEATURE_TLS` → `LUMA_HAS_TLS` and `LUMA_FEATURE_WEBVIEW` (+ backend detection) → `LUMA_HAS_WEBVIEW`. The CI `feature-flags` job builds with each OFF so the stub paths stay compiled and tested; locally, build with `-DLUMA_FEATURE_TLS=OFF` / `-DLUMA_FEATURE_WEBVIEW=OFF` to exercise them.
- 13 user-facing configure presets: `default`, `debug`, `msvc`, `xcode`, `sanitize`, `relwithdebinfo`, `coverage`, `lto`, `ninja`, `arm64-cross`, `release-no-tests`, `windows-arm64`, `macos-universal` (plus hidden `_base*` presets). See [build.instructions.md](build.instructions.md) §3 for the full preset/purpose table.
- Quick start: `cmake --preset default && cmake --build --preset default && ctest --preset default`.
- Windows (MSVC): always use `--config Release/Debug` with multi-config generators.
- Compiler security hardening is applied to all targets: MSVC gets `/W4 /permissive-`, SDL checks, CFG, DEP, ASLR; GCC/Clang get `-Wall -Wextra -Wpedantic`, stack protector, PIE, RELRO, non-exec stack.
- External dependencies are vendored in `external/`: mbedtls (HTTPS), miniz (compression), webview (GUI).
- **Toolchain minimum is GCC 13+ / Clang 15+ / MSVC 2022+ because Luma uses the C++20 library features `std::format` and `std::chrono::clock_cast`**, which libstdc++ ships only from GCC 13. Debian bookworm and the bookworm-based Raspberry Pi OS default to GCC 12, so `#include <format>` fails with "No such file or directory"; CI therefore builds the Debian matrix entry and the ARM64 RPi proxy on Debian **trixie** (GCC 14). Apple libc++ lacks `clock_cast` entirely, so the file-time conversion is feature-tested with a rebasing fallback in `core/common/file_time.hpp`.
- **`CMAKE_POSITION_INDEPENDENT_CODE` is set `ON` globally** (top-level `CMakeLists.txt`) so every static library — first-party and vendored — compiles `-fPIC`. The executables link `-pie` for ASLR hardening; Ubuntu's GCC defaults to PIE so partial `-fPIE` on executables alone happened to work, but Fedora's does not (`relocation R_X86_64_32S against '.rodata' can not be used when making a PIE object`). No-op on Windows/macOS.
- **The Linux GraphicalUi backend links WebKitGTK via raw pkg-config result variables, not a `pkg_check_modules` IMPORTED_TARGET** (`cmake/LumaWebView.cmake`): an `IMPORTED_TARGET` (even with `GLOBAL`) is directory-scoped and unresolvable at generate time for `luma_core`'s cross-directory PUBLIC consumers (the `luma` executable, tests). Use `WEBKITGTK_LINK_LIBRARIES` (full paths, no scope) for the PUBLIC link and attach `WEBKITGTK_INCLUDE_DIRS`/`WEBKITGTK_CFLAGS_OTHER` to the `luma_webview` INTERFACE target.

## Static Analysis (clang-tidy)

*Configured in `.clang-tidy` (requires clang-tidy 18+ and a `compile_commands.json`, enabled via `CMAKE_EXPORT_COMPILE_COMMANDS`). A `tidy` build target (guarded by `find_program(CLANG_TIDY_EXE ...)`) wraps the run.*

- `.clang-tidy` is the **single source of truth** for severity: `WarningsAsErrors: 'clang-analyzer-*,bugprone-*,concurrency-*'` — these real-bug categories fail the build everywhere (local `tidy` target, editor integrations, CI). Style groups (`readability-*`, `modernize-*`, …) stay advisory by their absence from that list. CI no longer passes its own `--warnings-as-errors`.
- `HeaderFilterRegex` limits header diagnostics to first-party dirs (`core|language-server|debugger|shared`), anchored to path boundaries so a vendored `external/.../core/` path can't be mistaken for `core/`.
- A handful of `clang-analyzer-*` checks are disabled with in-file justification because they fire *only* as false positives that location filters can't suppress (the static analyzer bypasses `HeaderFilterRegex`): `optin.core.EnumCastOutOfRange` (flag-enum casts like `ValueCategory`, plus MSVC `<filesystem>` internals), and `cplusplus.NewDeleteLeaks` + `optin.cplusplus.VirtualCall` (both only inside vendored `external/webview/webview.h`). `cppcoreguidelines-pro-bounds-avoid-unchecked-container-access` is also off — its only fix is `.at()`, which injects bounds checks into the VM dispatch hot path, and it is clang-tidy 19+ only (project pins 18).
- **Intentional empty catches** get `// NOLINT(bugprone-empty-catch)` per-site (~15 files) rather than disabling the check globally.
- **Test entry points must not let exceptions escape**: `run_test()` in `tests/test_framework.hpp` is `noexcept` and catches both `const std::exception&` and `...`; the `RUN`/`RUN_PARAMETERIZED`/`SUMMARY()` macro-built `main()` bodies rely on this to satisfy `bugprone-exception-escape` on every test executable.
- **Two `bugprone-*` patterns that compile clean but fail the gate** (both in `WarningsAsErrors`): `bugprone-implicit-widening-of-multiplication-result` — a size like `std::vector<T> v(64 * 1024)` multiplies as `int` *before* widening to `size_t`; do the arithmetic in `size_t` (a `constexpr std::size_t k_inflate_scratch_size = std::size_t{64} * 1024;` constant, as in `compression_module.cpp`). `bugprone-throwing-static-initialization` — a namespace-scope object whose constructor allocates / can throw (e.g. a `std::deque<std::string>`); move it into a function-local `static` accessor so init is lazy (first-use) and a throw surfaces at a call site, not during static init (as fixed in `terminal_testing.cpp`).
- **clang-analyzer mis-models a lambda-captured structured binding as a possibly-null pointer** (a `core.NullDereference` false positive): capturing `[name, flag]` from `auto& [name, flag] = entry` by reference into a lambda trips it. Bind plain locals (`const auto& name = entry.first;`) before the lambda so it captures ordinary variables (`statement_type_checker_control.cpp`).
- **CI runs clang-tidy on Linux only, sharded 4 ways (round-robin `NR % 4`), and excludes `*_win32.cpp`** — those files are absent from the Linux `compile_commands.json`, so clang-tidy would parse them with default flags and fail on their unconditional `<windows.h>`/`<io.h>` includes. The first full sweep surfaced 62 findings; the recurring real fixes beyond widening (above) were `bugprone-unchecked-optional-access` (bind the optional to a `const&` local before the deref the analyser can't pair with a prior `has_value()`) and `concurrency-mt-unsafe` on `getenv`/`setenv`/`strerror` (NOLINT — no portable mt-safe form; call sites are single-threaded init or the child side of a fork).

## CMake Style

*Canonical guide: [cmake.instructions.md](cmake.instructions.md). The notes below are a quick-reference summary.*

- Targets over variables — never set global `CMAKE_CXX_FLAGS`, use target-scoped properties.
- `PRIVATE`/`PUBLIC`/`INTERFACE` always on every `target_*` call.
- No `file(GLOB)` for sources — list explicitly so CMake re-runs on file changes.
- External dependencies are **vendored** in `external/` and built from source — no `FetchContent` or other configure-time downloads (keeps builds hermetic and offline). See [cmake.instructions.md](cmake.instructions.md) §7.2.
- Avoid legacy commands: no `add_definitions`, `include_directories`, `link_directories`.

## Git Conventions

*Canonical guide: [git.instructions.md](git.instructions.md). The notes below are a quick-reference summary.*

- Conventional commit prefixes: `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`.
- Branch naming: `category/short-description` with categories: `chore/`, `docs/`, `feature/`, `fix/`, `refactor/`, `test/`.
- Use `git switch` (not `checkout`). Merge with `--no-ff`. Force-push only on personal branches with `--force-with-lease`.

## Continuous Integration

*Canonical guide: [github-actions.instructions.md](github-actions.instructions.md). Workflows live in `.github/workflows/`.*

- Every first-party language has a lint/format CI gate in its own path-filtered workflow (so an unrelated change never triggers it): **C++** `ci.yml` (build matrix + a `Static Analysis` clang-tidy job + a `Formatting` clang-format `--dry-run --Werror` job + a warning/clang-tidy *sync* check + coverage/tsan/distro jobs), **Python** `ci-python.yml` (Ruff lint + format), **PowerShell** `ci-powershell.yml` (PSScriptAnalyzer), **CSS** `ci-css.yml` (Stylelint), **Markdown** `ci-markdown.yml` (markdownlint-cli2), **Shell** `ci-shell.yml` (ShellCheck), **CMake** `ci-cmake.yml` (cmakelint), **TS/JS/VS Code** `ci-vscode.yml` (ESLint + Prettier + unit tests), **Rust/Zed** `ci-zed.yml` (cargo fmt). Plus `codeql.yml`, `fuzz.yml`, `benchmark.yml`, `docs.yml`, the `release*.yml` set, and the shared `reusable-linux-build.yml`.
- Each linter's config is a pinned root file (`.clang-format`, `.clang-tidy`, `ruff.toml`, `PSScriptAnalyzerSettings.psd1`, `stylelint.config.mjs`, `.markdownlint-cli2.jsonc`) that is *also* on its workflow's path filter, so editing the config re-runs the gate. Tool versions are pinned (e.g. `ruff==0.15.17`, `cmakelint==1.4.3`, `stylelint@17.13.0`, `markdownlint-cli2@0.22.1`, PSScriptAnalyzer `1.25.0`).
- Touching any language's sources triggers its gate — run the matching local formatter before pushing (`clang-format`, `ruff format`, `prettier`, …). The C++ `Formatting` job fails on *any* clang-format diff, so format C++ with clang-format 18 first.
- **The C++ build matrix spans Windows (MSVC), Ubuntu (GCC 14; plus a non-PIE ASan+UBSan runtime-safety entry on GCC 13), macOS (Apple Clang), and — via `.github/workflows/linux-distros.json` and a native-ARM64 Raspberry Pi runner — Fedora, Kali, and Debian trixie.** Only the Ubuntu GCC 14 job runs the headless example sweep and installs WebKitGTK. These first non-Windows builds surfaced most of the portability defects in "C++ Pitfalls Discovered"; sanitizer jobs lower ASLR entropy (`vm.mmap_rnd_bits`) and link non-PIE, and ThreadSanitizer is best-effort/non-blocking.

## Build Environment

- **Full rebuild takes 5-8 minutes** with `cmake --build build --config Release --parallel`.
- **VS generator ZERO_CHECK race → prefer Ninja Multi-Config**: configuring/building with the default Visual Studio generator (`cmake --preset default`, "Visual Studio 18 2026") can intermittently fail under parallel MSBuild with a `generate.stamp` access-denied error in the ZERO_CHECK target. The root `CMakeLists.txt` now sets `CMAKE_SUPPRESS_REGENERATION ON` for the Visual Studio generator (dropping the in-build regeneration target — re-run `cmake --preset <name>` after editing any `CMakeLists.txt`), and `tests/CMakeLists.txt` replaced its `file(GLOB CONFIGURE_DEPENDS)` feature-test discovery (whose per-build glob-verification stamp amplified the storm into many parallel reconfigures) with explicit sorted lists, so the baseline VS build no longer races. Configuring with `-G "Ninja Multi-Config"` also avoids the race and still produces `build/Release/luma.exe` (matching `run_examples.py` defaults). Ninja needs the MSVC toolchain on PATH — import it via `vcvars64.bat`; since the sync/async shells here are ephemeral, re-import vcvars at the start of each self-contained build command (~3-5 s). Observed toolchain: VS 18 (2026, MSVC 19.51), cmake 4.3.2, clang 22, node 24, cargo 1.95, python 3.11.
- **Tests take ~180-200 seconds** with `ctest -C Release --timeout 60 --output-on-failure`.
- **5 primary CMake targets**: `luma_analysis` (front-end), `luma_core` (runtime), `luma_shared` (shared libs), `luma_lsp` (language server), `luma_dap` (debugger). The two tools also build a testable `*_lib` static library via `luma_add_tool_library`.
- **Fuzz targets require Clang; on Windows use the bundled clang-cl, not MSVC.** VS18's `Launch-VsDevShell.ps1 -VsInstallPath` does NOT establish a usable dev environment — import the toolchain via vcvars instead: `cmd /c "vcvars64.bat >nul 2>&1 && set" | ForEach-Object { if ($_ -match '^([^=]+)=(.*)$') { Set-Item "env:$($matches[1])" $matches[2] } }`, then prepend the bundled LLVM dir (`VC\Tools\Llvm\x64\bin`, provides `clang-cl`) and the Ninja dir to `PATH` before configuring with `-DLUMA_BUILD_FUZZ=ON`.
- **All executables land in the build *root*, not a per-target subdirectory.** The top-level `CMakeLists.txt` sets `CMAKE_RUNTIME_OUTPUT_DIRECTORY = ${CMAKE_BINARY_DIR}`, so fuzz binaries are at `build-fuzz/fuzz_parser.exe`, *not* the `build-fuzz/fuzz/...` path shown in `fuzz/README.md`, `fuzz/CMakeLists.txt`, and `build.instructions.md §7` — those documented paths are misleading on every platform.
- **Windows Defender can quarantine the Release-MSVC `dap_integration_test.exe` as a false positive** (`Trojan:Win32/Wacatac.C!ml`) the moment it is launched. When real-time protection is on and managed by group policy, you can't add an exclusion (no admin → `0x800704ec`). Workaround that survives: build the *same* target in **Debug** config (the different codegen is not flagged), copy that exe over `build\Release\dap_integration_test.exe`, and run it with the Debug CRT + UCRT dirs prepended to `PATH` (`...\VC\Redist\MSVC\<ver>\debug_nonredist\x64\Microsoft.VC<NNN>.DebugCRT` and `...\Windows Kits\10\bin\<ver>\x64\ucrt`). Any later **Release** rebuild re-quarantines it. The RelWithDebInfo clang-cl fuzz exes were *not* flagged — the trigger is specific to the Release MSVC codegen, not the test logic.

## C++ Pitfalls Discovered

- **`std::string_view` dangling after `std::move`**: `CompiledFunction`'s `param_name_index_` originally used `string_view` keys into `param_names`. After move, SSO-sized strings get new addresses → dangling views. Fix: use `std::string` keys. The same pitfall applies to any `string_view` into a `std::vector<std::string>` — reallocation invalidates them (e.g., constant pool string_view keys).
- **`std::once_flag` makes objects non-copyable/non-movable**: Attempted using `std::once_flag` for lazy `param_name_index` initialization, but it made `CompiledFunction` non-copyable/non-movable. Switched to eager initialization in `end_function()` and after deserialization.
- **`__builtin_unreachable()` / `__assume(false)` cannot be used in `constexpr` functions**: Use `assert(false)` instead for unreachable default cases in constexpr contexts.
- **MSVC `[[deprecated]]` on base class causes error on derived class use**: Use comment-based deprecation instead when the base class has active derived classes.
- **Atomic memory ordering matters for debug hooks**: `pause_requested` store was relaxed → changed to release ordering. Debug callback setters need release ordering; readers need acquire.
- **`notify_one()` outside the lock**: Channel notify should call `notify_one()` after releasing the lock to avoid waking a receiver that immediately blocks on the mutex.
- **Recursive-descent parser branches each need a depth guard**: every branch in `core/analysis/parser/` that recurses must take `auto guard = make_recursion_guard(current().location);` (defined in `parser.hpp`). It is easy to miss *conditional* recursion branches — the prefix-unary path in `parse_unary()`, the `spawn`/`await` postfix branches and `else if` chains in `parse_if_expression()`/`parse_if_statement()`, and `type_annotation_parser` — which fuzzing surfaces as stack overflows. **Lookahead helpers that recurse need their own explicit depth parameter**, because they run *before* the `make_recursion_guard`-tracked parse path: `Parser::skip_type_at(offset, depth)` (`parser_stmt.cpp`) bounds `depth` by `ResourceLimits::max_parse_depth` and bails (returning the current offset to route the construct to the bounded expression parser) instead of overflowing the native stack on a deeply nested type-like construct (e.g. thousands of `(`). This parser-side guard is distinct from the runtime `RecursionGuard` in `value.cpp` (which guards `to_string`/`equals`/`deep_copy`).
- **Windows headers leak `min`/`max` macros**: every translation unit that pulls in a Windows header must `#define NOMINMAX` *before* it (done in ~25 files) or `std::min`/`std::max` and `(std::numeric_limits<T>::max)()` fail to compile. Some portability defects only surface *off* Windows: a missing `<utility>`/`<cstdint>` include, or `extern char** environ;` (must be declared at file scope — not inside a function — for POSIX `process_module.cpp`), compiles under MSVC but breaks under Linux/clang. Build on both before claiming cross-platform.
- **MSVC `/W4` does not enforce the project's gcc/clang warning flags** (`cmake/LumaCompilerFlags.cmake`), and there is no global `/WX` on MSVC — so warnings never fail the MSVC build and must be grepped from logs. Three defect classes therefore compile clean under MSVC but break the Linux/clang(-cl) build: (1) **`-Wreorder-ctor`/`-Wreorder`** — the constructor member-initializer list must list members in *declaration* order; (2) **`-Wdouble-promotion`** — initialise doubles with `std::numeric_limits<double>::quiet_NaN()`, never the float `NAN` macro; (3) **LP64-vs-LLP64 literal ambiguity** — on LP64 targets (Linux/macOS) `int64_t` is `long`, so a `long long` literal like `42LL` becomes ambiguous across overloaded `Value` constructors, whereas MSVC's LLP64 (`int64_t` == `long long`) hides it — write `static_cast<std::int64_t>(42)`. The same LP64/LLP64 split also breaks `std::initializer_list<auto>` deduction — a braced range-`for` mixing `unsigned long long` literals with `std::uint64_t` values sees two distinct element types on LP64 (deduction fails on gcc/clang) but one type under LLP64; give the array an explicit `std::uint64_t` element type (`stdlib_test_random.cpp`).
- **clang-cl MSVC-EH catch-funclet codegen traps when a catch destroys a non-trivial temporary *and* throws**: under clang-cl on Windows a `catch` block that both destroys a non-trivial temporary and rethrows/throws emits an `int3` (TrapUnreachable) inside the funclet, surfacing only at runtime as `STATUS_BREAKPOINT` (exit `0x80000003` / `-2147483645`) — e.g. on try/catch-heavy fuzz seeds. Production MSVC `cl.exe` and Linux clang (Itanium EH, no funclets) are unaffected, so it never appears in those builds. Fix by keeping the non-trivial temporary and the throw **out of the funclet**: materialise exception payloads in a normal frame and re-raise *lexically*. The VM `run()` loop now splits `handle_exception` into `[[nodiscard]] bool` overloads (`vm.hpp`/`vm_helpers.cpp`) that build the `std::optional<Value>` payload outside the catch and return `false` when no Luma handler exists, so the caller re-raises with a bare `throw;` (a cross-function rethrow from the helper is *also* mishandled). `path_validator.hpp` moves its construct-and-throw into a `[[noreturn]]` out-of-line helper (`detail::throw_invalid_path`). This is a real codegen bug distinct from the `0xC0000409` `__fastfail` fuzz artifact noted under Testing.
- **Standard exception types need a direct `<stdexcept>` include — the clang-cl fuzz build catches missing transitive includes *on Windows***: any header that names `std::runtime_error`, `std::logic_error`, `std::invalid_argument`, `std::out_of_range`, `std::length_error`, etc. must `#include <stdexcept>` itself. MSVC supplies it transitively so the default preset stays green, but clang-cl's stricter transitive includes do not, breaking the fuzz build (`-DLUMA_BUILD_FUZZ=ON`). The useful corollary: the local **clang-cl fuzz build surfaces missing-transitive-include gaps without an off-Windows build**, so it is a cheaper check than the Linux/clang build the "Build on both before claiming cross-platform" note above implies — treat every header as include-what-you-use for the types it names. Fixed four headers in commit `8aeefa60` (`core/common/url_codec.hpp`, `core/runtime/stdlib/io/http_url_parser.hpp`, `core/runtime/vm/vm.hpp`, `debugger/source/dap_error_handler.hpp`).
- **Between `fork()` and `execvp()` the child may call only async-signal-safe functions — build `argv` *before* the fork**: `execute_command` (`platform_process_posix.cpp`) allocates the `argv` pointer vector before forking because `operator new`/`malloc` is not async-signal-safe. In the multithreaded interpreter (the thread pool runs `Process.run` from worker tasks) another thread can hold the allocator lock at the instant of the fork, which would deadlock the single-threaded child forever. The child inherits the pre-built `argv` at identical addresses via copy-on-write, so the pointers stay valid; it then does only `close`/`dup2`/`execvp`/`_exit`.
- **The first Linux/macOS/multi-distro CI builds surfaced a batch of latent stdlib divergences across the three C standard libraries** that MSVC-only building had hidden. (1) **`timegm`/`_mkgmtime` disagree at the calendar extremes** — glibc accepts the full range, BSD/macOS `timegm` rejects a year-0001 broken-down time (returns −1), Windows `_mkgmtime` rejects negative `time_t`; replaced with a platform-identical `safe_timegm` computed via Howard Hinnant's `days_from_civil` (`platform_time.hpp`), and `tm_to_unix` bounds the result to the documented year 0001–9999 range so `DateTime.add_months`/`add_years` overflow consistently. (2) **`Converter.from_binary`** — glibc's `strtoll` accepts a `0b` prefix (a C23 extension) that MSVC does not, so `parse_in_base` now rejects it explicitly (the standard `0x` hex prefix is left untouched). (3) **`Graph.has_cycle`** iterated an adjacency hash map whose root order differs across stdlibs, so the traversal-depth guard fired only on some platforms → iterate roots in deterministic sorted order (both directed and undirected branches). (4) **`Process.run`** on POSIX now reports an `execvp` failure to the parent via a close-on-exec self-pipe and returns a **negative** exit code (launch failure) to match the Windows `CreateProcessA` path, instead of the child's `_exit(127)` being reaped as a successful run. Feature tests/examples that spawn processes must also stay platform-neutral (`echo`/`exit` are `cmd.exe` built-ins on Windows but need a real binary/`sh -c` on POSIX).
- **POSIX stdio-protocol servers must `signal(SIGPIPE, SIG_IGN)` at `main()` start** (guarded by `!_WIN32`) — done in `luma_dap` and `luma_lsp`. `protocol::StdioTransport::write_message()` throws `ConnectionClosed` when a write to stdout fails (the intended "editor disconnected" path), but on POSIX the default `SIGPIPE` disposition kills the process by signal *before* `fwrite`/`fflush` can report the error, making that catch dead code. This was the root cause of an intermittent `dap_integration_test` stress-test failure on slower CI runners (a late write racing adapter teardown). Windows has no `SIGPIPE`.
- **AddressSanitizer defeats a `static_assert` that reaches a global's address**: ASan instruments every global-variable access, so a global table's address is no longer a core constant expression and GCC rejects e.g. `static_assert(opcode_metadata_matches())` with "is not a constant expression" under `-fsanitize=address`. Guard the compile-time form out (detect via `__SANITIZE_ADDRESS__` or Clang's `__has_feature(address_sanitizer)`) and rely on the equivalent runtime check, which still executes under ASan (`compiler_opcode_test.cpp`).
