# Learnings

Patterns, pitfalls, and non-obvious knowledge discovered during development sessions.

## Project Identity

- Luma is a statically typed, expression-oriented, interpreted programming language for beginners — "as easy as Python, as safe as Rust." Implemented in C++20 with a bytecode compiler and stack-based VM. Status: Alpha (0.5) — language, stdlib, and interpreter feature-complete; tooling under active development.
- The project spans ~150K+ lines across interpreter core, 41 stdlib module namespaces (30 always-available + 3 sandbox-aware + 8 OS-only), an LSP language server (`luma_lsp`), a DAP debugger (`luma_dap`), and editor extensions for VS Code and Zed.

## Architecture & Pipeline

- The interpreter follows a strict 8-phase pipeline: `Source → Lexer → Parser → Include Resolver → Type Checker → Linter → Compiler → VM`. Information flows in one direction only — phases are independent, composable, and testable.
- The pipeline is implemented via a composable pass framework in `core/analysis/pipeline/`. Builder pattern: `Pipeline::builder().add<Pass1>().add<Pass2>().build()`. Each pass declares `required_passes()` dependencies using `pass_name::` constants (compile-time `string_view` values). Advisory passes (linter) can `run_after_failure()`. The generic framework (`Pass`/`Pipeline`/`PipelineResult`) and the front-end pass wrappers (`TypeCheckerPass`/`LintPass`) depend only on the AST and diagnostics, so they compile into `luma_analysis`; `PipelineResult` derives success from `has_errors()` and stores diagnostics plus per-pass timing via `PassTiming` — it is deliberately artifact-agnostic. The back-end pass wrappers (`CompilerPass`/`OptimizerPass`/`VerifierPass`) live next to the code they wrap under `core/runtime/compiler/` and exchange the clean `CompileArtifact` (bytecode only, no diagnostics) through a caller-owned `std::optional<CompileArtifact>` slot, which `compile_program()` surfaces via `CompilationOutcome::artifact`. The `merge_diagnostics()` helper standardises diagnostic transfer across all passes.
- The lexer emits structured `Diagnostic` objects via a `DiagnosticCollector` reference instead of throwing `SyntaxError` exceptions. This enables graceful degradation and better error recovery during analysis.
- Centralised AST dispatch via `core/analysis/ast/ast_dispatch.hpp` using C++20 concepts (`ExpressionHandler`, `StatementHandler`, `DeclarationHandler`) and free-function templates. Maps node kinds to concrete types in a single switch — eliminates duplicated dispatch across passes.
- There is no intermediate representation (SSA, CFG). The compiler translates the type-checked AST directly to bytecode (105 opcodes across 25 categories).
- The VM is stack-based: value stack (max 65,536 entries), call frame stack (max 256 frames), plus a separate exception handler stack for try/catch/finally. VM internals are decomposed via composition: **VMStack** (stack + call frame storage with O(1) push/pop), **VMGlobalCache** (inline cache for global variable lookups exploiting `std::unordered_map` pointer stability), and a **function pointer dispatch table** (`vm_dispatch_table.cpp`) that maps opcodes to `void (VM::*)()` handler methods — replaces the previous switch-based dispatch for better branch prediction. A narrow **VMStackAPI** seam (`vm_stack_api.hpp`) abstracts the stack/frame/exception operations opcode handlers use, so extracted handlers can be unit-tested against a lightweight mock stack (see `vm_stack_api_test.cpp`); the VM is declared `final`, so the virtual calls devirtualize back to direct calls under optimisation — zero hot-path overhead. Debug-hook callback storage and its `callbacks_mutex` live in a first-class **VMDebugInterface** component (`vm_debug_interface.hpp`, `debug_` member, methods in `vm_debug.cpp`) that owns its own synchronisation — extracted from the former nested `DebugContext` struct as the first staged component of the VM god-class decomposition (`TODO(refactor/V1)`). Task/concurrency state (the `task_scope` LIFO stack, thread pool, task-id counter, and the thread-local current-scope pointer) likewise lives in a first-class **VMTaskManager** component (`vm_task_manager.hpp`, `task_manager_` member) — the second staged extraction. Note the dispatch table's `void (VM::*)()` member-pointer entries force every `op_*()` handler to stay a VM member, so these components own only STATE + helpers that thin `op_*()` members delegate to; the remaining VMCallDispatch/VMCore split is deferred because the call handlers are the execution-engine core (coupled to frames/base_depth_/PC beyond the seam).
- Memory management uses C++ smart pointers (`shared_ptr` for heap values, `unique_ptr` for ownership). No garbage collector — reference counting via `shared_ptr`.
- Closures use CLox-style capture chains for upvalues with value semantics (copy at closure-creation time, not open upvalues).
- Red-green trees (immutable green + ephemeral red wrappers) are used for incremental updates, primarily by the LSP. Green nodes store widths (not offsets) enabling reuse even when preceding text changes. Inspired by Roslyn (C# compiler) — unchanged subtrees shared between versions, O(log n) per-change re-parsing.
- `ScopeStack<T>` in `core/common/scope_stack.hpp` is a generic template for nested scope management with RAII Guard objects (push on construction, pop on destruction; constrained on `std::movable<T>`). Its sole user is `LinterTracker` (`core/analysis/linter/linter_tracker.hpp`), which stores `ScopeStack<ScopeData>` for flat variable-usage tracking. `NameResolver` (`ResolveScope`) and the type checker (`TypeScope`) deliberately do NOT use it — they need a `shared_ptr`-linked parent chain for cross-scope lookup and `frame_depth` accounting. See the §Component Usage rationale in `scope_stack.hpp` for why these scopes are not unified.

## Module Layout & Key Files

- `core/analysis/` = front-end (lexer, parser, types, linter, resolver, diagnostics, errors, source, ast, pipeline, prelude).
- `core/runtime/` = back-end (compiler, vm, stdlib, repl, concurrency, cli, include, interpreter).
- `core/common/` = shared utilities (overflow, resource_limits, utf8, scope_guard, scope_stack, export, result, path_utils, platform_utils, string_hash, format_number, escape, lru_cache, overloaded, narrow_int).
- `shared/` = cross-tool resources (json, protocol transport, stdlib catalog/symbols/return types).
- `shared/json/` = standalone JSON library (JsonValue variant + JsonBuilder/ArrayBuilder fluent APIs) used by both DAP and LSP. Deterministic serialization via `std::map`. Builder supports `set_if()` for conditional fields. Free `luma::json::parse()` function decouples parsing from the value type. Mutable `as_array()`/`as_object()` accessors for in-place mutation. Parser rejects duplicate object keys (throws `JsonParseError`). Serialisation is depth-bounded (`JsonValue::serialise(out, depth)`; nodes deeper than `max_json_depth` = 128 collapse to `null`) so a pathologically nested value cannot overflow the native stack — mirroring the parser's depth guard and the stdlib serializer.
- `shared/symbols/` = shared symbol metadata: **SymbolKind** (LSP-aligned enum: Namespace=3, Function=12, Variable=13, Struct=23; Choice→Enum(10), Record→Struct(23) in LSP mapping; used directly by the language server via `to_lsp_symbol_kind()`), plus qualified-name helpers in `qualified_name.hpp`. Prefer the **non-allocating free functions** for splitting: `make_qualified(ns, member)` builds a dotted string; `is_qualified_name(sv)` tests for a dot (the canonical predicate — the LSP re-exports it as `luma::lsp::util::is_qualified_name`, don't re-fork it); `qualified_module(sv)` returns the head before the FIRST dot; `qualified_member(sv)` returns the leaf after the LAST dot; `split_module(sv)` returns `optional<pair<sv,sv>>` split at the FIRST dot (nullopt when unqualified). The **QualifiedName** struct is now parse-only: `QualifiedName::parse()` splits at the LAST dot into owned `{namespace_part, member_part}` std::strings — use it only where both halves are needed as `std::string` (e.g. `lsp_server_code_actions.cpp`); its formatting/ordering/hashing members were removed as unused. The type checker's own `symbol_registry.hpp` uses a separate **SuggestionCategory** enum (Variable, Function, Type, Module) for "did you mean?" suggestions — intentionally distinct from the LSP-aligned SymbolKind.
- `shared/protocol/` = transport layer utilities (Content-Length framed JSON over stdio) shared by language server and debugger.
- The type checker is split across multiple files for maintainability: `type_checker.cpp` (core), `type_info.cpp` (TypeInfo methods), `type_scope.cpp` (TypeScope methods), `type_checker_decl.cpp`, `type_checker_resolve.cpp`, `type_checker_fwd.hpp`, `expression_type_checker.cpp` with sub-files `_access`, `_binary`, `_calls`, `_literals`, `_misc`, `statement_type_checker.cpp` with sub-files `_control`, `_declarations`, `_misc`, `stdlib_type_handler.cpp`, `generic_resolver.cpp`, and `symbol_exporter.cpp`. Further decomposed into sub-checker classes: **ExpressionTypeChecker** (expression inference with type refinement stack for boolean narrowing), **StatementTypeChecker** (statement validation with definite-return analysis and match exhaustiveness), **StdlibTypeHandler** (stdlib metadata from catalog with return-type refinement), **GenericResolver** (type parameter binding with push/pop lifecycle), and **SymbolExporter** (builds SymbolTable from stdlib signatures and user definitions).
- The compiler is split into core files: `compiler.cpp` (core), `expression_compiler.cpp`, `statement_compiler.cpp`, `optimizer.cpp` with sub-files `_constant_fold`, `_control_flow`, `_dead_code`, `_peephole`, and `optimizer_internal.hpp`. Further decomposed into: **PatternCompiler** (all pattern-matching compilation with `PatternTestArgs`/`GuardResult` structs), **VariableResolver** (3-level local→upvalue→global resolution with `VarSlot` struct), **ConstFolder** (compile-time constant folding for binary/unary ops via `IConstantEmitter` narrow interface). All helpers access the compiler through the **ICompilationBackend** pure virtual interface (implemented by **CompilerAccess**). Type definitions are extracted into `compilation_context.hpp` (CompilerScope, CompilationContext, Local) and `compiled_function.hpp` (CompiledFunction, FunctionDebugInfo). Supporting modules: `chunk.hpp/.cpp` (bytecode container), **ConstantPool** (extracted deduplication with `std::bit_cast` for doubles), `opcode.hpp` (105 opcodes), `emitter.hpp` (bytecode emitter helpers), `bytecode_serializer.hpp/.cpp` (persistent `.lumc` binary format), `compilation_cache.hpp/.cpp` (in-memory LRU cache), `verifier.hpp/.cpp` (structural bytecode verification).
- The VM is split into `vm.cpp` (dispatch loop), `vm_helpers.cpp` (non-inlined helper methods extracted to reduce file size), plus dispatch headers: `vm_dispatch_arithmetic.cpp`, `vm_dispatch_collections.cpp`, `vm_dispatch_control_flow.cpp`, `vm_dispatch_concurrency.cpp`, `vm_dispatch_types.cpp`, `vm_dispatch_table.cpp` (function pointer table). Additional modules: `vm_stack.hpp` (stack + frame storage), `vm_global_cache.hpp` (inline global lookup cache), `vm_introspection.hpp/.cpp` (high-level state access for debuggers — stack trace, locals, upvalues, set_local/set_upvalue), `vm_types.hpp` (`TypeMatcher` class for runtime IS_TYPE / match dispatch — simple, tuple, parameterized, choice/record patterns). Opcode handlers follow two naming conventions: short, simple handlers are defined inline as `op_*` in `vm_dispatch_table.cpp`, while complex handlers are `handle_*` methods in the topical `vm_dispatch_*.cpp` files.
- The runtime `Environment` delegates two concerns to focused policies extracted behind its facade: **SandboxPolicy** (`sandbox_policy.hpp`, owns the `--box` blocked-module prefix set and the access-denied decision) and **LazyLoader** (`lazy_loader.hpp`, holds the on-demand module-registration callback). The lexer's source buffer and scan position (byte offset, line, code-point column) live in **LexerCursor** (`lexer_cursor.hpp`), which the `Lexer` composes and delegates its character-stream primitives to.
- Stdlib has 58+ files: 41 module namespaces plus infrastructure (`native_function.hpp`, `function_builder.hpp`, `container_ops.hpp`, `container_module_builder.hpp`, `path_validator.hpp`, `error_messages.hpp`, `stdlib_registry.hpp`, `lazy_registry.cpp/.hpp`, `platform_socket.hpp`, `platform_time.hpp`, `terminal_input.hpp` + platform-specific `terminal_input_posix.cpp`/`terminal_input_win32.cpp`) and shared helpers (`numeric_converters.hpp`, `numeric_helpers.hpp`, `value_compare.hpp`, `xml_module_internal.hpp`, `file_helpers.hpp`, `escape_helpers.hpp`, `hash_module_internal.hpp`, `http_module_request.hpp`, `http_module_connection.hpp`).
- Stdlib module registration uses a fluent DSL: `ModuleBuilder{"Array", env}.func("length", 1).extract_body(expect_array, impl)`. `FuncBuilder<Self>` separates type extraction (ExtractFn) from implementation (BodyFn) for clearer error contexts.

## Build System

*Canonical guides: [build.instructions.md](build.instructions.md) and [cmake.instructions.md](cmake.instructions.md). The notes below are a quick-reference summary.*

- CMake 3.21+ with C++20 required, no extensions. The top-level `VERSION` file is the single source of truth for the project version (read by `CMakeLists.txt` into `project()`, `common/version.hpp`, and CPack); never hardcode the version number elsewhere.
- Key build options: `LUMA_BUILD_TESTS` (ON), `LUMA_BUILD_FUZZ` (OFF), `LUMA_FEATURE_SANITIZERS` (OFF), `LUMA_FEATURE_COVERAGE` (OFF), `LUMA_FEATURE_TLS` (ON), `LUMA_FEATURE_WEBVIEW` (ON), `LUMA_FEATURE_LTO` (OFF).
- The two `LUMA_HAS_*` macro-scopes are gated by `LUMA_FEATURE_TLS` → `LUMA_HAS_TLS` and `LUMA_FEATURE_WEBVIEW` (+ backend detection) → `LUMA_HAS_WEBVIEW`. The CI `feature-flags` job builds with each OFF so the stub paths stay compiled and tested; locally, build with `-DLUMA_FEATURE_TLS=OFF` / `-DLUMA_FEATURE_WEBVIEW=OFF` to exercise them.
- 13 user-facing configure presets: `default`, `debug`, `msvc`, `xcode`, `sanitize`, `relwithdebinfo`, `coverage`, `lto`, `ninja`, `arm64-cross`, `release-no-tests`, `windows-arm64`, `macos-universal` (plus hidden `_base*` presets). See [build.instructions.md](build.instructions.md) §3 for the full preset/purpose table.
- Quick start: `cmake --preset default && cmake --build --preset default && ctest --preset default`.
- Windows (MSVC): always use `--config Release/Debug` with multi-config generators.
- Compiler security hardening is applied to all targets: MSVC gets `/W4 /permissive-`, SDL checks, CFG, DEP, ASLR; GCC/Clang get `-Wall -Wextra -Wpedantic`, stack protector, PIE, RELRO, non-exec stack.
- External dependencies are vendored in `external/`: mbedtls (HTTPS), miniz (compression), webview (GUI).
- **Toolchain minimum is GCC 13+ / Clang 15+ / MSVC 2022+ because Luma uses the C++20 library features `std::format` and `std::chrono::clock_cast`**, which libstdc++ ships only from GCC 13. Debian bookworm and the bookworm-based Raspberry Pi OS default to GCC 12, so `#include <format>` fails with "No such file or directory"; CI therefore builds the Debian matrix entry and the ARM64 RPi proxy on Debian **trixie** (GCC 14). Apple libc++ lacks `clock_cast` entirely, so the file-time conversion is feature-tested with a rebasing fallback in `core/common/file_time.hpp`.
- **`CMAKE_POSITION_INDEPENDENT_CODE` is set `ON` globally** (top-level `CMakeLists.txt`) so every static library — first-party and vendored — compiles `-fPIC`. The executables link `-pie` for ASLR hardening; Ubuntu's GCC defaults to PIE so partial `-fPIE` on executables alone happened to work, but Fedora's does not (`relocation R_X86_64_32S against '.rodata' can not be used when making a PIE object`). No-op on Windows/macOS.
- **The Linux GraphicalUi backend links WebKitGTK via raw pkg-config result variables, not a `pkg_check_modules` IMPORTED_TARGET** (`cmake/LumaWebView.cmake`): an `IMPORTED_TARGET` (even with `GLOBAL`) is directory-scoped and unresolvable at generate time for `luma_core`'s cross-directory PUBLIC consumers (the `luma` executable, tests). Use `WEBKITGTK_LINK_LIBRARIES` (full paths, no scope) for the PUBLIC link and attach `WEBKITGTK_INCLUDE_DIRS`/`WEBKITGTK_CFLAGS_OTHER` to the `luma_webview` INTERFACE target.

## Type System

*Canonical guide: [luma.instructions.md](luma.instructions.md). The notes below are a quick-reference summary.*

- Primitives: `boolean`, `integer` (64-bit signed), `number` (IEEE-754 64-bit float), `string` (UTF-8), `none`.
- **Critical distinction**: `integer` is for indices, array subscripts, loop counters, range bounds only. `number` is for counts, measurements, scores, IDs, and all other numeric values. Getting this wrong causes type errors.
- Type promotion: `integer` + `number` → `number`; `integer` widens to `number` implicitly.
- Collections: `array<T>`, `dictionary<V>` (string keys), `set<T>`, `hashset<T>`, `queue<T>`, `stack<T>`, `linkedlist<T>`, `binarytree<T>`, `graph<T>`.
- Wrappers: `optional<T>`, `result<T>` (with optional second type param for error type), `reference<T>`, `channel<T>`, `task<T>`.
- Advanced: tuples (2-4 elements), choice types (ADTs with generics), records (with optional `private` fields), interfaces (structural satisfaction), type aliases (fully transparent).
- Match exhaustiveness is enforced: booleans need both cases, choice types need all variants, results need success/failure. Others require `else`.

## Error Handling

- **Domain failures** → `result<T>` with `match`, `??`, `?` (propagation), `!>` (error pipe). This is the primary mechanism.
- **Programmer errors** → runtime errors + `try`/`catch`/`finally`. Division by zero, out-of-bounds, `assert` failure, `Result.unwrap` on failure, `trusted_downcast` mismatch, max recursion.
- **Compile-time errors** → `SyntaxError`, `TypeError` — cannot be caught at runtime.
- Anti-patterns: using `try`/`catch` for expected failures (use `result<T>`), naked `Result.unwrap`, returning sentinel values, silently discarding results, wrapping infallible functions in `result<T>`.
- `downcast<T>(expr)` returns `result<T>` (safe). `trusted_downcast<T>(expr)` throws runtime error on mismatch (unsafe).
- `catch(err)` binding is an immutable `string` containing the error message.

## Luma Language Conventions

*Canonical guide: [luma.instructions.md](luma.instructions.md). The notes below are a quick-reference summary.*

- Every program requires exactly one `@main`-annotated, parameter-less function. REPL and test mode don't require it.
- Variables are immutable by default; use `mutable` keyword for mutability.
- No semicolons required (treated as whitespace). Comments start with `#`.
- Braces always required, even for single-statement bodies.
- Function declarations put the **return type before the name** (always required): `function <return-type> <name>(<params>) { … }` — e.g. `function void main()`, `function boolean is_ready()`. Writing the return type after the parameters as `function f() -> T` is a parse error (`missing return type for function`). The `->` arrow *is* valid Luma, but only in **lambdas** (`(T x) -> expr`) and **function-type annotations** (`function(T) -> R`) — never a declaration's return type. Variables are declared **type-first**: `<type> name = value` or `mutable <type> name = value` (e.g. `number x = 5`); `let`/`var` are *not* keywords (the lexer warns `'let' is not a Luma keyword`). These bite whenever a tool *synthesizes* Luma source (debugger / LSP / REPL / codegen).
- String interpolation: `"value is ${expr}"`. Triple-quoted strings auto-dedent (common leading whitespace stripped).
- Pipe operator: `value |> Module.function()` — left becomes first argument.
- All collection operations return new collections (immutable by default). Build in single pass with `Array.map`/`Array.filter`/`Array.reduce` instead of incremental mutation.
- Naming: `snake_case` for variables/functions/files, `PascalCase` for records/choices/interfaces/namespaces, question form for booleans (`is_valid`, `has_children`).

## Concurrency

- `spawn` + `await` for independent tasks. `task_scope` for structured lifetime management (all children complete before parent exits — no orphaned tasks).
- Channels for inter-task communication with deep-copy semantics.
- Cooperative cancellation: `Task.cancel(t)`, `Task.is_cancelled(t)`.
- Each task gets a lightweight per-thread VM instance.
- Type checker warns on bare `spawn` outside `task_scope`.

## Testing

*Canonical guide: [testing.instructions.md](testing.instructions.md). The notes below are a quick-reference summary.*

- Two layers: C++ unit tests (custom framework in `tests/test_framework.hpp`, namespace `luma::test`) and Luma feature tests (`@test` annotations + `assert()`).
- C++ tests use `RUN(test_name)` to register/run tests and `return SUMMARY()` from `main()`.
- Assertion macros: `ASSERT_EQ`, `ASSERT_NE`, `ASSERT_TRUE`, `ASSERT_FALSE`, `ASSERT_THROWS`, `ASSERT_LT`, `ASSERT_LE`, `ASSERT_GT`, `ASSERT_GE`, `ASSERT_NEAR(a, b, epsilon)`.
- Snapshot testing: `ASSERT_SNAPSHOT(name, actual, __FILE__)` compares output against `.expected` files in `snapshots/` directory. Set `UPDATE_SNAPSHOTS=1` to create/update baselines.
- Test fixtures: derive from `TestFixture`, override `set_up()`/`tear_down()`, use `TEST_F(FixtureClass, test_name)` macro.
- Benchmarks: `BENCHMARK(name, iterations) { ... }` macro with warmup phase and ns/iter reporting.
- RAII helpers: `StdinRedirect` for redirecting `std::cin` in tests.
- Enum values are auto-formatted via `to_printable()` (casts to underlying integer type for assertion messages).
- Luma feature tests live in `tests/features/`, organised into `language/` and `stdlib/` subdirectories. Run via `luma --test file.luma`. **The ctest wrapper adds `--strict`, which promotes lint warnings to errors, but a bare `luma --test file.luma` does not** — so a feature test can pass locally yet fail its `luma_<stem>` ctest. Always validate with `luma --strict --test file.luma` to match CI. Two warnings bite typed-stdlib feature tests specifically: **W0009** (floating-point `==`/`!=`) fires on any `number == <float-literal>` — compare with `Math.approximately_equal(a, b, 0.001)` instead; **W0001** (unused variable) fires on unused pattern/match-arm bindings — prefix them with `_` (e.g. `failure(_e)`, `case Ns.T.Element(_tag, _attrs, kids)`).
- **Headless interactive-input test APIs** make display/TTY-dependent code testable in CI. `Terminal.test_*` (`terminal_testing.cpp`): `test_start(keys)`, `test_feed(keys)`, `test_output()→string`, `test_remaining()→integer`, `test_stop()→string` — keys are names (`"a"`, `"enter"`, `"ctrl+c"`, `"shift+tab"`) or mouse strings (`"mouse:left_press:5:10"`). `GraphicalUi.test_*` mirrors this for GUIs (see the GraphicalUi section). Prefer driving these from `@test` blocks so an example proves behaviour, not just "doesn't crash".
- **Example runner**: `python scripts/run_examples.py` executes every program in `examples/` headlessly — GUI via `LUMA_GUI_HEADLESS=1` (asserts an "initial render OK" marker), Terminal via scripted keys, Console via scripted stdin — and additionally runs any `@test` blocks (without `--strict`, so lenient on W0010 but still clean). An example with no `@test` block only proves it doesn't crash. `run_examples.py` discovers every `.luma` under `examples/` via `rglob`; current suite ≈ 117 examples (≈ 116 pass + 1 skip — `multi_file_utils.luma`, an include-only helper with no `@main`).
- 30 fuzz targets in `fuzz/` (authoritative list in `fuzz/CMakeLists.txt`) spanning the analysis/runtime pipeline (lexer → VM), stdlib parsers (JSON, CSV, XML, regex, compression, …), include resolver, protocol transport, and the bytecode deserializer (with round-trip oracles), using LibFuzzer with a shared harness and seed corpus.
- **Fuzzing is authoritative on Linux/clang only.** On Windows a clang-cl fuzz exe that exits `0xC0000409` (STATUS_STACK_BUFFER_OVERRUN — a `/GS` `__fastfail`, distinct from a *real* stack overflow's `0xC00000FD`) with **no crash artifact written** is a clang-cl SanitizerCoverage + MSVC hardening (`/GS /sdl /guard:cf`) codegen artifact, **not** a Luma bug — libFuzzer cannot intercept `__fastfail`. On Windows, validate that seeds load with `-runs=0`; run real campaigns on Linux/clang (or a Linux container) as CI does. The `fuzz_protocol` target has a separate, documented trap caveat (`fuzz/README.md`).
- All tests must pass before committing.

## Language Server (LSP)

- Standalone binary (`luma_lsp`) communicating via JSON-RPC 2.0 over stdio.
- Reuses interpreter pipeline (lexer, parser, type checker) — no runtime/VM.
- 27 LSP features including diagnostics, hover, completions, signature help, go-to-definition, references, rename, semantic tokens, code actions, code lens, formatting, folding, inlay hints, call/type hierarchy, linked editing.
- Incremental document sync (advertises `TextDocumentSyncKind.Incremental`): ranged edits are applied in place, with full-text replacement as a fallback when a change omits a range. Re-analysis is still full per change, with incremental red-green tree updates for efficiency.
- Source split across 50+ files in `language-server/source/`.
- **AnalysisService** (`lsp_analysis_service_impl.hpp`): Concrete implementation owning the full analysis pipeline (lex → parse → include → symbol collection → type-check → lint). Cancellation-aware with configurable deadlines. Accepts callbacks for logging and notifications — decoupled from server concerns.
- **AnalysisResult** (`lsp_analysis_result.hpp`): Cached analysis output with rich indexing — token index (sorted by line/col), function body ranges (binary searchable), identifier index (reverse lookup), scoped locals (block-level scope tracking), call graph (caller→callee sets). Function body ranges stored twice (map + sorted vector) for O(log n) enclosing-function lookup.
- **WorkspaceManager** (`lsp_workspace_manager.hpp`): Owns workspace roots, persisted index, and project configuration. Manages indexing state.
- **ConfigurationManager** (`lsp_configuration_manager.hpp`): Owns LSP settings and client capabilities. Isolated from server logic.
- **WorkspaceIndexer** (`lsp_workspace_indexer.hpp`): Recursive workspace file discovery with max file limit (500). Stateless scanner.
- **PersistedIndex** (`lsp_persisted_index.hpp`): Binary-serialized workspace symbol cache for fast incremental startup. Content hash validation for staleness detection.
- **DiagnosticBuilder** (`lsp_diagnostic_builder.hpp`): Converts internal diagnostics to LSP format with UTF-16 code unit conversion and documentation URL generation.
- **IncludeProcessor** (`lsp_include_processor.hpp`): Handles the include phase with batch pre-reading (each file read from disk at most once).
- **SymbolResolver** (`lsp_symbol_resolver.hpp`): Unified symbol resolution for hover, go-to-definition, rename, references, completion. Scope-aware lookup (enclosing function locals → globals), binary search for enclosing function, cross-file resolution.
- **TokenUtils** (`lsp_token_utils.hpp`): Coordinate conversion between Luma's 1-based source locations and LSP's 0-based Position/Range. Namespace-qualified name extraction by looking backward for "Namespace.identifier" pattern.
- **LSP Types** (`lsp_types.hpp`): Protocol types (Position, Range, Location, Diagnostic) with LSP-aligned constants. Error codes are strings (e.g., "E0006"). Position is 0-based per LSP spec.
- **Columns are codepoint-based, never byte-based**: Luma source columns and LSP `character` positions both count Unicode codepoints, so a lexeme's display width is its codepoint length — *never* `lexeme.size()`/`name.size()` (bytes). Using byte length for any lexeme containing multi-byte UTF-8 (string literals, non-ASCII identifiers) yields wrong hover/definition/rename ranges and edit corruption. Use `lexeme_column_width()` (`lsp_token_utils.hpp`), which delegates to the shared `luma::utf8_codepoint_count()` (`core/common/utf8.hpp`); it is the correct tool at every column computation across the LSP (~18 call sites in 9 files). Diagnostic `SourceLocation` columns are codepoint indices too, so mapping a Luma diagnostic to an LSP range goes codepoint-col → byte-offset (`codepoint_col_to_byte_offset`) → UTF-16 (`byte_offset_to_utf16_column`) in `lsp_diagnostic_builder.cpp`; it previously treated the column as a byte offset, corrupting ranges on any line with multi-byte UTF-8 before the diagnostic, and `word_end_column` similarly walks codepoints and counts bytes ≥ 0x80 as identifier characters.
- **Stored symbol definition `location`s are anchored at the leading declaration *keyword* (`function`/`record`/`choice`/`interface`/type alias), not the name.** Building an LSP range straight from `location` + `name.size()` (or `lexeme_column_width(name)`) covered the keyword/return-type region, and for `includeDeclaration=false` references the declaration-site exclusion *never* matched. Use `find_declaration_name_range(tokens, decl_loc, name)` (`lsp_token_utils.hpp`), which scans forward from the keyword location for the actual name token (reducing a qualified `Ns.func` key to its bare member via `qualified_member`) and returns a codepoint-safe range. Applied across document symbols, call/type hierarchy, go-to-type-definition/implementation, code lens, and the references declaration exclusion (`lsp_identifier_collector.cpp`).
- **Rename/references occurrence filtering must reject same-lexeme tokens that bind to a *different* symbol** (`collect_scoped_occurrences`, `lsp_identifier_collector.cpp`): for an *unqualified* target, an occurrence preceded by `Identifier Dot` (a receiver, e.g. the `value` in `point.value`) is a member/field access and is skipped; for a *global* target, occurrences shadowed by a local or parameter in their own function scope (via `ScopeStack::find_symbol` returning a `Block`/`Function` origin) are skipped. Otherwise renaming a global rewrites unrelated fields and shadowing locals.
- **Completion is suppressed inside string literals and comments** (`classify_cursor_context` in `lsp_server_completion.cpp`, reusing the shared `lexical::LineContext` forward scanner from `lsp_lexical_context.hpp`), except `include "..."` path completion which legitimately lives in a string; a `${...}` interpolation counts as code so completion still fires there. After a *foreground* debounced re-analysis commits, the server sends a param-less global `workspace/semanticTokens/refresh` so the client re-pulls fresh tokens and drops highlighting held from the debounce window (foreground-only, to avoid spamming during background indexing). Rename validates the new name with the shared `util::is_valid_identifier` (`lsp_string_utils.hpp`), which accepts UTF-8 multibyte bytes (≥ 0x80) so Unicode identifiers (`café`, `π`, `名前`) are legal, mirroring the lexer.
- **Path-containment checks compare by path *components*, not string prefix**: `collect_include_completions` (`lsp_completion_strategy.cpp`) rejects a search dir that escapes the base via `canonical_search.lexically_relative(canonical_base)`, testing whether the relative path is empty or its first component is `..`. A raw `starts_with(base)` string test wrongly admits a sibling that merely shares a character prefix (base `/p/proj` vs `/p/proj-secret`).

## Debugger (DAP)

- Standalone binary (`luma_dap`) implementing Debug Adapter Protocol over Content-Length framed JSON via stdio.
- Two-thread design: protocol I/O thread + VM execution thread. Shared state is mutex-protected.
- Supports breakpoints (line, conditional, hit count), stepping (over, into, out, reverse), stack trace, scope/variable inspection, expression evaluation, concurrent debugging (task → DAP thread mapping).
- Also supports TCP transport for remote debugging.
- Non-goals (`Luma_Debugger.md` §3): memory/performance profiling, and language-server integration. Hot-reload source watching *is* implemented (see DebugExecutionEngine below).
- **DebugSession** (`debug_session.hpp`): Top-level orchestrator delegating to extracted focused managers. SessionState uses atomic enum (`Idle`, `Running`, `Terminated`) instead of separate booleans — eliminates race windows. Documented lock ordering: (1) thread_states_mutex_→ (2) ThreadState::mutex → (3) config_mutex_→ leaf: exception_mutex_.
- **DebugExecutionEngine** (`debug_execution_engine.hpp`): Owns the execution lifecycle — program launch, VM creation, hook installation, execution control (continue, step, pause), and exception handling coordination. Split into `debug_execution_control.cpp` (control logic), `debug_execution_hooks.cpp` (VM hook installation), and `debug_execution_lifecycle.cpp` (lifecycle management). Configuration phase synchronization (waits for configurationDone). Integrates hot-reload source watcher.
- **ThreadStateManager** (`thread_state_manager.hpp`): Per-thread debugging state registry with RAII guards. Thread registration, lookup, paused-thread counter with condition variable signaling, force-unpause for terminate.
- **BreakpointManager** (`breakpoint_manager.hpp`): Single-class consolidation of all breakpoint logic (line, function, data, exception filters) with one mutex. Two phases: `set_breakpoints()` creates pending entries, `resolve_pending_breakpoints()` called after compilation. Split into focused source files (`line_breakpoint_manager.cpp`, `function_breakpoint_manager.cpp`, `data_breakpoint_manager.cpp`). Atomic flags for exception filter state (lock-free).
- **CompiledBreakpoint** (`compiled_breakpoint.hpp`): Compiles and validates breakpoint condition expressions and log-message templates to bytecode at creation time, surfacing syntax errors early and caching the compiled artefacts. It does **not** evaluate at runtime — condition evaluation runs in `DebugExecutionEngine` against the live paused frame (so it can resolve frame locals, which a standalone compiled function cannot).
- **VariableInspector** (`variable_inspector.hpp`): Owns variable reference registry using **generational entries** — `GenerationalEntry<T>` pairs value + generation counter. `invalidate_refs()` increments generation for O(1) invalidation instead of clearing maps. Scope types: Local(1), Global(2), Closure(3). Max expansion depth: 32. Supports custom visualizer rules.
- **ExpressionEvaluator** (`expression_evaluator.hpp`): Evaluates expressions in paused VM context with strategy chain: (1) direct local lookup → (2) closure upvalue lookup → (3) global env lookup → (4) scratch-VM compilation & execution (cached) — compiles `function boolean __bp_eval__() { return <expr> }` via `compile_expression_direct` (type checker bypassed; the return type is cosmetic) and runs it through `VM::execute_function`, which **returns** the expression's `Value`. Decoupled from VariableInspector via `RefAllocator` callback. Configurable timeout (default 5s).
- **ExpressionCompiler** (`expression_compiler.hpp`): Shared compilation utility (Lexer → Parser → Compiler) used by expression evaluator, compiled breakpoints, and logpoints.
- **VmHookRegistry** (`vm_hook_registry.hpp`): Installs debug hooks on VM instances and connects them back to the session.
- **TimeTravel** (`time_travel.hpp`): Reverse debugging via a ring buffer of VM state snapshots captured at periodic intervals. `ReplayEngine::restore_snapshot` restores a recorded snapshot's value stack for inspection on step-back; frame/IP restoration and forward replay are out of scope (the VM exposes no frame/IP restoration APIs).
- **CustomVisualizer** (`custom_visualizer.hpp`): Loads visualizer rules from JSON config files, matches against type names via pre-compiled regex, provides custom display/summary templates.
- **DapSessionTypes** (`dap_session_types.hpp`): Shared vocabulary types (SessionState enum, ThreadState struct) extracted to eliminate circular dependencies.
- **DAP Helpers** (`dap_helpers.hpp`): Type-safe JSON field extraction with defaults, `narrow_int()` narrowing with overflow checking (from `core/common/narrow_int.hpp`), `format_error_message()` for consistent error formatting, specialized parsers for launch config and breakpoint requests. Thread ID defaults to 1 (main thread).
- **Invoke session-terminating callbacks *after* releasing the transport send mutex**: `DapProtocolHandler::send_response`/`send_event` hold `send_mutex_` while writing; on a broken pipe they must set a flag and call `signal_disconnect()` only *after* the lock scope ends. The disconnect callback terminates the session and joins the VM execution thread, which may itself be blocked on `send_mutex_` inside `send_event()` — signalling while holding the lock self-deadlocks.
- **Evaluate synthesized Luma by returning a value, not by scraping `print`**: `ExpressionEvaluator::evaluate_on_scratch_vm` compiles `function boolean __bp_eval__() { return <expr> }` via `compile_expression_direct` and reads the `Value` that `VM::execute_function` returns. The previous design wrapped the expression as `@main function void main() { let __val = … print(__val) }` and scraped a stubbed `print()` argument; built on non-existent syntax (the `let __val` binding, plus an earlier `function …() -> <expr>` declaration form — see Luma Language Conventions), it failed to parse / threw a non-`std::exception` out of the scratch VM (caught only by `catch(...)` under `/EHsc`) for any compound expression like `1 + 1`. It survived because **no test ever compiled a representative wrapper** — a consistency check's `luma --check` (exit 3) finally caught it. Any path that synthesizes source to feed back through the compiler needs a test that compiles **and runs** one real example (`dap_integration_test.cpp::test_evaluate_compound_expression`, `dap_test_compiled_cache.cpp`).
- **A conditional breakpoint counts as *hit* only when its condition holds** (DAP semantics), so `BreakpointManager::check_breakpoint` runs in four phases: (1) locate the match *without* recording a hit (`line_mgr_`/`func_mgr_.find_matching_breakpoint(file_id, line, record_hit=false)`), (2) evaluate the condition against the live paused frame **outside** the leaf `ctx_.mutex`, (3) record the qualifying hit only when the condition held (`record_hit=true`) and read back the updated count, (4) gate the `hitCondition` on that condition-true count. Recording the hit before checking the condition would make `hitCondition` count condition-false passes. The breakpoint can be removed by a concurrent `setBreakpoints` between phases 1 and 3 — a phase-3 miss means *don't break*.
- **DAP `setVariable` coerces the edit to the target's *existing* type** rather than inferring one from the input text: `VariableInspector::set_variable` reads the current value (`read_scope_value`) and runs `parse_value_typed(str, current)`, which parses to the current value's type or returns `nullopt` to reject a type-changing edit with a DAP error. String targets always succeed (surrounding quotes optionally stripped); complex/null targets are rejected because they can't be reconstructed from a plain string. Prevents a `boolean`/`integer` slot being silently overwritten with a different primitive.
- **The scratch-VM expression evaluator enforces its timeout *during* execution, not just after**: `evaluate_on_scratch_vm` installs a per-line debug hook that aborts once the deadline passes (returning `true` arms a pause whose callback returns `false` to terminate); it previously only *measured* elapsed time afterwards, so a non-terminating watch/condition/logpoint hung the calling DAP thread forever, freezing request handling or the debuggee. The `std::atomic<bool> timed_out` flag is declared *before* the scratch `VM` so it outlives the hook that captures it by reference (locals destroy in reverse declaration order). The VM's global runaway-loop guard (`ResourceLimits::max_while_iterations`) can trip *before* the cooperative deadline on a fast host; both mean non-termination, so the runaway `RuntimeError` — matched via the shared `vm_errors::loop_exceeded_max_iterations(...)` generator to stay in step with the VM — is reported identically to a deadline abort. The scratch env also copies the program's top-level globals (user functions/records/choices/namespaces), skipping names already registered (stdlib) and letting copied locals shadow globals, so compound expressions can reference them.
- **A spawned task's exit hook must fire while its `VM` is still alive**: in `create_spawn_callable` (`vm_dispatch_concurrency.cpp`) the `TaskExitGuard` is declared *after* `task_vm` so it destructs *first* (reverse declaration order) — the hook nulls this task's `ThreadState::vm` before `task_vm` is destroyed, closing a use-after-free window where a concurrent DAP `stackTrace`/`variables`/`evaluate` on the exiting task could dereference the freed VM. The cancelled early-out path constructs no VM, so it fires the hook directly instead.
- **DAP thread introspection must gate on `ThreadState::is_paused` — only a STOPPED thread has a stable stack to read.** `DebugSession::get_stack_trace` and `VariableInspector::lock_frame_and_vm` return empty/unresolved for a non-paused thread, tested under the same `ThreadState` mutex that guards `is_paused`. A free-running task VM concurrently mutates its call-frame vector (growth reallocation on `OP_CALL`, pops on `OP_RETURN`, `FunctionValue` teardown on task exit) and value stack, so dereferencing it would race the execution thread and intermittently `SIGSEGV` the adapter — the `test_task_spawn_exit_stress` sub-test (which issues `threads → stackTrace → scopes → variables` against concurrently-exiting tasks) targets exactly this, and already tolerates empty frames.

## Editor Extensions

- **VS Code** (`extensions/vscode/`): TypeScript/JavaScript extension bundling LSP + DAP. TextMate grammar for syntax highlighting.
- **Zed** (`extensions/zed/`): Rust extension with Tree-sitter grammar and LSP integration.
- **Tree-sitter highlight queries exist as canonical and editor copies, and the editor copy intentionally diverges from canonical.** `extensions/shared/queries/highlights.scm` is the canonical reference but is **not consumed at runtime**: Zed ships `extensions/zed/languages/luma/highlights.scm`, which renames capture *groups* to its editor's highlight conventions (e.g. for `interpolation` the canonical `@punctuation.special` becomes `@string.special`; Zed also reorders literals and uses `@constant.builtin`) while matching the **same grammar nodes**. So a change to query *structure* — e.g. reordering a node's children — must be hand-applied to both files; editing only the shared copy changes nothing a user sees. `extensions/shared/sync-queries.py` (`--check`/`--force`) is meant to propagate the canonical copy, but its structural compare only strips comment/blank lines — it does **not** ignore group-name renames despite its docstring — so `--check` flags the *intentional* group-name divergence and exits 1, and `--force` does a literal `shutil.copy2` that would clobber the editor-specific names. It is **not** wired into CI; treat it as a coarse diff aid, not a clean gate.
- **A query pattern's child order must match the grammar's `seq(...)` order, or it silently never matches** — and stricter Tree-sitter runtimes reject the *entire* highlights query, killing all highlighting. The grammar is `generic_params: seq("<", commaSep1($.type_identifier), ">")`, so the capture must sit *between* the brackets — `("<" (type_identifier) @type.parameter ">")`, **not** `("<" ">" (type_identifier))`, which can never fire. **Validate impossible patterns with `tree-sitter query`, never `tree-sitter highlight`**: the latter ran in degraded mode here and "passed" by a coincidental match against the temp filename, hiding the dead pattern. `extensions/tests/validate_queries.js` (run manually from the repo root after generating the parser in `extensions/zed/grammars/tree-sitter-luma` via `npx tree-sitter generate`; among the Tree-sitter checks only `parse_fixtures.js` is wired into CI, so this guard is effectively local-only) compiles the editor copy against the grammar via `tree-sitter query` and asserts expected captures on known snippets; it SKIPs cleanly when the CLI/parser is unavailable. When you add or reorder a highlight capture, add a `tree-sitter query` regression snippet that asserts the new capture appears.

## Sandbox Mode

- `--box` flag disables OS-accessing modules: Console, Csv, FileSystem, Http, KeyValueStore, Process, Socket, Xml.
- Individual file-I/O functions (like `Compression.gunzip_file`, `Hash.sha256_file`, `Log.set_output`) also use `if (!sandbox)` guards.

## GraphicalUi

- Declarative GUI using Elm Architecture (Model–Update–View) with HTML/CSS/JS webview rendering.
- Conditionally compiled (`LUMA_HAS_WEBVIEW`). Requires: WebView2 (Windows, lazy-loaded), WebKit+Cocoa (macOS), webkit2gtk (Linux). Gracefully disabled if missing, or explicitly via `LUMA_FEATURE_WEBVIEW=OFF`. The stub path registers every function to throw a "not available" error (constants and the shared CSS validation helpers still work). Test split: `stdlib_test_graphicalui.cpp` (live module, registered when `LUMA_WEBVIEW_AVAILABLE`) vs `stdlib_test_graphicalui_stub.cpp` (stub path, registered otherwise).
- Features: 15 basic widgets, 24 composite widgets, 9 layout containers, 6 overlays, 7 chart types, 21 commands, 14 subscriptions, 17 styling helpers, routing, accessibility, animations.
- Commands are side effects as data — runtime executes them and delivers results as messages.
- **Headless mode & test API (how GUI examples are verified without a display)**: `LUMA_GUI_HEADLESS=1` runs the full Elm lifecycle (init → view → subscribe → optional scripted `update` messages from `LUMA_GUI_MESSAGES`) and returns *without* creating/running a webview — `render_view` and command/subscription application early-return when `state.webview == nullptr`. The `GraphicalUi.test_*` API (registered in `graphicalui_testing.cpp` via `define_native`, all using a throwaway `HeadlessApp`) drives interaction with no display: `test_init(config)→model`, `test_render(config, model)→tree`, `test_count(config, model, locator)→integer`, `test_click(config, model, locator, index?)→model`, `test_input(config, model, locator, value, index?)→model`, `test_event(config, model, locator, event, args?, index?)→model`, `test_find(config, model, locator)→widget`, `test_key(config, model, key)→model` (fires keyboard subscriptions), `test_message(config, model, message)→model` (delivers a message to `update`). Use these in `@test` blocks to assert behaviour, not just "doesn't crash".
- **Dev-assets iteration loop**: the JS/CSS/JSON embedded in `graphicalui_assets.hpp` is compressed and baked in at build time. Setting `LUMA_GUI_DEV_ASSETS=external/gui-framework` makes the runtime read raw `gui-renderer.js`/CSS/JSON (plus siblings `external/lucide`, `external/lit-html`, `external/uplot`) from disk, so you can iterate on the front-end **without a 5-8 min C++ rebuild**. The renderer is the `gui-renderer.js` shell with the per-category `renderers/*.js` fragments spliced in at the `// __GUI_WIDGET_RENDERER_FRAGMENTS__` marker; `scripts/generate_gui_assets.mjs` (prod) and `build_gui_renderer_js_dev` in `graphicalui_serialization.cpp` (dev) perform the identical splice, so keep the two in sync. To persist a change, run `node scripts/generate_gui_assets.mjs` to regenerate `graphicalui_assets.hpp`, then rebuild (the build does *not* invoke node — asset generation is a manual dev step).
- **"[unknown widget]" pitfall**: the browser renderer `renderWidget` (gui-renderer.js) is a pure `WIDGET_RENDERERS[type]` table lookup that falls back to `[unknown widget: <type>]`. A widget type present in `graphicalui_constants.hpp` but missing a renderer entry renders as plain text in the live webview — and headless `--test` *cannot* catch it (it inspects the C++ widget dictionary, not the JS). The `WIDGET_RENDERERS` table is split by category across `external/gui-framework/renderers/{basic,layout,advanced,interaction}.js` (mirroring `graphicalui_widgets_*.cpp`; menu/popover/combobox live in `interaction.js`). The guard is the `test_renderer_covers_all_widget_types` ctest in `tests/runtime/stdlib_test_graphicalui.cpp`, which parses `graphicalui_constants.hpp` widget types against the renderer keys in every `renderers/*.js` fragment plus the `CHART_TYPES` loop in `gui-renderer.js`. After adding a widget, add its renderer entry to the matching fragment and regenerate assets.
- **GraphicalUi HTTP commands run *natively*, not via the browser's `fetch()`** — the `http_get`/`http_post`/… commands dispatch through `cmd_http` → `do_http_fetch_text` (raw sockets/TLS), so they are **not** subject to CORS: a cross-origin GET the browser would reject with `Failed to fetch` now succeeds (this *reverses* the older browser-fetch behaviour — the `Http`-module workaround is no longer needed). The request runs **synchronously on the UI thread**, freezing the window until it returns, so the default timeout is `k_gui_http_default_timeout_ms` = 8 s — deliberately below the standalone `Http` module's 30 s. An off-thread design is intentionally avoided: `do_http_fetch_text` exposes no cancellation, so worker requests would have to be joined on window close, trading a freeze-during-use for a hang-up-to-timeout on shutdown. Pass an explicit larger `timeout` (trailing arg) for slow trusted endpoints.
- **String message routing**: an interactive widget callback that returns a bare `string` is routed by `apply_event_result` (`graphicalui_commands.cpp`) through the app's `update(model, msg)` — this is what makes `navigation_link("X", "navigate:/about")` work. `process_callback_result` stays the terminal primitive (it must not re-route, to avoid recursion). Relatedly, VM string indexing (`handle_string_index_get`, `vm_dispatch_collections.cpp`) must reject non-integer keys cleanly rather than calling `as_integer()` unchecked — an unchecked call surfaced as `bad variant access` when a string message reached a dict-typed `update`.
- **URL-scheme allow-listing is enforced twice and the two sides must stay in sync.** Model-derived strings reach anchor `href`, image/avatar `src`, `window.open` (`open_url`), and the download anchor (`download_file`); lit-html escapes attribute *values* but does **not** validate URL *schemes*, so a `javascript:`/`vbscript:` URL would execute script (and can reach the `__gui_event`→C++ bridge). The JS `sanitizeUrl` (`gui-renderer.js`) and C++ `has_allowed_url_scheme` (`graphicalui_commands.cpp`) are deliberate mirrors: each strips ASCII tab/newline/CR and lowercases the scheme (defeating `java\tscript:`, and leading-whitespace/mixed-case forms such as a space before `JavaScript:`) and permits only an explicit set — links & `open_url` → `http,https,mailto,tel`; image/avatar & `download_file` → `http,https,data,blob`. A scheme-less (relative) URL is always allowed. Change one side → change the other.
- **The model JSON is embedded inside a `<script>` element** in the initial HTML (`GraphicalUi.app`, `graphicalui_module.cpp`), so the serializer (`value_to_json`, `graphicalui_serialization.cpp`) must escape with the slash-escaping `luma::json_escape` (`/`→`\/`, turning `</script>` into `<\/script>`) — **never** the non-slash `json_escape_string` variant. Pinned by `escape_utils_test.cpp::test_json_escape_closes_script_tag`.
- **A single malformed value wipes the entire GUI render**, because the webview `eval`s the serialized tree (`__gui_render({…})`) and any throw triggers the top-level error renderer. Three guards: (1) `value_to_json` coerces non-finite doubles (NaN/±inf) to `null` — the bare tokens `nan`/`inf` are invalid JS; (2) the event handlers `handle_keyboard`/`handle_resize`/`handle_focus_change` (`graphicalui_events.cpp`) check `event.has_string()`/`has_bool()` before reading the payload, else `std::bad_variant_access` escapes; (3) `cmd_random` orders its bounds with `std::min`/`std::max` because `std::uniform_real_distribution{a,b}` is undefined behaviour when `a>b` (e.g. `GraphicalUi.random(10, 1, cb)`).
- **The renderer never fully clears the DOM between renders, which imposes node-ownership invariants** (`gui-renderer.js`/`gui-charts.js`): (1) a `virtual_list` viewport must have exactly one lit-html render root — the parent template emits it *empty* and a deferred `flushPendingVlists` windows items in; two roots writing one node corrupt part bookkeeping. Its once-bound scroll handler reads live data from `container.__vlMeta` (refreshed each render) so it stays correct across model updates. (2) Chart axis label formatters read `container.__chartMeta.labels` live, not a closure captured at creation (uPlot reuse only calls `setData`, so a captured array goes stale). (3) The visually-hidden chart-summary a11y node is reused via `querySelector`, not re-appended, or duplicate hidden summaries pile up in the a11y tree. (4) `flushDeferred` drains queues in dependency order — vlist windows first (their items enqueue charts/accessible/ARIA/nested lists), then charts → accessible → per-widget ARIA.
- **Per-widget ARIA & the construct-context contract**: any widget accepts `aria_*` (and `role`) keys in its style dictionary (the C++ side serialises them to `_aria_*`; `buildAriaAttrs` collects them). Because lit-html static templates can't bind arbitrary attribute names, they are applied post-render located by element id — a synthetic `__gui_attr_*` id is assigned when the author supplied none. Widgets that bind a *deferred* callback (`slider`, `switch`, `text_area`, `number_input`, `form`, `drop_target`, `paginator`, `infinite_scroll`, `wizard`) or read the live window size (`responsive`) **throw if built outside an app/`view` context**; pure-data widgets (`draggable`) and command builders (`delay`, `random`, `debounce`, `http_post`, …) are constructible anywhere — handy for unit tests.
- **On Linux, `graphicalui_module.cpp` must include the real `<gtk/gtk.h>` and call `gtk_window_maximize(GtkWindow*)`** — the bundled `webview.h` already pulls GTK into the TU once `LUMA_HAS_WEBVIEW=1`, so the earlier local `extern "C" void gtk_window_maximize(void*)` forward declaration (used to maximise the window while the Linux backend was always the stub, before WebKitGTK was installed on CI) now conflicts with GTK's real prototype and mis-converts `void*`→`GtkWindow*` at the call site.

## Solaris (Prelude GUI Surface)

*Canonical guides: [../documents/Luma_Solaris_Architecture.md](../documents/Luma_Solaris_Architecture.md) (full design vision — broader than the shipped surface) and [../documents/Luma_Solaris_Guide.md](../documents/Luma_Solaris_Guide.md) (exact shipped API). The notes below are a quick-reference summary.*

- **Solaris is a beginner-first Model–View–Update (MVU) GUI surface layered over the low-level `GraphicalUi` web-view engine**: the app supplies a `Model` record, an `update` function, and a `view` built from `Solaris.*` elements with fluent modifier chains via the pipe operator; effect/subscription wrappers (`notify`, `set_scheme`, `after`, `fetch`, `every`, `on_key_press`) forward to the engine, which reconciles the immutable `View` tree onto `GraphicalUi`. Beginners write only Luma — never HTML/CSS/JS.
- **It ships as a built-in *prelude*, not an includable library** (`core/analysis/prelude/`). It is authored as ordinary Luma in `gui_prelude.luma` (so the lexer/parser/type-checker/editor tooling treat it as the language it is), then embedded verbatim by `scripts/generate_prelude_asset.mjs` into `gui_prelude_generated.hpp` as an **uncompressed byte array** — a byte array (not a string literal) sidesteps MSVC's 16 KB string-literal limit, and leaving it uncompressed keeps the analysis layer free of any miniz/decompression dependency. Regenerate manually after editing the `.luma` (the build does not run node), mirroring the `generate_gui_assets.mjs` GraphicalUi dev-asset split.
- **Injection is a conditional pipeline step between include resolution and type checking**, gated on the source mentioning `Solaris` as a **standalone identifier** (`contains_identifier_token` in `common/string_utils.hpp` / `SourceManager::any_source_contains_word`, so a longer name like `mySolarisHelper` never triggers it) and guarded against double injection by scanning for an existing `namespace Solaris`. Non-GUI programs pay nothing and get no global-type pollution.
- **Design-token choice types (`Emphasis`, `TextScale`, `Weight`, `Spacing`, `Align`, `Justify`, `Length`, `Radius`, `Scheme`) and the `View` record are declared top-level, NOT under `namespace Solaris`** — because the type checker cannot resolve a namespaced record in a `with`-update nor destructure a namespaced choice data-variant. The element constructors, fluent modifiers, reconciler, and app builder/runner live under `namespace Solaris`.
- **The two injection entry points (`gui_prelude.hpp`) differ in how prelude source is attributed.** `inject_gui_prelude(program, source_manager)` registers a virtual source file `<gui-prelude>` via `SourceManager::load_virtual`, so prelude AST locations attribute to it and never shift the user's line numbers — used by the interpreter (`program_loader.cpp`), REPL (`repl.cpp`), and DAP scratch compiler (`expression_compiler.cpp`). `inject_gui_prelude_tagged(program, prelude_file_id)` retains no source text and tags declarations with a caller-owned file id — used by the LSP (`lsp_analysis_service_impl.cpp`), which allocates an id past the include range (`includes.next_file_id`) and **drops every diagnostic carrying it**, because it renders diagnostics by line against the user's own document where a prelude location would otherwise paint on the wrong line. A malformed prelude fails safe (prepends nothing); a debug `assert` makes the build-time defect loud. Tests: `tests/analysis/gui_prelude_test.cpp`, `tests/features/stdlib/solaris_functions.luma`; examples `examples/applications/solaris_{counter,gallery,showcase}.luma`.

## REPL

- `luma` (no args) enters REPL. Also `--repl`/`-r`.
- Type checking is skipped in REPL (errors caught at runtime).
- Persistent environment across lines. Variables and functions can be redefined.

## Non-Obvious Patterns

- Semicolons are tokenized but treated as whitespace — they're neither required nor forbidden.
- String interpolation `"hello ${x}"` produces `StringStart`, expression tokens, `StringEnd` — not a single token. `InterpolationStart`/`InterpolationEnd` use `${` and `}` tokens.
- **The interpolation nesting-depth limit must be enforced *before* emitting `InterpolationStart`**: `Lexer::begin_interpolation` (`lexer_string.cpp`) checks `check_interpolation_depth()` before consuming `${` and pushing onto `interpolation_state_`. If the token were emitted first, an over-limit level would leave a start token with no matching state entry, and a later `}` would then close an *outer* level prematurely, desynchronising the token stream from the state stack. On over-limit it returns with the cursor still on `$`, so the main loop re-scans `${` as ordinary operators — the `{` still increments the enclosing level's `brace_depth`, which its `}` decrements, keeping outer levels balanced during error recovery. Pinned by `tests/analysis/lexer_test.cpp`.
- Annotations (`@main`, `@test`) must be on the line immediately before the function declaration.
- Private record fields require the `trusted` keyword on function parameters for access. Access is gated by checking if the base object's variable name is in `current_trusted_params_`.
- Include paths resolve relative to the including file's directory (not the working directory, except in REPL). `LUMA_PATH` provides additional search directories. Circular includes, path traversal (`..`), and symlinks in include paths are all detected and rejected (security).
- The type checker collects errors as `vector<Diagnostic>` data — it doesn't throw exceptions. The caller decides whether to halt.
- **A pipe shifts explicit user-function arguments by one during type and ownership checking**: in `a |> f(b, c)` the piped `a` fills parameter 0, so `ExpressionTypeChecker::check_user_function_args` and `check_call_ownership` (`expression_type_checker_calls.cpp`) match explicit arguments starting at parameter index 1 via `param_offset = tc_.context().is_in_pipe ? 1 : 0` — mirroring the stdlib and generic-function checks (the piped value's own ownership is checked separately in `check_pipe_first_parameter`). Omitting the offset mis-reported argument types and ownership for every piped call into a user-defined function; Solaris's heavy fluent-modifier pipe chains surfaced it.
- The optimizer has 3 levels: L0 (none), L1 (peephole), L2 (adds `constant_fold`, `unary_fold`, `comparison_fold`, `dead_code`, `jump_threading`, `dead_store`, `tail_call` — run to convergence, then `compact()`). Cross-function inlining (`inline_small_functions`) must run before per-chunk `optimize()` so inlined code benefits from passes. Constant folding is handled by the extracted **ConstFolder** class.
- **Two optimizer passes were intentionally removed as unsound at the bytecode level** (documented at `optimizer.hpp:94-102`): the multiply→shift **strength reduction**, and **constant propagation** (`GetLocal`→`Constant` for single-assigned locals). The optimizer sees only a `Chunk` — no local scopes/liveness — so a slot holding a single-assigned constant can be freed at scope-exit and reused by a later binding whose initializer is left on the stack (an *invisible* write with no `SetLocal` opcode); the stale constant then propagates into the wrong variable's reads, miscompiling exotic shapes like `match case == <block-with-locals>`. Re-enabling either needs a proper per-slot liveness/depth analysis. Removing an optimization can only improve correctness, so removal (not a risky fix) is the project precedent — **do not naively re-add a propagation/strength-reduction pass.**
- **Chunk** (`core/runtime/compiler/chunk.hpp`): Bytecode container. Source map stored as sparse `(byte_offset, SourceLocation)` pairs — one entry per opcode saves ~60% memory vs per-byte tracking. Source-location bookkeeping and the deduplicating name pool are now extracted into focused **SourceMap** (`source_map.hpp`, a binary-searched sparse map) and **NameTable** (`name_table.hpp`, interned 16-bit name handles) types that Chunk composes — so the name vector and its O(1) dedup index can no longer drift out of sync. **ConstantPool** (`constant_pool.hpp`) extracted: manages constant deduplication (integers, strings, and doubles use separate maps; doubles use `bit_cast` for exact equality to distinguish `0.0` from `-0.0`). Max 65,536 constant pool entries (uint16_t addressing).
- **NameResolver** (`core/analysis/resolver/resolver.hpp`): Single-pass resolution assigning slot indices for O(1) VM access. `ResolvedVar` has `frame_depth` (0=local, 1=enclosing — relative, not absolute), `slot_index`, `is_mutable`. Marks `is_captured` when variable is used in nested scope for upvalue handling.
- **Value-block scratch slots (compiler invariant)**: local slots are assigned as `locals.size() - 1` (`declare_local`), which assumes the value being bound is the first temporary above the locals region. When a value-producing block — a `match`/`if` used as an expression, or any sub-expression that declares locals mid-compilation — is compiled while operand-stack temporaries are already live *beneath* it (e.g. the container+index of `container[index] = match {…}`, prior call arguments, the left operand of a binary op, dict keys, pipe stages, interpolation parts), the block's locals get slots that ignore those temporaries → `GetLocal`/`SetLocal` hit wrong stack positions → corruption (`cannot index-assign into 'string'`, `cannot call 'string'`, `bad variant access`, or silently wrong values). Fix: bracket every such site with `reserve_scratch_slots(count, loc)` / `release_scratch_slots(count)` (defined in `assignment_compiler.cpp`, declared on `compiler.hpp` and the `i_variable_manager.hpp` role interface) — they declare empty-named placeholder locals so block locals land at their true runtime slots; release emits **no** runtime pops (the temporaries are consumed by the trailing `IndexSet`/`SetField`/compound op). For a balanced single-scope pair prefer the `ScratchSlotGuard` RAII wrapper (`scratch_slot_guard.hpp`, mirrors `ScopeDepthGuard`) so the count is stated once and can't leak on an early exit; keep the explicit `reserve`/`release` calls only for per-iteration or unequal-count shapes. Existing callers: `assignment_compiler`, `binary_operator_compiler`, `collection_compiler`, `interpolation_handler`, `pipe_compiler`, `expression_compiler`, `declaration_compiler` (one slot around a default parameter value — `JumpIfFalse` *peeks*, not pops, its boolean condition, so that temporary stays live while the default, possibly a value block, is compiled), and `pattern_compiler` (value-form `match` reserves `subject_temps_below + 1` slots around each arm's pattern test — a `case == <expr>` comparison value can be an arbitrary locals-declaring block sitting above the untracked subject + `Dup` temps; value-form has 2 untracked temps below so `subject_temps_below=1`, statement-form's subject is a tracked hidden local so `subject_temps_below=0`). **When adding any compile path that leaves temporaries on the stack before compiling a sub-expression, you must reserve scratch slots** or you reintroduce this stack-corruption class.
- **TokenType enum**: 140+ token types with type keywords as distinct tokens (not string keywords). `token_type_to_string()` uses constexpr array lookup (replaces switch). Token literals are pre-computed (`TokenLiteral = std::variant<monostate, int64_t, double, bool, string>`) to avoid re-parsing.
- **RecursionGuard** (`core/runtime/interpreter/value.cpp`): RAII class with thread-local depth counters (`to_string_depth`, `equals_depth`, `deep_copy_depth`) to prevent stack overflow on deeply nested recursive ADTs. Max depth is 64. Each operation maintains an independent counter to catch mutual recursion.
- **Value equality uses value semantics**: `Value::equals()` compares by value, not reference. Deduplication in `Array.unique()` and `LinkedList.unique()` uses `Value::equals()`. Closures compare by reference; records compare by type name + all fields; choice types compare by variant + payload. Equality logic is decomposed into named helpers: `equals_numeric()` (handles cross-numeric promotion), `equals_structural()` (choice, record, result, range, reference), and `elements_equal()` (template for container element comparison using ranges).
- **Clamping vs throwing**: Prefer clamping negative values to 0 over throwing for computed-length parameters (e.g., `String.truncate` clamps negative `max_length` to 0). Similar to Rust's `saturating_*` operations — more forgiving for beginners.

## Cross-Cutting Design Patterns

- **Composition over monoliths**: Large classes (VM, Compiler, TypeChecker, LspServer, DebugSession) decomposed into focused components that hold non-owning references to parents. Friendship access maintains encapsulation at module boundaries.
- **Builder/Fluent API**: Used in JsonBuilder (`set → set_if → build`), ArrayBuilder (`add → add_if → build`), ModuleBuilder (`func → constant → native`), Pipeline (`add → add → build`). Methods return `*this` or parent reference for chaining. `build()` is ref-qualified: lvalue copies (builder reusable), rvalue moves (efficient for temporaries).
- **Callback decoupling**: ExpressionEvaluator uses `RefAllocator` callback to decouple from VariableInspector. BreakpointManager uses `ConditionEvaluator` callback. AnalysisService uses callbacks for logging and notifications. Enables modular testing and dependency injection.
- **Lock ordering documentation**: DebugSession documents explicit mutex acquisition order to prevent deadlocks. All code paths follow the documented order. RAII helpers enforce ordering.
- **Safe narrowing**: `narrow_int(int64_t)` throws on overflow (ES.46 compliant), defined in `core/common/narrow_int.hpp` and re-exported by `json_helpers.hpp`. `clamp_to_int(int64_t)` clamps to [0, INT_MAX] for non-negative protocol fields. Null-safe field extraction with defaults throughout DAP helpers.
- **Naming conventions for lookups**: `find_*` methods return `std::optional` or `const` pointer (nullable). `is_*`/`has_*` methods return bool. `*_range`/`*_bounds` return Range or `pair<int, int>`.
- **RAII Guard pattern**: `ScopeStack<T>::Guard` auto-pushes on construction and pops on destruction. Standardized `ScopeGuard<Func>` in `core/common/scope_guard.hpp` for generic cleanup. Used wherever scope depth must track control flow exactly.
- **Query object pattern**: AnalysisQuery provides read-only accessors over analysis results, decoupling consumers from internal data structures.
- **Platform abstraction pattern**: Platform-specific code uses conditional declarations in headers (`#ifdef _WIN32` / `#else`) with separate `*_posix.cpp` / `*_win32.cpp` implementation files. Shared inline utilities wrap OS-specific APIs (e.g., `platform_socket.hpp` provides unified `close()`, `last_error()`, `set_non_blocking()`, `set_timeout()`; `platform_utils.hpp` provides `wstring_to_utf8()` and `safe_getenv()`). Use for sockets, terminal I/O, and environment access where implementations differ significantly.
- **Thread-safe caching**: Mutex-guarded caches with size caps (e.g., ReDoS validation cache: 1024 patterns; compiled-regex cache: 256 entries; compilation cache: 128 entries; semantic token cache). Check-then-validate-then-insert pattern with minimal lock scope for hot paths. Atomic globals (`std::atomic<T>`) for lightweight runtime-configurable values (e.g., `escape_timeout_ms`).
- **Centralised dispatch**: AST dispatch (`ast_dispatch.hpp`) and opcode dispatch (`vm_dispatch_table.cpp`) each map kind/opcode to handler in a single location, enforced by concepts or static_assert.
- **Role interfaces (Interface Segregation)**: Fat back-reference interfaces are decomposed into focused role interfaces so a collaborator depends only on the slice it uses and can be mocked in isolation. The compiler's `ICompilationBackend` is composed from `i_bytecode_emitter.hpp`, `i_scope_lifecycle.hpp`, `i_variable_manager.hpp`, `i_sub_compiler.hpp`, `i_diagnostic_sink.hpp`, and `i_context_access.hpp`; the type checker's `TypeCheckingServices` inherits a set of roles defined in `type_checking_services_roles.hpp`. The aggregate interface still inherits all roles (and the production class remains the sole implementor), so existing code that depends on the whole surface is unaffected.

## C++ Coding Style

*Canonical guide: [cpp.instructions.md](cpp.instructions.md). The notes below are a quick-reference summary.*

- `snake_case` for variables, functions, namespaces, files. `PascalCase` for types/classes/structs. 4-space indentation. Always use braces.
- West-const (`const int`, not `int const`). `const` by default, `constexpr` where possible.
- RAII for all resource management. `std::unique_ptr` for ownership, `std::shared_ptr` for shared ownership.
- Exceptions for errors, `std::optional` for expected absence.
- `[[nodiscard]]` on functions whose return values must not be ignored; to intentionally discard such a result, prefix the call with `(void)` (silences MSVC C4834 — follow the `(void)eval(...)` convention in `tests/shared_eval.hpp` / `tests/runtime/stdlib_test_helpers.hpp`). `explicit` on single-argument constructors.
- Prefer algorithms and range-based for loops over index-based iteration.
- No third-party runtime dependencies except when functionality truly cannot be achieved with the standard library and OS APIs.
- Comments explain **why**, not **what**. Code should be self-documenting.

## Static Analysis (clang-tidy)

*Configured in `.clang-tidy` (requires clang-tidy 18+ and a `compile_commands.json`, enabled via `CMAKE_EXPORT_COMPILE_COMMANDS`). A `tidy` build target (guarded by `find_program(CLANG_TIDY_EXE ...)`) wraps the run.*

- `.clang-tidy` is the **single source of truth** for severity: `WarningsAsErrors: 'clang-analyzer-*,bugprone-*,concurrency-*'` — these real-bug categories fail the build everywhere (local `tidy` target, editor integrations, CI). Style groups (`readability-*`, `modernize-*`, …) stay advisory by their absence from that list. CI no longer passes its own `--warnings-as-errors`.
- `HeaderFilterRegex` limits header diagnostics to first-party dirs (`core|language-server|debugger|shared`), anchored to path boundaries so a vendored `external/.../core/` path can't be mistaken for `core/`.
- A handful of `clang-analyzer-*` checks are disabled with in-file justification because they fire *only* as false positives that location filters can't suppress (the static analyzer bypasses `HeaderFilterRegex`): `optin.core.EnumCastOutOfRange` (flag-enum casts like `ValueCategory`, plus MSVC `<filesystem>` internals), and `cplusplus.NewDeleteLeaks` + `optin.cplusplus.VirtualCall` (both only inside vendored `external/webview/webview.h`). `cppcoreguidelines-pro-bounds-avoid-unchecked-container-access` is also off — its only fix is `.at()`, which injects bounds checks into the VM dispatch hot path, and it is clang-tidy 19+ only (project pins 18).
- **Intentional empty catches** get `// NOLINT(bugprone-empty-catch)` per-site (~15 files) rather than disabling the check globally.
- **Test entry points must not let exceptions escape**: `run_test()` in `tests/test_framework.hpp` is `noexcept` and catches both `const std::exception&` and `...`; the `RUN`/`RUN_PARAMETERIZED`/`SUMMARY()` macro-built `main()` bodies rely on this to satisfy `bugprone-exception-escape` on every test executable.
- **Two `bugprone-*` patterns that compile clean but fail the gate** (both in `WarningsAsErrors`): `bugprone-implicit-widening-of-multiplication-result` — a size like `std::vector<T> v(64 * 1024)` multiplies as `int` *before* widening to `size_t`; do the arithmetic in `size_t` (a `constexpr std::size_t k_inflate_scratch_size = std::size_t{64} * 1024;` constant, as in `compression_module.cpp`). `bugprone-throwing-static-initialization` — a namespace-scope object whose constructor allocates / can throw (e.g. a `std::deque<std::string>`); move it into a function-local `static` accessor so init is lazy (first-use) and a throw surfaces at a call site, not during static init (as fixed in `terminal_testing.cpp`).
- **clang-analyzer mis-models a lambda-captured structured binding as a possibly-null pointer** (a `core.NullDereference` false positive): capturing `[name, flag]` from `auto& [name, flag] = entry` by reference into a lambda trips it. Bind plain locals (`const auto& name = entry.first;`) before the lambda so it captures ordinary variables (`statement_type_checker_control.cpp`).
- **CI runs clang-tidy on Linux only, sharded 4 ways (round-robin `NR % 4`), and excludes `*_win32.cpp`** — those files are absent from the Linux `compile_commands.json`, so clang-tidy would parse them with default flags and fail on their unconditional `<windows.h>`/`<io.h>` includes. The first full sweep surfaced 62 findings; the recurring real fixes beyond widening (above) were `bugprone-unchecked-optional-access` (bind the optional to a `const&` local before the deref the analyser can't pair with a prior `has_value()`) and `concurrency-mt-unsafe` on `getenv`/`setenv`/`strerror` (NOLINT — no portable mt-safe form; call sites are single-threaded init or the child side of a fork).

## Performance

- Lexer: single-pass, O(n) in source length.
- Parser: recursive descent, O(n) tokens.
- Type checker: single AST walk, O(n) nodes.
- Compiler: single pass, O(n) AST nodes.
- VM: O(1) per opcode dispatch via function pointer table (replaces switch). Variable lookup: O(1) locals (stack slot), O(1) globals (inline cache via VMGlobalCache, exploiting pointer stability).
- All collection operations return new copies (O(n)). Incremental string concatenation is O(n²) — use `Array.map` + `String.join` instead.
- LinkedList has no performance advantage over Array due to deep-copy semantics.
- HashSet provides O(1) average `contains` (vs O(n) for Set) but only supports hashable primitives.

## Bytecode Serialization & Caching

- Two-level caching system: (1) `CompilationCache` — in-memory LRU (default 128 entries), keyed by `(absolute path, content hash, options)`, thread-safe (mutex). (2) `BytecodeSerializer` — disk-based; `run_file` (in `cli_runner.cpp`) writes compiled bytecode to a `<source>.lumc` file **next to the source** via `BytecodeSerializer::cache_path_for`, which just does `replace_extension(".lumc")`. On the next run it reads/validates that file and skips compilation on a hit. The disk cache key mixes the source hash with the optimization level. Only normal runs write `.lumc`; `--check` and `--test` compile in memory only. `CompilationCache` is injectable via `run_file()` for testability.
- `.lumc` binary format: 24-byte header (`"LUMC"` magic, u32 format version, u32 flags, u64 source hash via **FNV-1a** — `fnv1a_hash`, not xxHash — u64 timestamp), followed by function table (count + per-function metadata, bytecode chunks, constant pools, source maps).
- `BytecodeSerializer` handles serialize/deserialize with typed `DeserializeResult` containing error codes (`BadMagic`, `VersionMismatch`, `CorruptFunction`, `HashMismatch`, etc.) and detail strings.
- Format version currently 2 (v1→v2 widened every serialized string's length prefix from u16 to u32, so a string constant or name of ≥ 65,536 bytes no longer wraps its prefix and desyncs the rest of the stream — `k_string_length_prefix_bytes` went 2→4 accordingly). Bump `k_bytecode_format_version` for incompatible changes.
- `BytecodeVerifier` validates structural integrity (valid opcodes, jump targets on instruction boundaries, constant/name indices in-bounds, stack depth simulation, upvalue/local slot ranges). Optional, disabled by default.
- **Bounds-check counts before `reserve()` when deserializing `.lumc`**: an attacker-controlled length (e.g. the source-map entry count) can otherwise trigger a huge `reserve()` and OOM. The deserializer rejects any count whose implied byte size exceeds the remaining input before reserving — `if (r.error() || !r.has_remaining(map_count * SerializerLimits::k_source_map_entry_bytes)) error;`. Apply the same `has_remaining()` guard to every `reserve(count)` driven by untrusted input — the top-level function vector likewise rejects `func_count` against `SerializerLimits::k_min_function_bytes` (31, the smallest a fully-empty serialized function can be) and returns `DeserializeError::BadFunctionCount` before `functions.reserve()`, joining the source-map (`k_source_map_entry_bytes`) and name-table guards (found via fuzzing the bytecode deserializer).

## Stdlib Infrastructure

- **ErrorMessages** (`error_messages.hpp`): Centralised error message factories and machine-readable error code constants in `error_codes` namespace (`empty_container`, `index_out_of_bounds`, `key_not_found`, `type_mismatch`, `division_by_zero`, `size_limit_exceeded`, `parse_error`, `io_error`, `invalid_argument`, `not_found`). All stdlib modules use these for consistent error reporting. Two styles: **unqualified** (short, e.g. `"index 5 out of bounds for array of length 3"`) and **qualified** (prefixed, e.g. `"Array.get: index 5 out of bounds (size 3)"`). Prefer qualified variants in new code. Qualified helpers include: `expected_type`, `empty_container`, `index_out_of_bounds`, `key_not_found`, `invalid_argument`, `division_by_zero`, `value_out_of_range`, `size_limit_exceeded`, `result_exceeds_maximum_size`, `must_be_non_negative`, `must_be_positive`, `conversion_error`, `parse_error`, `io_error`, `not_found`.
- **ContainerOps<Container, ReverseEach>** (`container_ops.hpp`): Template registering standard operations (`length`, `is_empty`, `to_array`, `map`, `filter`, `reduce`, `each`, `partition`, `concat`) for any container with a `std::vector<Value>` elements member. Used by Queue, Stack, Set, LinkedList, HashSet to eliminate near-identical implementations. The `ReverseEach` template parameter (default `false`) uses `if constexpr` to dispatch iteration direction — `true` for LinkedList (which iterates in reverse for `each()`), `false` for all others.
- **LazyRegistry** (`lazy_registry.hpp/.cpp`): Delays stdlib module initialization until first use via factory callbacks. Environment calls back into registry on namespace miss. Reduces startup from O(N modules) to O(1) + per-module cost on demand. Thread-safe.
- **StdlibCatalog** (`shared/stdlib/stdlib_catalog.hpp`): Single source of truth for function metadata (arity, params, return types, param types, capabilities). Both type checker and language server derive from it. `Capability` flags (`None`, `FileSystem`, `Network`, `Process`, `Console`) for sandbox-awareness. `ReturnTypeDesc` describes return types without depending on TypeInfo — lightweight descriptors convertible to TypeInfo by the type checker. The stdlib namespace list is derived from the catalog — not hardcoded. `FunctionSpec` includes `param_types` vector for structured parameter type info, auto-derived by `StdlibTypeHandler::init_param_types()`.
- **StdlibRegistry** (`stdlib_registry.hpp`): Module table mapping module names to registration functions with `os_only` and `sandbox_aware` flags (unified — no special-case sandbox handling outside the table). O(1) lookup via static hash map built on first call. 30 always-available + 8 OS-only + 3 sandbox-aware (Compression, Hash, Log) = 41 module namespaces.
- **Stdlib choice variants: unit variants are `ChoiceValue` globals, payload variants are `NativeFunctionValue` constructors** (`register_stdlib_postamble`, `stdlib_registry.hpp`). The postamble walks every choice in `stdlib_choice_types()` and binds `Namespace.Type.Variant` at runtime. A **unit** variant (no fields, e.g. `Log.Output.Stdout`, `Terminal.Key.Enter`) binds a field-less `ChoiceValue` — it is a `GetGlobal` lookup, so it MUST stay a value. A **payload** variant (`variant.fields` non-empty, e.g. `Log.Output.File(path)`, `Json.Value.JsonString(s)`, `Xml.Node.Element(...)`, `Terminal.Key.Character/Function`) binds a `NativeFunctionValue` whose body builds `ChoiceValue{type_name=ch->name, variant, fields=[copied args]}`, mirroring `handle_make_choice_constructor` (`vm_dispatch_construction.cpp`). Originally the postamble registered *every* variant as a field-less `ChoiceValue`, so calling a payload variant threw "cannot call 'X'" at runtime even though the type checker accepted it — **no stdlib payload-variant was runtime-constructible**. `match` is unaffected by the representation: the compiler emits `Op::IsType` with the variant name from its compile-time name table and `TypeMatcher` inspects `ChoiceValue.variant`/`type_name` directly — it never reads the runtime global binding. Consequence for the conformance test (`stdlib_catalog_conformance_test.cpp`): payload constructors are now `is_native_function()`, not `is_choice()`, so `test_all_registered_functions_are_in_catalog` must skip any binding whose name is a known choice-variant full name (built from `stdlib_choice_types()`), not just skip `value.is_choice()`.
- **ReDoS Validation Cache** (`regularexpression_module.cpp`): Thread-safe cache (`std::unordered_set<std::string>`, max 1024 entries, mutex-guarded) of regex patterns that have passed ReDoS safety validation. `has_dangerous_quantifier_nesting()` uses a single bounds-checked pass with a per-group state stack to detect two catastrophic-backtracking shapes under repetition: (1) **nested quantifiers** like `(a+)+`, and (2) **ambiguous alternation** whose branches overlap on their first token like `(a|aa)+`, `(.|a)+`, or `(a|)+` (an empty branch). Disjoint alternation such as `(cat|dog)+` or `(a|b|c)+` stays accepted. It deliberately prefers false positives (rejecting a borderline-safe pattern) over false negatives, since `std::regex` backtracking is catastrophic on some standard-library implementations even where MSVC happens to optimise it. `is_pattern_redos_safe()` checks cache first (lock-guard), validates if missing, caches on success. Prevents re-parsing identical patterns in loops.
- **Compiled-Regex Cache** (`regularexpression_module.cpp`): Sibling to the ReDoS validation cache but distinct — a thread-safe `std::unordered_map<std::string, std::shared_ptr<const std::regex>>` (max 256 entries, mutex-guarded) that memoizes *compiled* `std::regex` objects so hot loops don't recompile the same pattern each call. `get_compiled_regex()` compiles **outside** the lock (only the map insert is guarded, via `try_emplace`) so callers never serialize on the regex engine, and returns a `shared_ptr<const std::regex>` so the handle stays valid and immutable after the lock is released — concurrent const `regex_search`/`regex_replace` on it are data-race free. Never evicts (mirrors the validated-pattern policy: once full, stops inserting). Keyed by pattern string **alone**, which is correct only because every call site uses default ECMAScript flags — a flagged variant would have to fold the flags into the key. Only ReDoS-safe, size-checked patterns ever reach it (validation runs first), so no dangerous pattern is compiled or cached; invalid patterns throw `std::regex_error` from construction exactly as before. Kept separate from the validation cache (different cap and lifecycle) to preserve that cache's documented behaviour.

## Common Utilities

- **Result<T, E>** (`core/common/result.hpp`): Generic result type modeled after Rust's `Result<T, E>`. Static factories `Result::ok(value)` and `Result::err(error)`. Default error type is `std::string`. Use over `std::optional<T>` when failure reasons vary and must be communicated.
- **StringHash / StringMap\<V\> / StringSet** (`core/common/string_hash.hpp`): Transparent hash functor enabling heterogeneous lookup — `std::string_view` can be passed to `find()`, `contains()`, `count()` without allocating a `std::string`. Use `StringMap<V>` and `StringSet` aliases for string-keyed containers throughout the codebase.
- **format_number()** (`core/common/format_number.hpp`): Formats doubles with trailing zero trimming while keeping at least one digit after the decimal (e.g., `3.0`, `1.5`, `-0.25`). Consequence: a whole `number` (double) always prints with a trailing `.0` (e.g. `42` → `"42.0"`); flooring/rounding the value is *not* enough to display an integer-looking string — convert to the `integer` type (`Converter.to_integer`) so it formats without the decimal.
- **has_directory_traversal()** (`core/common/path_utils.hpp`): Returns true if any path component is `..`. Used for include path security validation.
- **platform_utils** (`core/common/platform_utils.hpp`): Header-only shared utilities for platform-abstracted environment access. `wstring_to_utf8()` (Win32-only, `WideCharToMultiByte`) and `safe_getenv()` (MSVC `_dupenv_s` with RAII vs POSIX `std::getenv`). Used wherever environment variables or wide-string conversion is needed.
- **file_time_to_system_clock()** (`core/common/file_time.hpp`): Header-only, feature-tested conversion of a `std::filesystem::file_time_type` to a `std::chrono::system_clock::time_point`. Uses `std::chrono::clock_cast` when available (`__cpp_lib_chrono >= 201907L`), else rebases the file-clock time point onto the system clock — Apple libc++ (and some others) do not provide `clock_cast`. Single home for both the FileSystem module and the LSP persisted index (`lsp_persisted_index.cpp`), which each had a `clock_cast` call site that broke the macOS build.
- **LruCache<Key, Value, Hash>** (`core/common/lru_cache.hpp`): Header-only LRU cache. O(1) lookup, insertion, and eviction via `std::list` (LRU order) + `std::unordered_map` (key → list iterator). Front = MRU, back = LRU. `put()` returns a `Value&`; `get()` promotes to MRU and returns pointer or nullptr. Not thread-safe — callers must guard externally. Used by `ExpressionEvaluator` (expression cache) and `LspAnalysisService` (document analysis cache).
- **VariableReferenceRegistry\<T\>** (`debugger/source/variable_reference_registry.hpp`): Generational registry replacing per-frame `std::unordered_map<int, T>` in `VariableInspector`. `allocate()` assigns an ID and records the current generation. `lookup()` returns `std::nullopt` for stale (wrong-generation) entries. `advance_generation()` + lazy `purge_stale()` provides O(1) bulk invalidation — far cheaper than clearing maps every resume.
- **escape_string_impl\<EscapePolicy\>** (`core/common/escape.hpp`): Policy-based escape engine. An `EscapePolicy` provides either `escape_char(char, std::string&)` or `try_escape(char) → optional<string_view>`. Built-in policies: `JsonEscapePolicy`, `XmlEscapePolicy`, `JsEscapePolicy`, `HtmlEscapePolicy`. `json_escape()` and `js_string_escape()` are thin wrapper functions returning strings; `json_escape_string()`, `xml_escape_string()`, and `html_escape_string()` append directly to an output buffer (zero intermediate allocations). All input parameters accept `std::string_view`. Add new escape variants by defining a policy struct — no code duplication.
- **HandlerRegistry\<HandlerFn\>** (`shared/protocol/handler_registry.hpp`): Generic method→handler dispatch map template used by both LSP and DAP servers. `register_handler()` throws `std::logic_error` on duplicate (works in Release builds unlike assert). `find()` returns `const HandlerFn*` (nullptr if unknown). Populated once at startup, read-only thereafter — no locking needed.
- **CompilerLimits / OptimizerLimits** (`core/runtime/compiler/compiler_limits.hpp`): Consolidated `static constexpr` limit constants for the compiler and optimizer. Replaces 14+ scattered constants across compiler.hpp, optimizer.cpp, and bytecode_serializer.cpp. `compiler.hpp` aliases them for backward compatibility.
- **ParsedUrl** (`core/runtime/stdlib/io/http_url_parser.hpp`): Lightweight URL parser for HTTP(S) requests. Extracts scheme, host, port, path, and query. IPv6-aware (handles `[addr]:port` bracket syntax). Header-only for reuse across stdlib modules.
- **LspConfig / ConfigSnapshot** (`language-server/source/lsp_config.hpp`): Uses copy-on-write snapshots. `get()` briefly acquires `update_mutex_` to copy the `shared_ptr`, then callers access the immutable `ConfigSnapshot` fields lock-free. The comment "without holding any lock" was incorrect — `get()` *does* hold the mutex briefly. Writers call `apply_lsp_settings()` / `apply_project_config()` which build a new snapshot and publish atomically. Callers: `config().get()->analysis_debounce_ms` pattern.
- **HandlesAll concept** (`core/analysis/ast/ast_dispatch.hpp`): `template<typename H, typename... NodeTypes> concept HandlesAll = (requires(H&& h, const NodeTypes& node) { h(node); } && ...)`. Used to build `ExpressionHandler`, `StatementHandler`, `DeclarationHandler` concepts as one-liners. Catches missing handler overloads at the call site rather than inside the switch body.
- **OrderedLockGuard\<LockIdType\>** (`debugger/source/dap_session_types.hpp`): Class template constrained by `LockId` concept (`std::is_enum_v<T> && std::totally_ordered<T>`). In debug builds, applies DAP lock-ordering assertions via `if constexpr (std::same_as<LockIdType, DapLockId>)` — other conforming enums are accepted and lock/unlock without ordering checks. `OrderedUniqueLock` variant exposes `underlying()` for `condition_variable::wait()`.

## C++ Pitfalls Discovered

- **`std::string_view` dangling after `std::move`**: `CompiledFunction`'s `param_name_index_` originally used `string_view` keys into `param_names`. After move, SSO-sized strings get new addresses → dangling views. Fix: use `std::string` keys. The same pitfall applies to any `string_view` into a `std::vector<std::string>` — reallocation invalidates them (e.g., constant pool string_view keys).
- **`std::once_flag` makes objects non-copyable/non-movable**: Attempted using `std::once_flag` for lazy `param_name_index` initialization, but it made `CompiledFunction` non-copyable/non-movable. Switched to eager initialization in `end_function()` and after deserialization.
- **`__builtin_unreachable()` / `__assume(false)` cannot be used in `constexpr` functions**: Use `assert(false)` instead for unreachable default cases in constexpr contexts.
- **MSVC `[[deprecated]]` on base class causes error on derived class use**: Use comment-based deprecation instead when the base class has active derived classes.
- **Atomic memory ordering matters for debug hooks**: `pause_requested` store was relaxed → changed to release ordering. Debug callback setters need release ordering; readers need acquire.
- **`notify_one()` outside the lock**: Channel notify should call `notify_one()` after releasing the lock to avoid waking a receiver that immediately blocks on the mutex.
- **Recursive-descent parser branches each need a depth guard**: every branch in `core/analysis/parser/` that recurses must take `auto guard = make_recursion_guard(current().location);` (defined in `parser.hpp`). It is easy to miss *conditional* recursion branches — the prefix-unary path in `parse_unary()`, the `spawn`/`await` postfix branches and `else if` chains in `parse_if_expression()`/`parse_if_statement()`, and `type_annotation_parser` — which fuzzing surfaces as stack overflows. **Lookahead helpers that recurse need their own explicit depth parameter**, because they run *before* the `make_recursion_guard`-tracked parse path: `Parser::skip_type_at(offset, depth)` (`parser_stmt.cpp`) bounds `depth` by `ResourceLimits::max_parse_depth` and bails (returning the current offset to route the construct to the bounded expression parser) instead of overflowing the native stack on a deeply nested type-like construct (e.g. thousands of `(`). This parser-side guard is distinct from the runtime `RecursionGuard` in `value.cpp` (which guards `to_string`/`equals`/`deep_copy`).
- **Windows headers leak `min`/`max` macros**: every translation unit that pulls in a Windows header must `#define NOMINMAX` *before* it (done in ~25 files) or `std::min`/`std::max` and `(std::numeric_limits<T>::max)()` fail to compile. Some portability defects only surface *off* Windows: a missing `<utility>`/`<cstdint>` include, or `extern char** environ;` (must be declared at file scope — not inside a function — for POSIX `process_module.cpp`), compiles under MSVC but breaks under Linux/clang. Build on both before claiming cross-platform.
- **MSVC `/W4` does not enforce the project's gcc/clang warning flags** (`cmake/LumaCompilerFlags.cmake`), and there is no global `/WX` on MSVC — so warnings never fail the MSVC build and must be grepped from logs. Three defect classes therefore compile clean under MSVC but break the Linux/clang(-cl) build: (1) **`-Wreorder-ctor`/`-Wreorder`** — the constructor member-initializer list must list members in *declaration* order; (2) **`-Wdouble-promotion`** — initialise doubles with `std::numeric_limits<double>::quiet_NaN()`, never the float `NAN` macro; (3) **LP64-vs-LLP64 literal ambiguity** — on LP64 targets (Linux/macOS) `int64_t` is `long`, so a `long long` literal like `42LL` becomes ambiguous across overloaded `Value` constructors, whereas MSVC's LLP64 (`int64_t` == `long long`) hides it — write `static_cast<std::int64_t>(42)`. The same LP64/LLP64 split also breaks `std::initializer_list<auto>` deduction — a braced range-`for` mixing `unsigned long long` literals with `std::uint64_t` values sees two distinct element types on LP64 (deduction fails on gcc/clang) but one type under LLP64; give the array an explicit `std::uint64_t` element type (`stdlib_test_random.cpp`).
- **clang-cl MSVC-EH catch-funclet codegen traps when a catch destroys a non-trivial temporary *and* throws**: under clang-cl on Windows a `catch` block that both destroys a non-trivial temporary and rethrows/throws emits an `int3` (TrapUnreachable) inside the funclet, surfacing only at runtime as `STATUS_BREAKPOINT` (exit `0x80000003` / `-2147483645`) — e.g. on try/catch-heavy fuzz seeds. Production MSVC `cl.exe` and Linux clang (Itanium EH, no funclets) are unaffected, so it never appears in those builds. Fix by keeping the non-trivial temporary and the throw **out of the funclet**: materialise exception payloads in a normal frame and re-raise *lexically*. The VM `run()` loop now splits `handle_exception` into `[[nodiscard]] bool` overloads (`vm.hpp`/`vm_helpers.cpp`) that build the `std::optional<Value>` payload outside the catch and return `false` when no Luma handler exists, so the caller re-raises with a bare `throw;` (a cross-function rethrow from the helper is *also* mishandled). `path_validator.hpp` moves its construct-and-throw into a `[[noreturn]]` out-of-line helper (`detail::throw_invalid_path`). This is a real codegen bug distinct from the `0xC0000409` `__fastfail` fuzz artifact noted under Testing.
- **Standard exception types need a direct `<stdexcept>` include — the clang-cl fuzz build catches missing transitive includes *on Windows***: any header that names `std::runtime_error`, `std::logic_error`, `std::invalid_argument`, `std::out_of_range`, `std::length_error`, etc. must `#include <stdexcept>` itself. MSVC supplies it transitively so the default preset stays green, but clang-cl's stricter transitive includes do not, breaking the fuzz build (`-DLUMA_BUILD_FUZZ=ON`). The useful corollary: the local **clang-cl fuzz build surfaces missing-transitive-include gaps without an off-Windows build**, so it is a cheaper check than the Linux/clang build the "Build on both before claiming cross-platform" note above implies — treat every header as include-what-you-use for the types it names. Fixed four headers in commit `8aeefa60` (`core/common/url_codec.hpp`, `core/runtime/stdlib/io/http_url_parser.hpp`, `core/runtime/vm/vm.hpp`, `debugger/source/dap_error_handler.hpp`).
- **Between `fork()` and `execvp()` the child may call only async-signal-safe functions — build `argv` *before* the fork**: `execute_command` (`platform_process_posix.cpp`) allocates the `argv` pointer vector before forking because `operator new`/`malloc` is not async-signal-safe. In the multithreaded interpreter (the thread pool runs `Process.run` from worker tasks) another thread can hold the allocator lock at the instant of the fork, which would deadlock the single-threaded child forever. The child inherits the pre-built `argv` at identical addresses via copy-on-write, so the pointers stay valid; it then does only `close`/`dup2`/`execvp`/`_exit`.
- **The first Linux/macOS/multi-distro CI builds surfaced a batch of latent stdlib divergences across the three C standard libraries** that MSVC-only building had hidden. (1) **`timegm`/`_mkgmtime` disagree at the calendar extremes** — glibc accepts the full range, BSD/macOS `timegm` rejects a year-0001 broken-down time (returns −1), Windows `_mkgmtime` rejects negative `time_t`; replaced with a platform-identical `safe_timegm` computed via Howard Hinnant's `days_from_civil` (`platform_time.hpp`), and `tm_to_unix` bounds the result to the documented year 0001–9999 range so `DateTime.add_months`/`add_years` overflow consistently. (2) **`Converter.from_binary`** — glibc's `strtoll` accepts a `0b` prefix (a C23 extension) that MSVC does not, so `parse_in_base` now rejects it explicitly (the standard `0x` hex prefix is left untouched). (3) **`Graph.has_cycle`** iterated an adjacency hash map whose root order differs across stdlibs, so the traversal-depth guard fired only on some platforms → iterate roots in deterministic sorted order (both directed and undirected branches). (4) **`Process.run`** on POSIX now reports an `execvp` failure to the parent via a close-on-exec self-pipe and returns a **negative** exit code (launch failure) to match the Windows `CreateProcessA` path, instead of the child's `_exit(127)` being reaped as a successful run. Feature tests/examples that spawn processes must also stay platform-neutral (`echo`/`exit` are `cmd.exe` built-ins on Windows but need a real binary/`sh -c` on POSIX).
- **POSIX stdio-protocol servers must `signal(SIGPIPE, SIG_IGN)` at `main()` start** (guarded by `!_WIN32`) — done in `luma_dap` and `luma_lsp`. `protocol::StdioTransport::write_message()` throws `ConnectionClosed` when a write to stdout fails (the intended "editor disconnected" path), but on POSIX the default `SIGPIPE` disposition kills the process by signal *before* `fwrite`/`fflush` can report the error, making that catch dead code. This was the root cause of an intermittent `dap_integration_test` stress-test failure on slower CI runners (a late write racing adapter teardown). Windows has no `SIGPIPE`.
- **AddressSanitizer defeats a `static_assert` that reaches a global's address**: ASan instruments every global-variable access, so a global table's address is no longer a core constant expression and GCC rejects e.g. `static_assert(opcode_metadata_matches())` with "is not a constant expression" under `-fsanitize=address`. Guard the compile-time form out (detect via `__SANITIZE_ADDRESS__` or Clang's `__has_feature(address_sanitizer)`) and rely on the equivalent runtime check, which still executes under ASan (`compiler_opcode_test.cpp`).

## Hash & Equality Invariants

- **ValueHash must respect ValueEqual**: Two arrays with equal content are `ValueEqual`, so deep hashing must be content-based, NOT pointer-based. Pointer-based hashing breaks the hash contract. Initial `ValueHash` only hashed the type tag → all arrays/dicts of the same type collided → O(n) lookups. Fix: structural deep-hashing with a depth limit (≤8 levels via `k_max_hash_depth`).
- **Integer/number cross-type hash**: Integers and numbers that compare equal (e.g., `3` and `3.0`) must produce the same hash. Fixed by hashing integers as doubles when they fit without precision loss.
- **Dictionary hash must be order-independent**: Uses XOR combination of key-value pair hashes.

## Refactoring Process Learnings

- **Sub-agent reports can be over-optimistic**: "DONE" reports from sub-agents should be verified. Some items were only superficially touched (comments added, but actual logic not changed). Sub-agents also sometimes apply fixes to wrong files. Always audit sub-agent work.
- **Todo lists may be incomplete**: When decomposing a large refactoring report into SQL todos, ensure all findings are captured. In one session, 20 SQL todos only covered ~1/3 of 60+ report findings.
- **Pre-existing test baselines**: Before refactoring, capture a fresh `ctest` baseline (exact test count + any known failures) so regressions stay distinguishable — don't trust a hardcoded number, the suite count drifts as tests are added. The graphicalui suites (`stdlib_test_graphicalui`, `luma_graphicalui_functions`) need a display and `dap_integration_test` needs loopback networking, so those may be skipped or fail under headless/offline CI.
- **File move strategy**: Create new file at destination, convert old file to thin deprecated redirect (`#include` to new location) — ensures backward compatibility.

## Build Environment

- **Full rebuild takes 5-8 minutes** with `cmake --build build --config Release --parallel`.
- **VS generator ZERO_CHECK race → prefer Ninja Multi-Config**: configuring/building with the default Visual Studio generator (`cmake --preset default`, "Visual Studio 18 2026") can intermittently fail under parallel MSBuild with a `generate.stamp` access-denied error in the ZERO_CHECK target. The root `CMakeLists.txt` now sets `CMAKE_SUPPRESS_REGENERATION ON` for the Visual Studio generator (dropping the in-build regeneration target — re-run `cmake --preset <name>` after editing any `CMakeLists.txt`), and `tests/CMakeLists.txt` replaced its `file(GLOB CONFIGURE_DEPENDS)` feature-test discovery (whose per-build glob-verification stamp amplified the storm into many parallel reconfigures) with explicit sorted lists, so the baseline VS build no longer races. Configuring with `-G "Ninja Multi-Config"` also avoids the race and still produces `build/Release/luma.exe` (matching `run_examples.py` defaults). Ninja needs the MSVC toolchain on PATH — import it via `vcvars64.bat`; since the sync/async shells here are ephemeral, re-import vcvars at the start of each self-contained build command (~3-5 s). Observed toolchain: VS 18 (2026, MSVC 19.51), cmake 4.3.2, clang 22, node 24, cargo 1.95, python 3.11.
- **Tests take ~180-200 seconds** with `ctest -C Release --timeout 60 --output-on-failure`.
- **5 primary CMake targets**: `luma_analysis` (front-end), `luma_core` (runtime), `luma_shared` (shared libs), `luma_lsp` (language server), `luma_dap` (debugger). The two tools also build a testable `*_lib` static library via `luma_add_tool_library`.
- **Fuzz targets require Clang; on Windows use the bundled clang-cl, not MSVC.** VS18's `Launch-VsDevShell.ps1 -VsInstallPath` does NOT establish a usable dev environment — import the toolchain via vcvars instead: `cmd /c "vcvars64.bat >nul 2>&1 && set" | ForEach-Object { if ($_ -match '^([^=]+)=(.*)$') { Set-Item "env:$($matches[1])" $matches[2] } }`, then prepend the bundled LLVM dir (`VC\Tools\Llvm\x64\bin`, provides `clang-cl`) and the Ninja dir to `PATH` before configuring with `-DLUMA_BUILD_FUZZ=ON`.
- **All executables land in the build *root*, not a per-target subdirectory.** The top-level `CMakeLists.txt` sets `CMAKE_RUNTIME_OUTPUT_DIRECTORY = ${CMAKE_BINARY_DIR}`, so fuzz binaries are at `build-fuzz/fuzz_parser.exe`, *not* the `build-fuzz/fuzz/...` path shown in `fuzz/README.md`, `fuzz/CMakeLists.txt`, and `build.instructions.md §7` — those documented paths are misleading on every platform.
- **Windows Defender can quarantine the Release-MSVC `dap_integration_test.exe` as a false positive** (`Trojan:Win32/Wacatac.C!ml`) the moment it is launched. When real-time protection is on and managed by group policy, you can't add an exclusion (no admin → `0x800704ec`). Workaround that survives: build the *same* target in **Debug** config (the different codegen is not flagged), copy that exe over `build\Release\dap_integration_test.exe`, and run it with the Debug CRT + UCRT dirs prepended to `PATH` (`...\VC\Redist\MSVC\<ver>\debug_nonredist\x64\Microsoft.VC<NNN>.DebugCRT` and `...\Windows Kits\10\bin\<ver>\x64\ucrt`). Any later **Release** rebuild re-quarantines it. The RelWithDebInfo clang-cl fuzz exes were *not* flagged — the trigger is specific to the Release MSVC codegen, not the test logic.
