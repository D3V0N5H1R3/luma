# Learnings — Virtual Machine

> **See also:** The compiler produces the bytecode the VM executes — see [learnings-compiler.instructions.md](learnings-compiler.instructions.md) for opcode semantics, the scratch-slot invariant, and optimizer constraints. Concurrency (task_scope, channels) is summarised in the core [learnings.instructions.md](learnings.instructions.md) § Concurrency.

## Architecture & Pipeline

- The VM is stack-based: value stack (max 65,536 entries), call frame stack (max 256 frames), plus a separate exception handler stack for try/catch/finally. VM internals are decomposed via composition: **VMStack** (a fixed `unique_ptr<Value[]>` block addressed by raw `base`/`top`/`limit` pointers plus the call frame vector; O(1) push/pop, never reallocates), **VMGlobalCache** (inline cache for global variable lookups exploiting `std::unordered_map` pointer stability), and a **function pointer dispatch table** (`vm_dispatch_table.cpp`) that maps opcodes to `void (VM::*)()` handler methods — replaces the previous switch-based dispatch for better branch prediction. A narrow **VMStackAPI** seam (`vm_stack_api.hpp`) abstracts the stack/frame/exception operations opcode handlers use, so extracted handlers can be unit-tested against a lightweight mock stack (see `vm_stack_api_test.cpp`); the VM is declared `final`, so the virtual calls devirtualize back to direct calls under optimisation — zero hot-path overhead. Debug-hook callback storage and its `callbacks_mutex` live in a first-class **VMDebugInterface** component (`vm_debug_interface.hpp`, `debug_` member, methods in `vm_debug.cpp`) that owns its own synchronisation — extracted from the former nested `DebugContext` struct as the first staged component of the VM god-class decomposition (`TODO(refactor/V1)`). Task/concurrency state (the `task_scope` LIFO stack, thread pool, task-id counter, and the thread-local current-scope pointer) likewise lives in a first-class **VMTaskManager** component (`vm_task_manager.hpp`, `task_manager_` member) — the second staged extraction. Note the dispatch table's `void (VM::*)()` member-pointer entries force every `op_*()` handler to stay a VM member, so these components own only STATE + helpers that thin `op_*()` members delegate to; the remaining VMCallDispatch/VMCore split is deferred because the call handlers are the execution-engine core (coupled to frames/base_depth_/PC beyond the seam).

## Module Layout & Key Files

- **`VM::handle_get_global` bypasses `Environment::get`**: it resolves names through `VMGlobalCache`, so miss-time behaviour implemented inside `Environment::get` (such as the `SandboxPolicy` access check) does not run on the VM path. Mirror any such behaviour explicitly — the VM reported a bare `undefined variable 'FileSystem.exists'` under `--box` until its miss branch consulted `Environment::sandbox_denial_hint` and raised `SandboxPolicy::access_denied_message`.
- **A qualified `GetGlobal` miss falls back to field access** (`VM::push_global_field_path`): the compiler emits `a.b` as one `GetGlobal "a.b"` whenever `a` is not a local, because it cannot tell a module member (`Math.pi`) from a field of a global. REPL top-level variables are globals, so `p.y` failed with `undefined variable 'p.y'` until the miss path resolved `a` as a global and applied `push_field` for each remaining segment. It runs after the sandbox denial check (so a blocked module member always reports the sandbox message), and only when the root name is itself a global.
- **REPL closures outlive their compile unit**: `FunctionValue::compiled` is a raw pointer into the input's function table, and `MakeClosure` indices are relative to that table. The REPL therefore hands each input's table to `VM::retain_compiled_functions` (stable `unique_ptr` storage, dropped with the VM on `:clear`), and every closure records its `function_table` so a lambda created inside an earlier input's function indexes the right table. Before this, calling a function declared on a previous line read freed bytecode ("bytecode truncated") — hidden only because the type checker had rejected every cross-line reference.
- The VM is split into `vm.cpp` (dispatch loop), `vm_helpers.cpp` (non-inlined helper methods extracted to reduce file size), plus dispatch headers: `vm_dispatch_arithmetic.cpp`, `vm_dispatch_collections.cpp`, `vm_dispatch_control_flow.cpp`, `vm_dispatch_concurrency.cpp`, `vm_dispatch_types.cpp`, `vm_dispatch_table.cpp` (function pointer table). Additional modules: `vm_stack.hpp` (stack + frame storage), `vm_global_cache.hpp` (inline global lookup cache), `vm_introspection.hpp/.cpp` (high-level state access for debuggers — stack trace, locals, upvalues, set_local/set_upvalue), `vm_types.hpp` (`TypeMatcher` class for runtime IS_TYPE / match dispatch — simple, tuple, parameterized, choice/record patterns). Opcode handlers follow two naming conventions: short, simple handlers are defined inline as `op_*` in `vm_dispatch_table.cpp`, while complex handlers are `handle_*` methods in the topical `vm_dispatch_*.cpp` files.
- `CallFrame::code_end` (`vm_stack.hpp`) caches the one-past-the-end pointer into the frame's bytecode chunk, computed once at frame-push time (and refreshed on tail-call, which reassigns `function` in place). `VM::current_code_end()` (`vm.hpp`) reads it directly instead of re-deriving `function->chunk().code.data() + chunk.code.size()` via two pointer chases every time a jump/loop opcode handler needs the frame's code bounds — a hot-path micro-optimisation pinned by `vm_test_core.cpp`.
- **In-place string concatenation** (`vm_dispatch_arithmetic.cpp`): `handle_concatenate`'s fast path uses `a_ref.as_string_mut() += sb` instead of constructing a new `Value{sa + sb}`. Strings are stored directly in the `Value` variant (not behind a `shared_ptr`), so the stack slot uniquely owns its buffer — appending in place reuses existing `std::string` capacity when the left operand's buffer has room, avoiding a reallocation on repeated concatenation (the `O(n²)` buildup case in a loop).
- **`SmallVector<std::uint8_t>` over `std::vector<bool>` for named-arg binding** (`vm_dispatch_control_flow.cpp`, `VM::handle_call_named()`): the per-call "which parameter slots are bound" tracker uses `std::uint8_t`, not `bool`. `SmallVector<T>`'s heap-fallback storage is a plain `std::vector<T>`; with `T = bool` that would silently degrade to the bit-packed `std::vector<bool>` specialisation (proxy references, no small-size optimisation), defeating the whole point of using `SmallVector` to dodge a heap allocation on the common small-arity path. `std::uint8_t` sidesteps the specialisation while keeping the same value-initialised-to-false semantics.
- **Named-arg calls must re-validate required-parameter coverage at the VM, not just at the type checker**: `VM::handle_call_named()` (`vm_dispatch_control_flow.cpp`) tracks which of `[0, arity)` slots were filled by `bind_positional_args`/`bind_named_args` and then calls `require_all_required_args_bound()`, which walks `[0, func.required_arity)` and throws `missing_required_argument` for any unfilled required slot. The type checker rejects a missing required argument at the source level, but debugger expression evaluation compiles without the type checker and a hand-crafted/corrupted `.lumc` can carry an arbitrary named-call arg set — without this VM-side check a missing required parameter silently ran as `none` instead of raising a clear runtime error. `VM::call_function` (`vm_helpers.cpp`) has the analogous `arg_count < required_arity` guard on the *positional*-call path, and `handle_tail_call` has it too — a tail call used to skip the check.

## Stack, Frames & Error Handling

- **Lower the stack top only through `VMStack::truncate_to`** (or `pop()`). It destroys every value above the new top. Merely moving `top` down left values alive until the slot was overwritten: a returned function's socket stayed open, and the extra reference counts forced needless copy-on-write copies. Return, exception unwinding, tail calls, the native-callback error path, string interpolation, and the `@test` reset all use it.
- **The 65,536-slot stack block is pooled per thread** (up to 2 spare blocks; `VMStack::acquire_storage`/`release_storage`). Every `spawn` constructs a task VM, and allocating and value-initialising a fresh ~3 MiB stack per spawn dominated the cost of `spawn`. A recycled block holds only empty or moved-from values, so it needs no re-initialisation.
- **`CallFrame` holds raw pointers**: `const CompiledFunction*` and `FunctionValue* closure` (the callee value in slot 0 keeps it alive), plus `ip`, `code_end`, `slot_offset`, and the lazily resolved `global_bindings`. There is no `slots` pointer; locals are `stack_.base[slot_offset + slot]`.
- **A returning or tail-calling frame drops its exception handlers** (`discard_frames_from`), and `handle_exception` validates a handler before using it (`is_valid_handler`: live frame, stack and task-scope depths not above the current ones, catch IP inside that frame's code). A stale handler from crafted `.lumc` bytecode could otherwise install its catch IP into an unrelated frame. `ExceptionHandler` also records `task_scope_depth`, so unwinding to it retires the task scopes opened inside the `try`.
- **Integer overflow raises; it never promotes.** `+ - *`, `Increment`/`Decrement` (and the `*Local` forms), and `Negate` raise `integer overflow in addition` / `subtraction` / `multiplication` / `increment` / `decrement` / `negation`. `/` always yields a `number` and raises `number overflow in division` when finite operands overflow to infinity; wrong operand types give `cannot divide 'T' and 'U'` (`%`: `cannot take the remainder of …`). `%` is truncating (sign of the dividend), `//` floors.
- **Call depth is `min(ResourceLimits::max_call_depth, VMStack::k_frame_max)`** (`effective_max_call_depth`), enforced by `validate_call_depth()` on every frame-pushing path. Raising `LUMA_LIMIT_MAX_CALL_DEPTH` above 256 used to bypass the frame cap.
- The default `assert` message is `assertion failed` (lower-case), matching the manual.

## Concurrency

- **`run()` retires the task scopes it opened** on every non-normal exit — see the Concurrency section of [learnings.instructions.md](learnings.instructions.md) for the per-task cancellation token tree, cancellation points, fail-fast join, pool compensation, and the read-only task global snapshot.
- **Every blocking wait in VM or stdlib code that can run on a pool worker must hold a `ThreadPool::BlockingRegion`** for its duration (await, scope join, blocking `Channel`/`Task` waits). Without it, the pool cannot see that its workers are blocked and will not start a compensating worker.
- **A task VM must not write the global environment.** `handle_set_global` calls `reject_global_write_in_task`; the snapshot is shared read-only by sibling tasks. `spawn_environment()` rebuilds the user-globals layer only when `globals_version_` changes and then re-copies only bindings whose `Binding::write_version` differs from their cached copy, so any new code path in the root VM that writes a global must bump `globals_version_` **and** stamp the binding's `write_version` (writes through `Environment::set` mark it `k_unversioned`, i.e. always re-copied). Re-copying every user global on each post-write spawn made a 300-spawn loop with one global write ~30× slower when a large global array existed. The test harness layers program globals over a shared stdlib scope, so the snapshot is built per scope of the chain — a fast path only for a root environment would leave every C++ test on the slow path.
- **A task's own cancellation skips `catch` but runs `finally`.** `TryCatch` carries no catch/finally flag, so `is_cleanup_handler()` (`vm_exception_handler.cpp`) recognises a `finally` handler from its code: a normal-control-flow walk from `catch_ip` (never another handler's exception edge) that reaches `Rethrow` with only the handler's own error value on the stack. `handle_cancellation` gives such a handler `none` (the cancellation marker — ordinary errors always bind a string) so `op_rethrow` re-raises `CancelledException`; before, `Rethrow` turned the cancellation into a `RuntimeError` and the whole `task_scope` failed. A `finally` entered while the task is cancelled runs under a **cancellation shield** (`VMExceptionManager`) so its calls and loops do not abort it; shields end at its `Rethrow`, when its frame returns or tail-calls (`discard_frames_from`), or when an error unwinds past it. A cancellation observed from another task (`await` of a cancelled task) stays catchable.
- **A task that fails while its token is cancelled completes as cancelled** (`build_spawn_future`), classified at completion rather than at join time so a later `Task.cancel` cannot hide a genuine failure. Tests of a cancellation point must therefore observe *where* the task stopped (e.g. report its counter from a `finally`): a loop that ran into the iteration limit after `Task.cancel` also ends "cancelled".
- **Thread-local `VMTaskManager::current_scope` belongs to the thread, not the VM.** A spawned task clears it on entry and restores the worker's previous value on exit; `~VM` touches it only if the VM still owns open scopes.
