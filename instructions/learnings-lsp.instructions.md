# Learnings — Language Server

## Language Server (LSP)

- Standalone binary (`luma_lsp`) communicating via JSON-RPC 2.0 over stdio.
- Reuses interpreter pipeline (lexer, parser, type checker) — no runtime/VM.
- 27 LSP features including diagnostics, hover, completions, signature help, go-to-definition, references, rename, semantic tokens, code actions, code lens, formatting, folding, inlay hints, call/type hierarchy, linked editing.
- Incremental document sync (advertises `TextDocumentSyncKind.Incremental`): ranged edits are applied in place, with full-text replacement as a fallback when a change omits a range. Re-analysis is still full per change, with incremental red-green tree updates for efficiency.
- Source split across 50+ files in `language-server/source/`.
- **AnalysisService** (`lsp_analysis_service_impl.hpp`): Concrete implementation owning the full analysis pipeline (lex → parse → include → symbol collection → type-check → lint). Cancellation-aware with configurable deadlines. Accepts callbacks for logging and notifications — decoupled from server concerns.
- **AnalysisResult** (`lsp_analysis_result.hpp`): Cached analysis output with rich indexing — token index (sorted by line/col), function body ranges (binary searchable), identifier index (reverse lookup), scoped locals (block-level scope tracking), call graph (caller→callee sets). Function body ranges stored twice (map + sorted vector) for O(log n) enclosing-function lookup.
- **WorkspaceManager** (`lsp_workspace_manager.hpp`): Owns workspace roots, persisted index, and project configuration. Manages indexing state.
- **ConfigurationManager** (`lsp_configuration_manager.hpp`): Owns LSP settings and client capabilities. Isolated from server logic.
- **WorkspaceIndexer** (`lsp_workspace_indexer.hpp`): Recursive workspace file discovery with max file limit (500). Stateless scanner.
- **PersistedIndex** (`lsp_persisted_index.hpp`): Binary-serialized workspace symbol cache for fast incremental startup. Content hash validation for staleness detection.
- **DiagnosticBuilder** (`lsp_diagnostic_builder.hpp`): Converts internal diagnostics to LSP format with UTF-16 code unit conversion and documentation URL generation.
- **IncludeProcessor** (`lsp_include_processor.hpp`): Handles the include phase with batch pre-reading (each file read from disk at most once).
- **SymbolResolver** (`lsp_symbol_resolver.hpp`): Unified symbol resolution for hover, go-to-definition, rename, references, completion. Scope-aware lookup (enclosing function locals → globals), binary search for enclosing function, cross-file resolution.
- **TokenUtils** (`lsp_token_utils.hpp`): Coordinate conversion between Luma's 1-based source locations and LSP's 0-based Position/Range. Namespace-qualified name extraction by looking backward for "Namespace.identifier" pattern.
- **LSP Types** (`lsp_types.hpp`): Protocol types (Position, Range, Location, Diagnostic) with LSP-aligned constants. Error codes are strings (e.g., "E0006"). Position is 0-based per LSP spec.
- **Columns are codepoint-based, never byte-based**: Luma source columns and LSP `character` positions both count Unicode codepoints, so a lexeme's display width is its codepoint length — *never* `lexeme.size()`/`name.size()` (bytes). Using byte length for any lexeme containing multi-byte UTF-8 (string literals, non-ASCII identifiers) yields wrong hover/definition/rename ranges and edit corruption. Use `lexeme_column_width()` (`lsp_token_utils.hpp`), which delegates to the shared `luma::utf8_codepoint_count()` (`core/common/utf8.hpp`); it is the correct tool at every column computation across the LSP (~18 call sites in 9 files). Diagnostic `SourceLocation` columns are codepoint indices too, so mapping a Luma diagnostic to an LSP range goes codepoint-col → byte-offset (`codepoint_col_to_byte_offset`) → UTF-16 (`byte_offset_to_utf16_column`) in `lsp_diagnostic_builder.cpp`; it previously treated the column as a byte offset, corrupting ranges on any line with multi-byte UTF-8 before the diagnostic, and `word_end_column` similarly walks codepoints and counts bytes ≥ 0x80 as identifier characters.
- **Stored symbol definition `location`s are anchored at the leading declaration *keyword* (`function`/`record`/`choice`/`interface`/type alias), not the name.** Building an LSP range straight from `location` + `name.size()` (or `lexeme_column_width(name)`) covered the keyword/return-type region, and for `includeDeclaration=false` references the declaration-site exclusion *never* matched. Use `find_declaration_name_range(tokens, decl_loc, name)` (`lsp_token_utils.hpp`), which scans forward from the keyword location for the actual name token (reducing a qualified `Ns.func` key to its bare member via `qualified_member`) and returns a codepoint-safe range. Applied across document symbols, call/type hierarchy, go-to-type-definition/implementation, code lens, and the references declaration exclusion (`lsp_identifier_collector.cpp`).
- **Rename/references occurrence filtering must reject same-lexeme tokens that bind to a *different* symbol** (`collect_scoped_occurrences`, `lsp_identifier_collector.cpp`): for an *unqualified* target, an occurrence preceded by `Identifier Dot` (a receiver, e.g. the `value` in `point.value`) is a member/field access and is skipped; for a *global* target, occurrences shadowed by a local or parameter in their own function scope (via `ScopeStack::find_symbol` returning a `Block`/`Function` origin) are skipped. Otherwise renaming a global rewrites unrelated fields and shadowing locals.
- **Completion is suppressed inside string literals and comments** (`classify_cursor_context` in `lsp_server_completion.cpp`, reusing the shared `lexical::LineContext` forward scanner from `lsp_lexical_context.hpp`), except `include "..."` path completion which legitimately lives in a string; a `${...}` interpolation counts as code so completion still fires there. After a *foreground* debounced re-analysis commits, the server sends a param-less global `workspace/semanticTokens/refresh` so the client re-pulls fresh tokens and drops highlighting held from the debounce window (foreground-only, to avoid spamming during background indexing). Rename validates the new name with the shared `util::is_valid_identifier` (`lsp_string_utils.hpp`), which accepts UTF-8 multibyte bytes (≥ 0x80) so Unicode identifiers (`café`, `π`, `名前`) are legal, mirroring the lexer.
- **Path-containment checks compare by path *components*, not string prefix**: `collect_include_completions` (`lsp_completion_strategy.cpp`) rejects a search dir that escapes the base via `canonical_search.lexically_relative(canonical_base)`, testing whether the relative path is empty or its first component is `..`. A raw `starts_with(base)` string test wrongly admits a sibling that merely shares a character prefix (base `/p/proj` vs `/p/proj-secret`).
