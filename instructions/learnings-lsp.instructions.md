# Learnings — Language Server

> **See also:** The LSP reuses the interpreter front-end (lexer → type checker) — bugs may root-cause to `core/analysis/`. See the core [learnings.instructions.md](learnings.instructions.md) § Architecture & Pipeline. The shared protocol transport is documented in [learnings-dap.instructions.md](learnings-dap.instructions.md) (same `shared/protocol/` layer).

## Language Server (LSP)

- Standalone binary (`luma_lsp`) communicating via JSON-RPC 2.0 over stdio.
- Reuses interpreter pipeline (lexer, parser, type checker) — no runtime/VM.
- Core LSP features including diagnostics, hover, completions (+resolve), signature help, go-to-definition, go-to type-definition, go-to implementation, references, rename (+prepareRename), document symbols, full semantic tokens, quick-fix code actions, document formatting, folding, and document links.
- Incremental document sync (advertises `TextDocumentSyncKind.Incremental`): ranged edits are applied in place, with full-text replacement as a fallback when a change omits a range. Re-analysis is still full per change, with incremental red-green tree updates for efficiency.
- Source split across 50+ files in `language-server/source/`.
- **AnalysisService** (`lsp_analysis_service_impl.hpp`): Concrete implementation owning the full analysis pipeline (lex → parse → include → symbol collection → type-check → lint). Cancellation-aware with configurable deadlines. Accepts callbacks for logging and notifications — decoupled from server concerns.
- **AnalysisResult** (`lsp_analysis_result.hpp`): Cached analysis output with rich indexing — token index (sorted by line/col), function body ranges (binary searchable), identifier index (reverse lookup), scoped locals (block-level scope tracking). Function body ranges stored twice (map + sorted vector) for O(log n) enclosing-function lookup.
- **WorkspaceManager** (`lsp_workspace_manager.hpp`): Owns workspace roots and project configuration (`luma.json` discovery/apply), and answers `is_in_workspace()` path-containment queries (case-insensitive on Windows) used by watched-file handling.
- **ConfigurationManager** (`lsp_configuration_manager.hpp`): Owns LSP settings and client capabilities. Isolated from server logic.
- **DiagnosticBuilder** (`lsp_diagnostic_builder.hpp`): Converts internal diagnostics to LSP format with UTF-16 code unit conversion and documentation URL generation.
- **IncludeProcessor** (`lsp_include_processor.hpp`): Handles the include phase with batch pre-reading (each file read from disk at most once).
- **SymbolResolver** (`lsp_symbol_resolver.hpp`): Unified symbol resolution for hover, go-to-definition, rename, references, completion. Scope-aware lookup (enclosing function locals → globals), binary search for enclosing function, cross-file resolution.
- **TokenUtils** (`lsp_token_utils.hpp`): Coordinate conversion between Luma's 1-based source locations and LSP's 0-based Position/Range. Namespace-qualified name extraction by looking backward for "Namespace.identifier" pattern.
- **LSP Types** (`lsp_types.hpp`): Protocol types (Position, Range, Location, Diagnostic) with LSP-aligned constants. Error codes are strings (e.g., "E0006"). Position is 0-based per LSP spec.
- **Columns are codepoint-based internally, never byte-based**: Luma source columns count Unicode codepoints, and the server keeps every token/range in codepoint columns, converting to the client's UTF-16 `character` positions only at the protocol boundary (`PositionEncoder`, `AnalysisResult::to_wire`/`to_codepoint_col`). A lexeme's display width is therefore its codepoint length — *never* `lexeme.size()`/`name.size()` (bytes). Using byte length for any lexeme containing multi-byte UTF-8 (string literals, non-ASCII identifiers) yields wrong hover/definition/rename ranges and edit corruption. Use `lexeme_column_width()` (`lsp_token_utils.hpp`), which delegates to the shared `luma::utf8_codepoint_count()` (`core/common/utf8.hpp`); it is the correct tool at every column computation across the LSP (~18 call sites in 9 files). Diagnostic `SourceLocation` columns are codepoint indices too, so mapping a Luma diagnostic to an LSP range goes codepoint-col → byte-offset (`codepoint_col_to_byte_offset`) → UTF-16 (`byte_offset_to_utf16_column`) in `lsp_diagnostic_builder.cpp`; it previously treated the column as a byte offset, corrupting ranges on any line with multi-byte UTF-8 before the diagnostic, and `word_end_column` similarly walks codepoints and counts bytes ≥ 0x80 as identifier characters.
- **Stored symbol definition `location`s are anchored at the leading declaration *keyword* (`function`/`record`/`choice`/`interface`/type alias), not the name.** Building an LSP range straight from `location` + `name.size()` (or `lexeme_column_width(name)`) covered the keyword/return-type region, and for `includeDeclaration=false` references the declaration-site exclusion *never* matched. Use `find_declaration_name_range(tokens, decl_loc, name)` (`lsp_token_utils.hpp`), which scans forward from the keyword location for the actual name token (reducing a qualified `Ns.func` key to its bare member via `qualified_member`) and returns a codepoint-safe range. Applied across document symbols, go-to-type-definition/implementation, and the references declaration exclusion (`lsp_identifier_collector.cpp`).
- **Rename/references occurrence filtering must reject same-lexeme tokens that bind to a *different* symbol** (`collect_scoped_occurrences`, `lsp_identifier_collector.cpp`): for an *unqualified* target, an occurrence preceded by `Identifier Dot` (a receiver, e.g. the `value` in `point.value`) is a member/field access and is skipped; for a *global* target, occurrences shadowed by a local or parameter in their own function scope (via `ScopeStack::find_symbol` returning a `Block`/`Function` origin) are skipped. Otherwise renaming a global rewrites unrelated fields and shadowing locals.
- **Completion is suppressed inside string literals and comments** (`classify_cursor_context` in `lsp_server_completion.cpp`, reusing the shared `lexical::LineContext` forward scanner from `lsp_lexical_context.hpp`), except `include "..."` path completion which legitimately lives in a string; a `${...}` interpolation counts as code so completion still fires there. After a *foreground* debounced re-analysis commits, the server sends a param-less global `workspace/semanticTokens/refresh` so the client re-pulls fresh tokens and drops highlighting held from the debounce window (foreground-only, to avoid spamming during background indexing). Rename validates the new name with the shared `util::is_valid_identifier` (`lsp_string_utils.hpp`), which accepts UTF-8 multibyte bytes (≥ 0x80) so Unicode identifiers (`café`, `π`, `名前`) are legal, mirroring the lexer.
- **Path-containment checks compare by path *components*, not string prefix**: `collect_include_completions` (`lsp_completion_strategy.cpp`) rejects a search dir that escapes the base via `canonical_search.lexically_relative(canonical_base)`, testing whether the relative path is empty or its first component is `..`. A raw `starts_with(base)` string test wrongly admits a sibling that merely shares a character prefix (base `/p/proj` vs `/p/proj-secret`).
- **`Token.location` for the `include` keyword records the column *past* its last character**, per `Lexer::add_token`'s post-scan stamping — so an include diagnostic squiggle built from `inc.location.column - 1` as if it pointed at the path string was off by the width of the separating space plus the keyword itself, underlining the `include` keyword and its trailing space instead of the quoted path. Fixed by deriving `path_start`/`path_end` explicitly: `keyword_end = inc.location.column - 1` is the 0-based column right after `include`, `path_start = keyword_end + 1` skips the single mandatory space to the opening quote, and `path_end = path_start + path_width + 2` spans the path (already UTF-16-width-converted via `byte_offset_to_utf16_column`) plus both surrounding quote characters.
- **`find_comment_start_on_line` (`lsp_lexical_context.hpp`) must special-case triple-quoted strings (`"""`) before its per-character `in_str` toggle**, or the scanner misreads a `"""..."""` literal's *interior* double-quotes as three separate open/close events, desynchronising in/out-of-string state for the rest of the line and letting a `#` inside the literal be misidentified as a comment start. `skip_triple_quoted_string_forward` jumps straight from the opening `"""` to just past the matching closing `"""` (or to `line_end` if unterminated on this line — multi-line triple-quoted strings are handled by the caller's outer per-line loop) whenever a `"""` is seen while *not* already inside a regular string.
- **`ParameterInformation.label` offsets in `textDocument/signatureHelp` are UTF-16 code units (LSP §3.17), not the UTF-8 byte offsets `std::string::find()`/`::size()` produce** — `build_parameter_labels` (`lsp_signature_label.hpp`) locates each parameter substring within the signature label via `std::string::find`, then converts *both* the start and end byte offsets through `byte_offset_to_utf16_column` before emitting the `[start, end]` pair. Skipping the conversion mis-highlights the active parameter for any signature containing a non-ASCII type or parameter name preceding it. Falls back to a plain-text `label` string if the parameter substring isn't found (e.g. it was renamed/reformatted between the raw signature text and its rendered label).
- **Rename-conflict detection must exclude the no-op case before querying scope maps**: `has_rename_conflict` (`lsp_server_rename.cpp`, declared in `lsp_rename_handler.hpp` for direct unit testing) takes the symbol's pre-rename `target_name` and returns `false` immediately when `new_name == target_name`. The function/locals maps it queries necessarily already contain `target_name` (it names the very symbol being renamed), so without the early exclusion every no-op rename request was misreported as a self-collision.
- **Scope ends come from brace matching, never from statement start lines**: AST statements carry only their *start* location, so "last statement's line + 1" truncated any function or block whose last statement is a multi-line `if`/`for`/`match` — local rename then missed the later uses, or (cursor past the truncated range) found no enclosing function and renamed same-named locals file-wide. `symbol_phase` now builds `FunctionStructure::block_spans` (every matched `{`…`}` of the current file, sorted by opening brace) and `block_end_line()`/`declaration_body_block()` (`lsp_analysis_service_symbols.cpp`) take scope ends from the innermost enclosing span; the old guess remains only as the fallback for unclosed braces. Declarations merged in from included files (`location.file_id != 0`) get no `function_body_ranges` entry — their lines belong to another file and used to shadow this file's functions in `find_enclosing_function`.
- **Namespace members are reached only qualified or through `use` — even inside their own namespace**: verified with `luma`, a bare `area(r)` inside `namespace Geo { … }` is `undefined variable 'area'` (or binds to a top-level `area`), exactly as the User Manual's "Bare Names Require `use`" states. So occurrences of `Geo.area` are `Geo.area` anywhere, the member's own *declaration name* (recorded in `SymbolTable::namespace_member_names` by position), and bare names imported with `use Geo` / `use Geo.area` (`SymbolTable::imported_names`, mirroring `TypeChecker::register_use_declaration`: a wildcard import skips names a top-level symbol already defines). `unqualified_binding_namespace()` / `target_namespace_prefix()` (`lsp_identifier_collector.hpp`) give rename/references the target's namespace from any of those tokens. Do not bind bare uses by "line is inside the namespace block" — that renamed calls that refer to the top-level function.
- **Go-to-definition resolves scoped locals first, by binding site**: locals and parameters carry no stored declaration location and `function_locals` is not position-aware, so `DefinitionResolver::try_resolve_scoped_local` walks back from the cursor to the last *binding occurrence* (`is_binding_occurrence()` in `lsp_token_utils.hpp`: `<type> name =`, `(<type> name, …)`, `for`/`catch`/`case` bindings) whose block is still open. With no binding before the cursor — a call to a top-level `value()` made before a local `value` is declared — it returns nothing so the top-level lookup runs. Taking the *first* occurrence in the function resolved such a call to itself.
- **Build filesystem paths from UTF-8 with `utf8_path()` / render with `path_to_utf8()`** (`lsp_path_utils.hpp`). Every path the server holds as text (decoded from a URI, written in an include) is UTF-8, while MSVC's `std::filesystem::path{std::string}` and `path::string()` use the ANSI code page — so every include under a non-ASCII folder (`C:\Users\José\…`) was reported "not found". The same applies to `std::ifstream` opened with a `std::string`.
- **`lexical::LineContext` is a mode stack** (string / `${…}` with its brace depth), consumed by both the formatter and completion's cursor classification. The old flat counter raised the depth twice for `${` and never returned to code after `}`, so the formatter rewrote operators inside later strings and comments (`"${lo}..${hi}"` → `"${lo} .. ${hi}"`); quote escapes are decided by backslash *parity* (`"\\"` closes the string). `update()` consumes every string/interpolation character, so the formatter's operator rules see only plain code.
- **Semantic tokens**: a multi-line token (triple-quoted string) is emitted once per line (the client does not negotiate `multilineTokenSupport`); the literal segments of an interpolated string (`StringStart`/`StringMiddle`/`StringEnd`) are `string`; `void` and the demoted type identifiers (`set`, `queue`, …) are `type` only in a type position (`in_type_position`: not after `.`, and before `<`/a name or after `<`/`->` — the encoder passes each token's neighbours) and when the document declares no variable of that name, because they are also valid field and argument names (`job.task`); `true`/`false`/`none`/`success`/`failure`/`some` are deliberately *not* tokenised so they keep the grammar's `constant.language`/`support.function.builtin` scopes (see `Luma_Syntax_Highlighting.md` §4). An empty token list is a valid cache hit.
- **Lifecycle requests go through the same error handling as features** (`LspServer::respond`): `initialize` is accepted once (a second gets `InvalidRequest`), every other request — `shutdown` included — gets `ServerNotInitialized` until `initialize` succeeded, and a throwing `initialize` now answers with an error instead of nothing. `dispatch_message` answers envelopes without a string `method` with `InvalidRequest` but ignores responses to server-initiated requests (`result`/`error`, no `method`).
- **Whole-document edits must end at the real document end**: `{line_count, utf16_length(last_line)}`, not `{line_count + 1, 0}` — a position past the end is invalid and strict clients reject the formatting edit.
- **The E0006 "Add 'mutable'" fix must insert before the *type***: Luma declares variables type-first (`mutable integer x = 0`); `name:` only occurs in named arguments and generic bounds. `mutable_insertion_position()` (`lsp_quickfix_handler.hpp`) walks back from the nearest `<type> name =` declaration over one type annotation (bounded by the line start via `Token::preceded_by_newline`).
- **Most LSP test fixtures historically used non-Luma syntax** (`function f(a: T) -> R`, `function main()`), so those tests ran on parse-error ASTs and several assertions passed vacuously. Write new LSP tests with valid Luma and prefer the deterministic `LspAnalysisService::analyze()` fixture (`lsp_test_analysis_service.cpp`) over session tests, whose analysis timing races the request.
- **`lsp_builders::try_resolve` must test each resolver's own result**: the fold `(result.empty() && (result = r(), true)) || …` is true after the *first* resolver whatever it returned, so hover never reached the user-symbol resolvers — hover on functions, variables, parameters, records, choices, interfaces and namespaces was always empty. With the chain live, resolver *order* matters (`resolve_hover_text`, `lsp_hover_handler.hpp`): the member after a dot (`p.x`, `Geo.area`) is resolved by the dot-access resolvers *only* — the plain-identifier ones would describe an unrelated local or top-level symbol with the same name — and plain identifiers go innermost scope first (parameter, function local, then top-level), with module-level variables last because declarations also resolve as "variables" (a record `Point` has type `"record"`).
- **Show user code in Luma syntax**: hover text is a ```` ```luma ```` block, so signatures are `function integer add(integer a, integer b)` (built by `build_function_signature`), variables `mutable integer total`, fields `number x` — never the `name: type` / `-> R` forms. Stdlib signatures keep the catalog's own format.
- **Type-only completion fires only where nothing but a type can appear**: after `function ` (return type), at a parameter's type in a declaration's parameter list, after `mutable `, inside a generic type's `<…>`, and after a generic bound's `:`. A statement start may begin an expression, and `name: |` is a named argument's *value*, so neither is a type position. The `<` trigger requires a generic *type* head (built-in generic, `downcast`, or PascalCase) — a bare `\w+<` also matched a comparison typed as `i<n` and replaced every variable completion with type names.
