# Learnings — Debug Adapter

> **See also:** The debugger hooks into the VM — see [learnings-vm.instructions.md](learnings-vm.instructions.md) for VMDebugInterface and hook installation. Expression evaluation compiles Luma source — see [learnings-compiler.instructions.md](learnings-compiler.instructions.md). The shared protocol transport serves both DAP and LSP.

## Debugger (DAP)

- Standalone binary (`luma_dap`) implementing Debug Adapter Protocol over Content-Length framed JSON via stdio.
- Two-thread design: protocol I/O thread + VM execution thread. Shared state is mutex-protected.
- Supports breakpoints (line, conditional, hit count), stepping (over, into, out), stack trace, scope/variable inspection, expression evaluation, concurrent debugging (task → DAP thread mapping).
- Non-goals (`Luma_Debugger.md` §3): memory/performance profiling, and language-server integration.
- **DebugSession** (`debug_session.hpp`): Top-level orchestrator delegating to extracted focused managers. SessionState uses atomic enum (`Idle`, `Running`, `Terminated`) instead of separate booleans — eliminates race windows. Documented lock ordering: (1) thread_states_mutex_→ (2) ThreadState::mutex → (3) config_mutex_→ leaf: exception_mutex_.
- **DebugExecutionEngine** (`debug_execution_engine.hpp`): Owns the execution lifecycle — program launch, VM creation, hook installation, execution control (continue, step, pause), and exception handling coordination. Split into `debug_execution_control.cpp` (control logic), `debug_execution_hooks.cpp` (VM hook installation), and `debug_execution_lifecycle.cpp` (lifecycle management). Configuration phase synchronization (waits for configurationDone).
- **ThreadStateManager** (`thread_state_manager.hpp`): Per-thread debugging state registry with RAII guards. Thread registration, lookup, paused-thread counter with condition variable signaling, force-unpause for terminate.
- **BreakpointManager** (`breakpoint_manager.hpp`): Single-class consolidation of breakpoint logic (line, exception filters) with one mutex. Two phases: `set_breakpoints()` creates pending entries, `resolve_pending_breakpoints()` called after compilation. Line breakpoint logic lives in the focused source file `line_breakpoint_manager.cpp`. Atomic flags for exception filter state (lock-free).
- **CompiledBreakpoint** (`compiled_breakpoint.hpp`): Compiles and validates breakpoint condition expressions and log-message templates to bytecode at creation time, surfacing syntax errors early and caching the compiled artefacts. It does **not** evaluate at runtime — condition evaluation runs in `DebugExecutionEngine` against the live paused frame (so it can resolve frame locals, which a standalone compiled function cannot).
- **VariableInspector** (`variable_inspector.hpp`): Owns variable reference registry using **generational entries** — `GenerationalEntry<T>` pairs value + generation counter. `invalidate_refs()` increments generation for O(1) invalidation instead of clearing maps. Scope types: Local(1), Global(2), Closure(3). Max expansion depth: 32.
- **ExpressionEvaluator** (`expression_evaluator.hpp`): Evaluates expressions in paused VM context with strategy chain: (1) direct local lookup → (2) closure upvalue lookup → (3) global env lookup → (4) scratch-VM compilation & execution (cached) — compiles `function boolean __bp_eval__() { return <expr> }` via `compile_expression_direct` (type checker bypassed; the return type is cosmetic) and runs it through `VM::execute_function`, which **returns** the expression's `Value`. Decoupled from VariableInspector via `RefAllocator` callback. Configurable timeout (default 5s).
- **ExpressionCompiler** (`expression_compiler.hpp`): Shared compilation utility (Lexer → Parser → Compiler) used by expression evaluator, compiled breakpoints, and logpoints.
- **VmHookRegistry** (`vm_hook_registry.hpp`): Installs debug hooks on VM instances and connects them back to the session.
- **DapSessionTypes** (`dap_session_types.hpp`): Shared vocabulary types (SessionState enum, ThreadState struct) extracted to eliminate circular dependencies.
- **DAP Helpers** (`dap_helpers.hpp`): Type-safe JSON field extraction with defaults, `narrow_int()` narrowing with overflow checking (from `core/common/narrow_int.hpp`), `format_error_message()` for consistent error formatting, specialized parsers for launch config and breakpoint requests. Thread ID defaults to 1 (main thread).
- **Invoke session-terminating callbacks *after* releasing the transport send mutex, and exactly once regardless of which of three paths detects disconnection**: `DapProtocolHandler::send_response`/`send_event` hold `send_mutex_` while writing; on a broken pipe they must only *set* the `disconnected_` flag, never call the callback directly, because `send_event` may run on the execution thread and the callback joins that same thread (self-join deadlock). `signal_disconnect()` (external request) and `run()`'s message loop exiting (read failure/EOF, callback not yet invoked) are the other two triggers. All three funnel through `invoke_disconnect_callback_once()`, guarded by a separate `std::atomic<bool> callback_invoked_` compare-exchange — `run()` unconditionally calls it right before returning, so a broken-pipe write during an event send (flag set, callback deferred) still gets its callback fired once the loop notices and exits, and a `signal_disconnect()` that already fired it is a no-op.
- **Evaluate synthesized Luma by returning a value, not by scraping `print`**: `ExpressionEvaluator::evaluate_on_scratch_vm` compiles `function boolean __bp_eval__() { return <expr> }` via `compile_expression_direct` and reads the `Value` that `VM::execute_function` returns. The previous design wrapped the expression as `@main function void main() { let __val = … print(__val) }` and scraped a stubbed `print()` argument; built on non-existent syntax (the `let __val` binding, plus an earlier `function …() -> <expr>` declaration form — see Luma Language Conventions), it failed to parse / threw a non-`std::exception` out of the scratch VM (caught only by `catch(...)` under `/EHsc`) for any compound expression like `1 + 1`. It survived because **no test ever compiled a representative wrapper** — a consistency check's `luma --check` (exit 3) finally caught it. Any path that synthesizes source to feed back through the compiler needs a test that compiles **and runs** one real example (`dap_integration_test.cpp::test_evaluate_compound_expression`, `dap_test_compiled_cache.cpp`).
- **A conditional breakpoint counts as *hit* only when its condition holds** (DAP semantics), so `BreakpointManager::check_breakpoint` runs in four phases for **every** breakpoint bound to the line: (1) snapshot the matches *without* recording a hit (`line_mgr_.find_matching_breakpoints`), (2) evaluate each condition against the live paused frame **outside** the leaf `ctx_.mutex`, (3) record the qualifying hit only when the condition held (`record_breakpoint_hit`, non-const) and read back the updated count, (4) gate the `hitCondition` on that condition-true count. It must not return at the first qualifier: every qualifying logpoint logs (`log_messages`), and the line stops if any qualifier is not a logpoint — returning early let a logpoint hide a real breakpoint on the same line. Recording the hit before checking the condition would make `hitCondition` count condition-false passes. The breakpoint can be removed by a concurrent `setBreakpoints` between phases 1 and 3 — a phase-3 miss means *don't break*.
- **Multiple distinct source-line breakpoints can legitimately snap to the same executable line, so `LineBreakpointManager` stores one-to-many per line** — `map<int, vector<LineBreakpointInfo>>`, not one entry per executable line. Two `setBreakpoints` requests on adjacent non-executable lines that both `snap_line`-forward to the same executable line each keep their own condition/hit-count (a runtime hit evaluates *every* breakpoint bound at that line) instead of the second silently overwriting the first. The id/hit-count carry-over on re-`setBreakpoints` matches one prior entry by identical condition fields and then *consumes* it (erases from the bucket), so a byte-identical duplicate request gets a fresh id rather than aliasing the same counter.
- **Named-collection expansion honours DAP `start`/`count` paging, not just indexed collections:** the dictionary/record/choice expanders and `get_scope_variables` in `value_expander.cpp` now thread `start`/`count` and slice through the same `compute_window()` helper that `get_indexed_variables` uses (arrays/queues/stacks/sets/tuples); the `ScopeRef` branch in `variable_inspector.cpp` passes the window into `get_scope_variables`, so a paging-capable client's windowed request over a large dictionary/record/choice/scope returns only that window.
- **DAP `setVariable` coerces the edit to the target's *existing* type** rather than inferring one from the input text: `VariableInspector::set_variable` reads the current value (`read_scope_value`) and runs `parse_value_typed(str, current)`, which parses to the current value's type or returns `nullopt` to reject a type-changing edit with a DAP error. String targets always succeed (surrounding quotes optionally stripped); complex/null targets are rejected because they can't be reconstructed from a plain string. Prevents a `boolean`/`integer` slot being silently overwritten with a different primitive.
- **The scratch-VM expression evaluator enforces its timeout *during* execution, not just after**: `evaluate_on_scratch_vm` installs a per-line debug hook that aborts once the deadline passes (returning `true` arms a pause whose callback returns `false` to terminate); it previously only *measured* elapsed time afterwards, so a non-terminating watch/condition/logpoint hung the calling DAP thread forever, freezing request handling or the debuggee. The `std::atomic<bool> timed_out` flag is declared *before* the scratch `VM` so it outlives the hook that captures it by reference (locals destroy in reverse declaration order). The VM's global runaway-loop guard (`ResourceLimits::max_while_iterations`) can trip *before* the cooperative deadline on a fast host; both mean non-termination, so the runaway `RuntimeError` — matched via the shared `vm_errors::loop_exceeded_max_iterations(...)` generator to stay in step with the VM — is reported identically to a deadline abort. The scratch env also copies the program's top-level globals (user functions/records/choices/namespaces), skipping names already registered (stdlib) and letting copied locals shadow globals, so compound expressions can reference them.
- **A spawned task's exit hook must fire while its `VM` is still alive**: in `create_spawn_callable` (`vm_dispatch_concurrency.cpp`) the `TaskExitGuard` is declared *after* `task_vm` so it destructs *first* (reverse declaration order) — the hook nulls this task's `ThreadState::vm` before `task_vm` is destroyed, closing a use-after-free window where a concurrent DAP `stackTrace`/`variables`/`evaluate` on the exiting task could dereference the freed VM. The cancelled early-out path constructs no VM, so it fires the hook directly instead.
- **DAP thread introspection must gate on `ThreadState::is_paused` — only a STOPPED thread has a stable stack to read.** `DebugSession::get_stack_trace` and `VariableInspector::lock_frame_and_vm` return empty/unresolved for a non-paused thread, tested under the same `ThreadState` mutex that guards `is_paused`. A free-running task VM concurrently mutates its call-frame vector (growth reallocation on `OP_CALL`, pops on `OP_RETURN`, `FunctionValue` teardown on task exit) and value stack, so dereferencing it would race the execution thread and intermittently `SIGSEGV` the adapter — the `test_task_spawn_exit_stress` sub-test (which issues `threads → stackTrace → scopes → variables` against concurrently-exiting tasks) targets exactly this, and already tolerates empty frames.
- **`DebugSession::evaluate` reads the target `VM` only under the thread's `ThreadState` lock, and only for a paused thread**: `terminate()` nulls every thread's `vm` pointer under that same lock (`null_all_vms`) before destroying the VM, so reading `state->vm` unlocked is a TOCTOU race. `frameId` 0 means the main thread's innermost frame; a non-zero `frameId` that no longer resolves (from an earlier stop) must fail with `<evaluation failed>` — it used to be reinterpreted as a raw VM frame index and silently evaluated in an unrelated frame. Separately, `evaluate_on_scratch_vm`'s `timed_out` flag must use `memory_order_release` on the writing debug-hook thread and `memory_order_acquire` on the reading evaluation thread (not `relaxed` on both) so the timeout write is visible to the reader without a data race.
- **The debuggee shares the adapter's process, so it must not share its stdin**: `luma_dap` reads DAP requests from stdin, and `Console.read_line`/`prompt` read `std::cin` — the same descriptor. A program reading input consumed protocol bytes (and blocked forever once none were left). `main.cpp` calls `detach_protocol_input_from_stdin()` (`dap_transport.cpp`) *before* constructing the transport: it duplicates stdin to a private descriptor (close-on-exec on POSIX) handed to `StdioTransport(int input_fd)` and points fd 0 — plus `STD_INPUT_HANDLE` on Windows — at the null device, so the debuggee sees end of input.
- **Task IDs are process-wide, and a task VM inherits *all* of its parent's debug hooks**: `VMTaskManager::next_task_id` is `static inline` (it was per VM, so every task VM numbered its own spawns from 2 and a nested task aliased a sibling's `ThreadStateManager` entry — `add_thread` overwrites by ID, leaving the other task unresumable and `terminate` unable to wake it). `VM::propagate_debug_hooks` copies the whole `DebugCallbacks` (it used to copy only the line/pause/exception hooks, so tasks spawned *inside* tasks were never registered and their breakpoints never fired). The task exit hook resets `tl_debug_thread_id`, because the pool reuses the worker thread.
- **A breakpoint set before compilation keeps its ID through resolution, and resolution is reported**: the server gives pre-session breakpoints globally unique negative IDs (`DapHandlerContext::next_pending_breakpoint_id`), carried in `BreakpointRequest::id`; `LineBreakpointManager` stores them in `path_breakpoints_` and `resolve_pending_breakpoints()` binds with the same ID and returns the newly bound breakpoints, which the engine sends as `breakpoint` events (`reason: "changed"`). Without that the editor showed them unverified for the whole session and `hitBreakpointIds` named IDs it never saw. Hit IDs can therefore be negative — test `!= 0`, not `> 0`.
- **Returning from a call lands on the caller's line as a "line change"**: `check_debug_hooks` only compares against the last line seen, so the hook fires again on the call line after the callee returns, re-triggering that line's breakpoint. `update_line_state` records the last `(file, line)` per frame depth in `ThreadState::frame_lines`; a shallower depth at the *same* recorded line is a return and skips the breakpoint check (an exception unwinding to a handler on another line still checks). Stop-reason precedence is exception → entry → pause → breakpoint → step, so a breakpoint hit during a step reports `breakpoint`.
- **Terminate must cancel, not only request a stop**: the stop token is observed only on line changes, which a program blocked in `await`, a `task_scope` join, or `Channel.receive` never reaches, so the disconnect handler's join hung. The engine runs the root VM under a `CancellationToken` (`VM::set_cancellation_token`, plus `detail::active_cancel_token` so channel waits poll it) created before the execution thread starts; `terminate()` cancels it, which also cancels every task (their tokens chain to it). OS-blocking natives (sockets, processes, HTTP) are not covered. The stop token likewise comes from a `std::stop_source` published before the thread starts — assigning `execution_thread_.get_stop_token()` after construction raced the new thread's first read.
- **Adapter diagnostics must bypass `std::cerr`**: while a program runs, `std::cout`/`std::cerr` are redirected into output events attributed to the debuggee, so the adapter writes its own diagnostics with `write_adapter_diagnostic` (`diagnostic_log.hpp`, C `stderr`) — including the shared transport's framing/JSON errors, routed there by the error callback `DapServer` installs (the transport's default callback writes to `std::cerr`). `LineBufferedStreamBuf` overrides `sync()` so `std::flush` (prompts) emits a partial line, every `stopped` event flushes pending output, and the buffers are scoped so trailing output is sent before `terminated`.
- **Scratch-VM evaluation must see the same names as the plain lookups**: `build_scratch_environment` copies locals, then the frame's upvalues, then program globals, defining each name once (`Environment::define` throws on a duplicate, and two sibling blocks declaring `i` produce two slots named `i`) — first slot wins, matching `VMIntrospector::find_local`. Missing upvalues made `base + 1` fail inside a lambda although `base` alone worked.
