# Learnings — GUI

> **See also:** The Solaris prelude is injected before type checking — see the core [learnings.instructions.md](learnings.instructions.md) § Architecture & Pipeline for the injection point. Stdlib module registration patterns are in [learnings-stdlib.instructions.md](learnings-stdlib.instructions.md).

## GraphicalUi

- Declarative GUI using Elm Architecture (Model–Update–View) with HTML/CSS/JS webview rendering.
- Conditionally compiled (`LUMA_HAS_WEBVIEW`). Requires: WebView2 (Windows, lazy-loaded), WebKit+Cocoa (macOS), webkit2gtk (Linux). Gracefully disabled if missing, or explicitly via `LUMA_FEATURE_WEBVIEW=OFF`. The stub path registers every function to throw a "not available" error (constants and the shared CSS validation helpers still work). Test split: `stdlib_test_graphicalui.cpp` (live module, registered when `LUMA_WEBVIEW_AVAILABLE`) vs `stdlib_test_graphicalui_stub.cpp` (stub path, registered otherwise).
- Features: 15 basic widgets, 24 composite widgets, 9 layout containers, 6 overlays, 7 chart types, 21 commands, 14 subscriptions, 17 styling helpers, routing, accessibility, animations.
- Commands are side effects as data — runtime executes them and delivers results as messages.
- **Headless mode & test API (how GUI examples are verified without a display)**: `LUMA_GUI_HEADLESS=1` runs the full Elm lifecycle (init → view → subscribe → optional scripted `update` messages from `LUMA_GUI_MESSAGES`) and returns *without* creating/running a webview — `render_view` and command/subscription application early-return when `state.webview == nullptr`. The `GraphicalUi.test_*` API (registered in `graphicalui_testing.cpp` via `define_native`, all using a throwaway `HeadlessApp`) drives interaction with no display: `test_init(config)→model`, `test_render(config, model)→tree`, `test_count(config, model, locator)→integer`, `test_click(config, model, locator, index?)→model`, `test_input(config, model, locator, value, index?)→model`, `test_event(config, model, locator, event, args?, index?)→model`, `test_find(config, model, locator)→widget`, `test_key(config, model, key)→model` (fires keyboard subscriptions), `test_message(config, model, message)→model` (delivers a message to `update`). Use these in `@test` blocks to assert behaviour, not just "doesn't crash".
- **Dev-assets iteration loop**: the JS/CSS/JSON embedded in `graphicalui_assets.hpp` is compressed and baked in at build time. Setting `LUMA_GUI_DEV_ASSETS=external/gui-framework` makes the runtime read raw `gui-renderer.js`/CSS/JSON (plus siblings `external/lucide`, `external/lit-html`, `external/uplot`) from disk, so you can iterate on the front-end **without a 5-8 min C++ rebuild**. The renderer is the `gui-renderer.js` shell with the per-category `renderers/*.js` fragments spliced in at the `// __GUI_WIDGET_RENDERER_FRAGMENTS__` marker; `scripts/generate_gui_assets.mjs` (prod) and `build_gui_renderer_js_dev` in `graphicalui_serialization.cpp` (dev) perform the identical splice, so keep the two in sync. To persist a change, run `node scripts/generate_gui_assets.mjs` to regenerate `graphicalui_assets.hpp`, then rebuild (the build does *not* invoke node — asset generation is a manual dev step).
- **"[unknown widget]" pitfall**: the browser renderer `renderWidget` (gui-renderer.js) is a pure `WIDGET_RENDERERS[type]` table lookup that falls back to `[unknown widget: <type>]`. A widget type present in `graphicalui_constants.hpp` but missing a renderer entry renders as plain text in the live webview — and headless `--test` *cannot* catch it (it inspects the C++ widget dictionary, not the JS). The `WIDGET_RENDERERS` table is split by category across `external/gui-framework/renderers/{basic,layout,advanced,interaction}.js` (mirroring `graphicalui_widgets_*.cpp`; menu/popover/combobox live in `interaction.js`). The guard is the `test_renderer_covers_all_widget_types` ctest in `tests/runtime/stdlib_test_graphicalui.cpp`, which parses `graphicalui_constants.hpp` widget types against the renderer keys in every `renderers/*.js` fragment plus the `CHART_TYPES` loop in `gui-renderer.js`. After adding a widget, add its renderer entry to the matching fragment and regenerate assets.
- **GraphicalUi HTTP commands run *natively*, not via the browser's `fetch()`** — the `http_get`/`http_post`/… commands dispatch through `cmd_http` → `do_http_fetch_text` (raw sockets/TLS), so they are **not** subject to CORS: a cross-origin GET the browser would reject with `Failed to fetch` now succeeds (this *reverses* the older browser-fetch behaviour — the `Http`-module workaround is no longer needed). The request runs **synchronously on the UI thread**, freezing the window until it returns, so the default timeout is `k_gui_http_default_timeout_ms` = 8 s — deliberately below the standalone `Http` module's 30 s. An off-thread design is intentionally avoided: `do_http_fetch_text` exposes no cancellation, so worker requests would have to be joined on window close, trading a freeze-during-use for a hang-up-to-timeout on shutdown. Pass an explicit larger `timeout` (trailing arg) for slow trusted endpoints.
- **String message routing**: an interactive widget callback that returns a bare `string` is routed by `apply_event_result` (`graphicalui_commands.cpp`) through the app's `update(model, msg)` — this is what makes `navigation_link("X", "navigate:/about")` work. `process_callback_result` stays the terminal primitive (it must not re-route, to avoid recursion). Relatedly, VM string indexing (`handle_string_index_get`, `vm_dispatch_collections.cpp`) must reject non-integer keys cleanly rather than calling `as_integer()` unchecked — an unchecked call surfaced as `bad variant access` when a string message reached a dict-typed `update`.
- **URL-scheme allow-listing is enforced twice and the two sides must stay in sync.** Model-derived strings reach anchor `href`, image/avatar `src`, `window.open` (`open_url`), and the download anchor (`download_file`); lit-html escapes attribute *values* but does **not** validate URL *schemes*, so a `javascript:`/`vbscript:` URL would execute script (and can reach the `__gui_event`→C++ bridge). The JS `sanitizeUrl` (`gui-renderer.js`) and C++ `has_allowed_url_scheme` (`graphicalui_commands.cpp`) are deliberate mirrors: each strips ASCII tab/newline/CR and lowercases the scheme (defeating `java\tscript:`, and leading-whitespace/mixed-case forms such as a space before `JavaScript:`) and permits only an explicit set — links & `open_url` → `http,https,mailto,tel`; image/avatar & `download_file` → `http,https,data,blob`. A scheme-less (relative) URL is always allowed. Change one side → change the other.
- **The model JSON is embedded inside a `<script>` element** in the initial HTML (`GraphicalUi.app`, `graphicalui_module.cpp`), so the serializer (`value_to_json`, `graphicalui_serialization.cpp`) must escape with the slash-escaping `luma::json_escape` (`/`→`\/`, turning `</script>` into `<\/script>`) — **never** the non-slash `json_escape_string` variant. Pinned by `escape_utils_test.cpp::test_json_escape_closes_script_tag`.
- **A single malformed value wipes the entire GUI render**, because the webview `eval`s the serialized tree (`__gui_render({…})`) and any throw triggers the top-level error renderer. Three guards: (1) `value_to_json` coerces non-finite doubles (NaN/±inf) to `null` — the bare tokens `nan`/`inf` are invalid JS; (2) the event handlers `handle_keyboard`/`handle_resize`/`handle_focus_change` (`graphicalui_events.cpp`) check `event.has_string()`/`has_bool()` before reading the payload, else `std::bad_variant_access` escapes; (3) `cmd_random` orders its bounds with `std::min`/`std::max` because `std::uniform_real_distribution{a,b}` is undefined behaviour when `a>b` (e.g. `GraphicalUi.random(10, 1, cb)`).
- **The renderer never fully clears the DOM between renders, which imposes node-ownership invariants** (`gui-renderer.js`/`gui-charts.js`): (1) a `virtual_list` viewport must have exactly one lit-html render root — the parent template emits it *empty* and a deferred `flushPendingVlists` windows items in; two roots writing one node corrupt part bookkeeping. Its once-bound scroll handler reads live data from `container.__vlMeta` (refreshed each render) so it stays correct across model updates. (2) Chart axis label formatters read `container.__chartMeta.labels` live, not a closure captured at creation (uPlot reuse only calls `setData`, so a captured array goes stale). (3) The visually-hidden chart-summary a11y node is reused via `querySelector`, not re-appended, or duplicate hidden summaries pile up in the a11y tree. (4) `flushDeferred` drains queues in dependency order — vlist windows first (their items enqueue charts/accessible/ARIA/nested lists), then charts → accessible → per-widget ARIA.
- **Per-widget ARIA & the construct-context contract**: any widget accepts `aria_*` (and `role`) keys in its style dictionary (the C++ side serialises them to `_aria_*`; `buildAriaAttrs` collects them). Because lit-html static templates can't bind arbitrary attribute names, they are applied post-render located by element id — a synthetic `__gui_attr_*` id is assigned when the author supplied none. Widgets that bind a *deferred* callback (`slider`, `switch`, `text_area`, `number_input`, `form`, `drop_target`, `paginator`, `infinite_scroll`, `wizard`) or read the live window size (`responsive`) **throw if built outside an app/`view` context**; pure-data widgets (`draggable`) and command builders (`delay`, `random`, `debounce`, `http_post`, …) are constructible anywhere — handy for unit tests.
- **On Linux, `graphicalui_module.cpp` must include the real `<gtk/gtk.h>` and call `gtk_window_maximize(GtkWindow*)`** — the bundled `webview.h` already pulls GTK into the TU once `LUMA_HAS_WEBVIEW=1`, so the earlier local `extern "C" void gtk_window_maximize(void*)` forward declaration (used to maximise the window while the Linux backend was always the stub, before WebKitGTK was installed on CI) now conflicts with GTK's real prototype and mis-converts `void*`→`GtkWindow*` at the call site.

## Solaris (Prelude GUI Surface)

*Canonical guides: [../documents/Luma_Solaris_Architecture.md](../documents/Luma_Solaris_Architecture.md) (full design vision — broader than the shipped surface) and [../documents/Luma_Solaris_Guide.md](../documents/Luma_Solaris_Guide.md) (exact shipped API). The notes below are a quick-reference summary.*

- **Solaris is a beginner-first Model–View–Update (MVU) GUI surface layered over the low-level `GraphicalUi` web-view engine**: the app supplies a `Model` record, an `update` function, and a `view` built from `Solaris.*` elements with fluent modifier chains via the pipe operator; effect/subscription wrappers (`notify`, `set_scheme`, `after`, `fetch`, `every`, `on_key_press`) forward to the engine, which reconciles the immutable `View` tree onto `GraphicalUi`. Beginners write only Luma — never HTML/CSS/JS.
- **It ships as a built-in *prelude*, not an includable library** (`core/analysis/prelude/`). It is authored as ordinary Luma in `gui_prelude.luma` (so the lexer/parser/type-checker/editor tooling treat it as the language it is), then embedded verbatim by `scripts/generate_prelude_asset.mjs` into `gui_prelude_generated.hpp` as an **uncompressed byte array** — a byte array (not a string literal) sidesteps MSVC's 16 KB string-literal limit, and leaving it uncompressed keeps the analysis layer free of any miniz/decompression dependency. Regenerate manually after editing the `.luma` (the build does not run node), mirroring the `generate_gui_assets.mjs` GraphicalUi dev-asset split.
- **Injection is a conditional pipeline step between include resolution and type checking**, gated on the source mentioning `Solaris` as a **standalone identifier** (`contains_identifier_token` in `common/string_utils.hpp` / `SourceManager::any_source_contains_word`, so a longer name like `mySolarisHelper` never triggers it) and guarded against double injection by scanning for an existing `namespace Solaris`. Non-GUI programs pay nothing and get no global-type pollution.
- **Design-token choice types (`Emphasis`, `TextScale`, `Weight`, `Spacing`, `Align`, `Justify`, `Length`, `Radius`, `Scheme`) and the `View` record are declared top-level, NOT under `namespace Solaris`** — because the type checker cannot resolve a namespaced record in a `with`-update nor destructure a namespaced choice data-variant. The element constructors, fluent modifiers, reconciler, and app builder/runner live under `namespace Solaris`.
- **The two injection entry points (`gui_prelude.hpp`) differ in how prelude source is attributed.** `inject_gui_prelude(program, source_manager)` registers a virtual source file `<gui-prelude>` via `SourceManager::load_virtual`, so prelude AST locations attribute to it and never shift the user's line numbers — used by the interpreter (`program_loader.cpp`), REPL (`repl.cpp`), and DAP scratch compiler (`expression_compiler.cpp`). `inject_gui_prelude_tagged(program, prelude_file_id)` retains no source text and tags declarations with a caller-owned file id — used by the LSP (`lsp_analysis_service_impl.cpp`), which allocates an id past the include range (`includes.next_file_id`) and **drops every diagnostic carrying it**, because it renders diagnostics by line against the user's own document where a prelude location would otherwise paint on the wrong line. A malformed prelude fails safe (prepends nothing); a debug `assert` makes the build-time defect loud. Tests: `tests/analysis/gui_prelude_test.cpp`, `tests/features/stdlib/solaris_functions.luma`; examples `examples/applications/solaris_{counter,gallery,showcase}.luma`.
