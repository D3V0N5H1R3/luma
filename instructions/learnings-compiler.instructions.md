# Learnings — Compiler

> **See also:** The VM executes what the compiler emits — see [learnings-vm.instructions.md](learnings-vm.instructions.md) for dispatch and stack layout. Stdlib type signatures that affect compilation live in [learnings-stdlib.instructions.md](learnings-stdlib.instructions.md) § StdlibCatalog.

## Module Layout & Key Files

- The compiler is split into core files: `compiler.cpp` (core), `expression_compiler.cpp`, `statement_compiler.cpp`, `optimizer.cpp` with sub-files `_constant_fold`, `_control_flow`, `_dead_code`, `_peephole`, and `optimizer_internal.hpp`. Further decomposed into: **PatternCompiler** (all pattern-matching compilation with `PatternTestArgs`/`GuardResult` structs), **VariableResolver** (3-level local→upvalue→global resolution with `VarSlot` struct), **ConstFolder** (compile-time constant folding for binary/unary ops via `IConstantEmitter` narrow interface). All helpers access the compiler through the **ICompilationBackend** pure virtual interface (implemented by **CompilerAccess**). Type definitions are extracted into `compilation_context.hpp` (CompilerScope, CompilationContext, Local) and `compiled_function.hpp` (CompiledFunction, FunctionDebugInfo). Supporting modules: `chunk.hpp/.cpp` (bytecode container), **ConstantPool** (extracted deduplication with `std::bit_cast` for doubles), `opcode.hpp` (105 opcodes), `emitter.hpp` (bytecode emitter helpers), `bytecode_serializer.hpp/.cpp` (persistent `.lumc` binary format), `compilation_cache.hpp/.cpp` (in-memory LRU cache), `verifier.hpp/.cpp` (structural bytecode verification).

## Non-Obvious Patterns

- The optimizer has 3 levels: L0 (none), L1 (peephole), L2 (adds `constant_fold`, `unary_fold`, `comparison_fold`, `dead_code`, `jump_threading`, `dead_store`, `tail_call` — run to convergence, then `compact()`). Cross-function inlining (`inline_small_functions`) must run before per-chunk `optimize()` so inlined code benefits from passes. Constant folding is handled by the extracted **ConstFolder** class.
- **Constant folders never widen and never change error behaviour**: a fold whose integer result would overflow is skipped, leaving the operator for the VM to raise `integer overflow in …` (folding `INT64_MAX + 1` to a `number` disagreed with the VM). Mixed integer/number equality folds through `Value::equals`, which is exact, not through `double`. Folds and peephole rewrites that add a constant skip once the pool is full (`add_constant` would throw `std::overflow_error`).
- **A fused peephole opcode changes runtime error wording.** `One; Add` → `Increment` and `One; Subtract` → `Decrement` were removed: `Increment` reports "integer overflow in increment", so `x + 1` named the wrong operation (and type errors for an `any` operand were worded differently). A fusion is only sound if the replacement raises the *same* errors with the *same* text for every runtime value; `++`/`--` still compile to `Increment`/`IncrementLocal` directly. The same rule rules out arithmetic "identity" cancels (`x + 0`, `-(-x)`, `x // 1`, `!!x`) — see the comment block in `optimizer_peephole.cpp`.
- **The inliner copies only straight-line bodies.** `inline_small_functions` rejects a callee whose body has a jump, a terminator, or any control-flow opcode before its final `Return`, and never inlines a `Call` that is a jump target. Copying a mid-body `Return` returned from the *caller* (`integer v = (() -> { return 1 })()` skipped the rest of the caller at `-O2`), and a jump landing on the replaced `Call` would land inside the copied body.
- **Two optimizer passes were intentionally removed as unsound at the bytecode level** (documented at `optimizer.hpp:94-102`): the multiply→shift **strength reduction**, and **constant propagation** (`GetLocal`→`Constant` for single-assigned locals). The optimizer sees only a `Chunk` — no local scopes/liveness — so a slot holding a single-assigned constant can be freed at scope-exit and reused by a later binding whose initializer is left on the stack (an *invisible* write with no `SetLocal` opcode); the stale constant then propagates into the wrong variable's reads, miscompiling exotic shapes like `match case == <block-with-locals>`. Re-enabling either needs a proper per-slot liveness/depth analysis. Removing an optimization can only improve correctness, so removal (not a risky fix) is the project precedent — **do not naively re-add a propagation/strength-reduction pass.**
- **Chunk** (`core/runtime/compiler/chunk.hpp`): Bytecode container. Source map stored as sparse `(byte_offset, SourceLocation)` pairs — one entry per opcode saves ~60% memory vs per-byte tracking. Source-location bookkeeping and the deduplicating name pool are now extracted into focused **SourceMap** (`source_map.hpp`, a binary-searched sparse map) and **NameTable** (`name_table.hpp`, interned 16-bit name handles) types that Chunk composes — so the name vector and its O(1) dedup index can no longer drift out of sync. **ConstantPool** (`constant_pool.hpp`) extracted: manages constant deduplication (integers, strings, and doubles use separate maps; doubles use `bit_cast` for exact equality to distinguish `0.0` from `-0.0`). Max 65,536 constant pool entries (uint16_t addressing). A full constant pool or name table is reported as a compile-error diagnostic, never as an escaping `std::overflow_error`.
- **Jumps are u32 everywhere** (`Jump`, `JumpIfFalse`, `JumpIfTrue`, `Loop`, `NullCoalesce`, `TryCatch`): `emit_jump` writes the 4-byte placeholder `0xFFFFFFFF` (`k_jump_placeholder`) and `patch_jump` writes `code.size() - offset - 4`. `MakeTuple` takes a u16 count. `And`, `Or`, `Pipe`, `ErrorPipe`, `ConstantLong`, and `MatchStart`/`MatchArm`/`MatchEnd` are reserved: still in the opcode table (105 opcodes), accepted by the VM and verifier, never emitted.
- **`patch_jump` (and `emit_jump`/`emit_loop`) must clear `last_was_return`.** `end_function` skips the implicit `None; Return` when the last statement was a `return`. In `if c { … } else { return }` the else-branch's `return` set the flag, then patching the then-branch's jump made that jump land at `code.size()` — the implicit return was skipped, and the function ran off its bytecode ("bytecode truncated: not enough bytes for operand"). The verifier now also rejects a jump to `code.size()` and reports control flow that falls off the end, so `--verify` catches this class.
- **Value-block scratch slots (compiler invariant)**: local slots are assigned as `locals.size() - 1` (`declare_local`), which assumes the value being bound is the first temporary above the locals region. When a value-producing block — a `match`/`if` used as an expression, or any sub-expression that declares locals mid-compilation — is compiled while operand-stack temporaries are already live *beneath* it (e.g. the container+index of `container[index] = match {…}`, prior call arguments, the left operand of a binary op, dict keys, pipe stages, interpolation parts), the block's locals get slots that ignore those temporaries → `GetLocal`/`SetLocal` hit wrong stack positions → corruption (`cannot index-assign into 'string'`, `cannot call 'string'`, `bad variant access`, or silently wrong values). Fix: bracket every such site with `reserve_scratch_slots(count, loc)` / `release_scratch_slots(count)` (defined in `assignment_compiler.cpp`, declared on `compiler.hpp` and the `i_variable_manager.hpp` role interface) — they declare empty-named placeholder locals so block locals land at their true runtime slots; release emits **no** runtime pops (the temporaries are consumed by the trailing `IndexSet`/`SetField`/compound op). For a balanced single-scope pair prefer the `ScratchSlotGuard` RAII wrapper (`scratch_slot_guard.hpp`, mirrors `ScopeDepthGuard`) so the count is stated once and can't leak on an early exit; keep the explicit `reserve`/`release` calls only for per-iteration or unequal-count shapes. Existing callers: `assignment_compiler`, `binary_operator_compiler`, `collection_compiler`, `interpolation_handler`, `pipe_compiler`, `expression_compiler`, `declaration_compiler` (one slot around a default parameter value — `JumpIfFalse` *peeks*, not pops, its boolean condition, so that temporary stays live while the default, possibly a value block, is compiled), and `pattern_compiler` (value-form `match` reserves `subject_temps_below + 1` slots around each arm's pattern test — a `case == <expr>` comparison value can be an arbitrary locals-declaring block sitting above the untracked subject + `Dup` temps; value-form has 2 untracked temps below so `subject_temps_below=1`, statement-form's subject is a tracked hidden local so `subject_temps_below=0`), plus the three paths that compile `finally` bodies inline on an exit: `compile_return` and the failure path of `?` (`compile_unary`) each hold a `ScratchSlotGuard{1}` for the value they are about to return while `emit_try_unwind` emits the pending `finally` bodies, and `emit_loop_scope_unwind` (break/continue) runs `emit_try_unwind` **before** popping the loop's locals. **When adding any compile path that leaves temporaries on the stack before compiling a sub-expression, you must reserve scratch slots** or you reintroduce this stack-corruption class.
- **`finally` bodies compiled on an exit path must see the exact runtime stack layout.** A `finally` body is compiled inline wherever the protected code can leave — normal completion, the error path, `return`, `?`, `break`, `continue`. On each exit path, any value already on the operand stack needs a scratch slot, and the loop's locals must still be on the stack: `try { return 42 } finally { string m = "done"; print(m) }` printed `42` because `m` was given the return value's slot, and `break` inside `try` printed `<native function print>` because the loop locals were popped before the `finally` body read one. Feature tests cover `return`/`?`/`break`/`continue` through `finally`.
- **`try`/`catch`/`finally` is two nested handlers** (`compile_try_catch_finally`): `try { try A catch(e) B } finally C`, so `C` also runs when `B` throws or exits. `emit_try_unwind` detaches each handler before compiling its `finally` (bounding recursion for `try { return 1 } finally { return 2 }`) but keeps the outer ones active so a nested exit still runs every enclosing `finally`.
- **`?` inside `@main` compiles to a plain `Unwrap`**: `@main` has no caller to receive a propagated failure, so the old `TryEnd…; Return` path silently exited with code 0 and skipped an enclosing `catch`. Now a failure raises a `RuntimeError` with the failure text (`none` gives the standard unwrap message). Lambdas declared inside `@main` keep normal `?` semantics.
- **An empty interpolation piece must still push a value** (`interpolation_handler.cpp`): `"${""}"` pushed nothing, so the `Interpolate` count no longer matched the values on the stack.

## Bytecode Serialization & Caching

- Two-level caching system: (1) `CompilationCache` — in-memory LRU (default 128 entries), keyed by `(absolute path, content hash, options)`, thread-safe (mutex). `Options` carries the full `OptimizationLevel`, not a `bool optimized`: with a boolean, `-O1` and `-O2` artifacts collided and one level's bytecode was served for the other. (2) `BytecodeSerializer` — disk-based; `run_file` (in `cli_runner.cpp`) writes compiled bytecode to a `<source>.lumc` file **next to the source** via `BytecodeSerializer::cache_path_for`, which just does `replace_extension(".lumc")`. On the next run it reads/validates that file and skips compilation on a hit. The disk cache key mixes the source hash with the optimization level. Only normal runs write `.lumc`; `--check` and `--test` compile in memory only, and `--strict` and `--verify` bypass both caches (a cache hit would skip the strict-warning check or the verifier). `CompilationCache` is injectable via `run_file()` for testability.
- **Both cache levels must check included files, not just the entry point.** Their keys hash only the entry point's text, so before format v4 editing an `include`d file kept running the old bytecode. `run_file` now records every on-disk file the `SourceManager` loaded (`collect_source_dependencies`, skipping the entry point and `is_virtual` compiler-injected sources) as `SourceDependency{path, content_hash}`, stores the list in the `CompilationCache` entry and the `.lumc` dependency table, and rejects either cache when `are_source_dependencies_current` finds a dependency missing or re-hashed differently. The re-hash must mirror `SourceManager::try_load` (binary read, UTF-8 BOM stripped), or every BOM-prefixed include would read as edited. Known gap: a newly created file that would *shadow* a resolved include (e.g. earlier on `LUMA_PATH`) is not detected until a dependency or the entry point changes.
- `.lumc` binary format: 28-byte header (`"LUMC"` magic, u32 format version, u32 flags, u64 source hash via **FNV-1a** — `fnv1a_hash`, not xxHash — u64 timestamp), then the dependency table (u32 count + per-dependency path string and u64 content hash), followed by the function table (count + per-function metadata, bytecode chunks, constant pools, source maps).
- `BytecodeSerializer` handles serialize/deserialize with typed `DeserializeResult` containing error codes (`BadMagic`, `VersionMismatch`, `BadDependencyTable`, `CorruptFunction`, `HashMismatch`, etc.) and detail strings.
- Format version currently 9 (v1→v2 widened every serialized string's length prefix from u16 to u32, so a string constant or name of ≥ 65,536 bytes no longer wraps its prefix and desyncs the rest of the stream — `k_string_length_prefix_bytes` went 2→4 accordingly; v2→v3 removed the unemitted bitwise opcodes; v3→v4 added the dependency table; v4→v5 added `WidenNumber`, renumbering `Clone`/`EndModule`; v5→v6 added the copy-on-write opcodes `UniqueLocal`/`UniqueUpvalue`/`UniqueGlobal`/`GetFieldUnique`/`IndexGetUnique`, renumbering `EndModule`; v6→v7 changed no layout, only invalidating caches with wrong code for record literals before their declaration and immediately called lambdas; v7→v8 changed no layout, only invalidating caches built before the codegen fixes for `if`/`else`-return fall-off, `return`/`?`/`break`/`continue` through `finally`, the `-O2` inliner, `?` in `@main`, and `"${""}"`; v8→v9 widened each source-map entry from 16 to 24 bytes to store the token start line and column, so runtime errors from cached bytecode keep their caret on the token — `SerializerLimits::k_source_map_entry_bytes` went 16→24). Bump `k_bytecode_format_version` for incompatible changes **and for codegen changes that fix wrong behaviour** (otherwise a stale cache keeps running the old code), and regenerate `fuzz/corpus/bytecode_deserializer/minimal_valid.lumc` so the fuzzer's seed is not rejected at the version check. If only the version changed, bumping its big-endian version bytes 4–7 suffices; if a section's layout changed (as in v9, which contains source-map entries), regenerate it by running `luma` on a minimal `@main` program and copying the resulting `.lumc` (it embeds no paths when there are no includes).
- **Record declarations are registered before any declaration is compiled** (`DeclarationCompiler::register_record_declarations`, called first in `Compiler::compile`). Function bodies compile on the spot in source order, so a record literal in `main` used to miss a record declared later in the file: the compiler only warned and built the record from the explicit fields, silently dropping defaults. The REPL overload also takes the earlier inputs' programs for the same reason. Namespaced records also register their bare name with `try_emplace`, so they never shadow a top-level record.
- **Value semantics = shared storage + copy-on-write at write sites.** Copying a `Value` (bind, pass, return, capture, store in a collection) shares its heap object, so a write must never touch shared storage. The compiler compiles the *container path* of every assignment / compound-assignment / `++`/`--` target with `Compiler::compile_write_target`, which emits `UniqueLocal`/`UniqueUpvalue`/`UniqueGlobal` on the root variable and `GetFieldUnique`/`IndexGetUnique` for each intermediate step; each makes that level exclusive (`Value::make_exclusive`, a shallow copy when `use_count() > 1`) before the final `SetField`/`IndexSet` writes in place. Any new in-place write path must go through `compile_write_target` — compiling the container with plain `compile_expression` silently reintroduces aliasing (an immutable copy, a returned value, or an `Array.repeat`ed element changing when the mutable original is written). The check must run on the variable's own slot *before* the value is pushed, because the operand-stack copy adds a reference of its own. A target rooted in a temporary (`Reference.get(cell)[0] = 1`, `make_point().x = 5`) can still share storage, so the type checker rejects it and `compile_write_target` emits `Clone` after compiling it (debugger expression evaluation compiles without the type checker).
- **A compiler change does not invalidate `.lumc` caches unless the format version changes.** Caches are keyed by source and dependency hashes, not by compiler version, so after changing codegen within one format version, running an example can silently execute stale bytecode from a previous build. Delete the untracked `*.lumc` files under `examples/`, `tests/`, and `benchmarks/` before judging a codegen change by program output (the tracked ones under `fuzz/corpus/` are seeds — leave them).
- **Integer → number widening is type-checker driven.** The AST carries no resolved types, so the compiler's syntactic `emit_number_widening_if_needed` only covers declared `number` variables. Every other flow — record fields and `with` overrides, choice payloads, arguments (positional, named, piped, generic), returns, defaults, `if`/`match` branch values and `??` fallbacks, collection/tuple elements, mixed literals like `[3, 4.5]`, element-taking stdlib calls (`Array.push`/`insert_at`/`set`/`concat`, `Dictionary.set`), and generic user types (`List<integer>` → `List<number>`) — is marked by `type_check_helpers::mark_numeric_widening` on `Expression::numeric_widening` at the check site, and `Compiler::compile_expression` emits `IntToNumber` (plain `number`) or `WidenNumber <pattern>` (nested, e.g. `array<number>`, `(number,_)`) after the marked expression. Literal elements are marked individually so they constant-fold; a marked `return f(x)` is excluded from the hand-compiled tail call, since the widening must run after the call. New assignment-like check sites must call the marker, or values silently keep their integer representation (and print as `5` instead of `5.0`).
- `BytecodeVerifier` validates structural integrity (valid opcodes, jump targets on instruction boundaries and strictly inside the code — a jump to `code.size()` is rejected, constant/name indices in-bounds, upvalue/local slot ranges) in a linear pass, then checks stack depth by walking the control flow graph from the entry point with an exact pops/pushes model per opcode (`instruction_stack_effect`). The walk also reports control flow that can fall off the end of the chunk without a terminator. Each frame starts with `arity + 1` values — slot 0 holds the callee. The walk follows jump, loop, catch-handler (which pushes the error value), and loop-exhaustion edges (`ForIterStep`/`ForIterStepKV` push only `false` when exhausted). At merge points it simulates the deepest incoming stack, so it never rejects valid code. Stack growth across a loop back edge is reported directly. A step budget of 64 visits per instruction bounds the walk, because it runs on every deserialized (possibly crafted) `.lumc` file. Re-walking on deeper stacks is otherwise quadratic. The VM's runtime stack-depth checks stay on regardless. `--verify` runs it after compiling. It also runs on every deserialized `.lumc`, where a clean result sets `is_verified`, letting the VM skip operand-truncation and constant-index checks — both proven by the linear pass. A straight-line stack simulation is unsound here: before the walk, branch pops were double-counted and `MakeClosure`/`MakeRecord`/`SetField`/… had no modelled effect, so every program defining a function failed verification and cached bytecode never took the fast path. Keep `instruction_stack_effect` in sync when adding an opcode; `verifier_test` checks it against the opcode table's fixed effects.
- **Bounds-check counts before `reserve()` when deserializing `.lumc`**: an attacker-controlled length (e.g. the source-map entry count) can otherwise trigger a huge `reserve()` and OOM. The deserializer rejects any count whose implied byte size exceeds the remaining input before reserving — `if (r.error() || !r.has_remaining(map_count * SerializerLimits::k_source_map_entry_bytes)) error;`. Apply the same `has_remaining()` guard to every `reserve(count)` driven by untrusted input — the top-level function vector likewise rejects `func_count` against `SerializerLimits::k_min_function_bytes` (31, the smallest a fully-empty serialized function can be) and returns `DeserializeError::BadFunctionCount` before `functions.reserve()`, joining the source-map (`k_source_map_entry_bytes`) and name-table guards (found via fuzzing the bytecode deserializer).
